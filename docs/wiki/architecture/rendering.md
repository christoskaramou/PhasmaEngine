# Rendering And RHI Notes

The render path is split between PhasmaRuntime's shared scene renderer and PhasmaCore's backend-neutral RHI wrappers. Code remains the source of truth; use this page for cross-cutting pitfalls that are easy to miss when reading one file at a time.

## Scene Pipeline Script

A scene's pipeline is its render path (render mode, HDR, dynamic rendering: plain controls), its pipeline script, and the values that script exposes: culling/LOD/cluster, shadows, lighting and GI, the default post-process profile and G-buffer formats, plus any passes the script adds. Since 2026-10-09 (the user's plan C, replacing the pass list and `.pepipeline` assets) the script is the pack: [ScriptSystem.cpp](../../../Phasma/Runtime/Code/Script/ScriptSystem.cpp) `LoadPipelineScript` runs `SceneSettings::pipeline_script` (Assets-relative; empty = [default_pipeline.lua](../../../Phasma/Runtime/RuntimeAssets/Scripts/Pipeline/default_pipeline.lua)) at every scene load in the editor and the player, in edit and play mode, whether or not the scene has a Scene Settings node.

- `exposed {...}` declares its values. One named after a scene setting (`settings.get/set` names, plus `lod_distance_1..3` and `depth_bias_constant/_clamp/_slope` for the two arrays) mirrors that setting: a loaded scene keeps its own saved value, and the script's literal applies only when the script is picked in the editor (`ReloadPipelineScript`). Its other values persist in `SceneSettings::pipeline_values` (scene JSON `pipeline_values`).
- `init()` adds its passes (`render_graph.add_fullscreen_pass`, `render_graph.add_pass`); it runs at load and again when one of its own values changes. Passes added from the pipeline script belong to it (`SetLuaRenderPassOwner`) and are cleared when the scene or the script changes, or on a Lua reload, which runs the script again.
- `pipeline.base()` returns a fresh table of the default script's values, so a project script extends the engine's instead of copying it: `local p = exposed(pipeline.base()); p.ink = 0.8`. Its `exposed_when` nesting comes along.
- `exposed_when { cas_sharpness = "cas_sharpening" }` nests a value under a bool value: the panel shows it indented under that switch and hides it while the switch is off (the default script nests every pass's settings under its switch, and CAS under TAA). Node scripts' Exposed Variables honour it too, and both panels label values readably (`ui::ExposedLabel`: `cas_sharpness` -> "Cas Sharpness", `IBL_intensity` -> "IBL Intensity").
- C++ (2026-10-09, ABI 28): `pipeline_script` may name `cpp:<Type>`, a `ScriptKind::Pipeline` script in the game module (`PHASMA_PIPELINE_SCRIPT`). It is constructed at load and again after one of its own values changes; `ExposeNumber` / `ExposeBool` / `ExposeBase` feed the same panel and values (`ScriptSystem::ExposePipelineValue`); its passes belong to the pipeline, so Play Stop keeps them (`CppScriptSystem::CreatePipeline`). The script is created once the module has loaded (`ModuleLoads`), and again after a live module reload. AgainstTheHero's C++ scene uses `cpp:AthPipeline`; its Lua scenes use `ath_pipeline.lua` with the same ink values.
- `render_graph.add_fullscreen_pass{name, shader, order, params, thickness_at_1080, min_thickness}` records natively every frame ([FullscreenPasses.cpp](../../../Phasma/Runtime/Code/Render/FullscreenPasses.cpp), shared with the C++ scripts' `AddFullscreenPass`), so a pipeline needs no Lua per frame. `render_graph.add_pass` takes `order` again.
- Scene Settings > Pipeline ([PipelineControls.cpp](../../../Phasma/Editor/Code/GUI/Widgets/PipelineControls.cpp)): the render path, a script picker (Engine default, a .lua under `Scripts/Pipeline`, or a `cpp:` pipeline script from the game module) and every exposed value (`DrawExposedValues`: readable labels, nested under their switch, otherwise name order; no ranges or colour pickers). The Animator has no script system and shows only the render path. `render_pass_orders` still loads from scenes; nothing edits it.
- The values stay in `SceneSettings` in memory, so the renderer, post-process zones (which override the default profile), Lua `settings.*` and the Animator read them as before. One pipeline is active per frame.

Verified 2026-10-09: `.testpool/tests/pipeline_script.py` (Player, temp project: a script extending `pipeline.base()` kept the scene's saved `bloom`, restored its own `tint` from `pipeline_values`, and its fullscreen pass compiled its shader; a scene without one loaded the default and kept its settings); AgainstTheHero's `ath_pipeline.lua` draws the ink paper and outlines in editor edit mode, during Play and after Stop, in the C++ match on Vulkan and DX12 and in the Lua game; the editor viewport of `spud_fields_3d_v1` was unchanged (0 px) between the engine runner landing and the pass list's removal. Removed with it: the pass list (drag, sort numbers, Add Pass, minus buttons), templates, `.pepipeline` load/save and the scene `"pipeline"` key (old assets on disk are inert), `script_passes`, `RenderGraph::OrderConflict`. "Forward+" is tiled light culling for the deferred lighting passes; the engine has no forward-lit opaque path.

Columns and checks (2026-10-08): passes with equal sort numbers form a column; `RenderGraph::Execute` issues a multi-pass column's input barriers as one deduplicated batch, then records its passes in pass-id order. `RenderGraph::Compile` records problems (`GetProblems`): a read with no earlier writer (a pass reading an image it also writes, such as TAA and GI history, counts only when a later pass writes it too), two passes of one column sharing a resource that one writes, or a pass sampling an image it renders into. `RenderGraph::NewProblems` compiles the graph at the current and the proposed orders and lists what a move adds. Problems already present at the current orders do not count. The light passes read the shadow maps under the Shadow pass's own condition, `shadows` with an active Scene Settings node (`ShadowsActive` in [LightPass.cpp](../../../Phasma/Runtime/Code/RenderPasses/LightPass.cpp)); before 2026-10-10 they sampled maps the Shadow pass had not rendered while the node was inactive. Pool tests `render-warnings-vulkan`/`-dx12` fail on any `[Descriptor]` or `[RenderGraph]` warning through GI toggles, resizes, render modes, occlusion culling and a reload (verified 2026-10-10). `RGBuilder::ReadBuffer/WriteBuffer` only record ordering, with no barriers. The cull draw lists (counters buffers of the frustum set, set A and set B), the Forward+ tile buffer and the particle buffer are declared by their producers and consumers. Those declarations resolve `GetActiveScene()`, not the pass's `m_scene`: the graph compiles outside recording, and Depth, DepthLate, both G-buffer passes and SelectionOutline clear `m_scene` after recording, so until 2026-10-08 their buffer reads were invisible to the checks. An attachment a pass LOADs (`IRenderPassComponent::DeclareOutputs` passes `loadOp == PE_LOAD_OP_LOAD`; script-pass writes count as loads) also orders the pass after the image's writer, again without a barrier. With no earlier writer it is a problem only when a later pass writes the image; otherwise it is last frame's contents. Passes with their own `DeclareOutputs` do not carry the flag. The Player's deferred graph (LDR bloom and colour grading after the UI) compiles with `Compile(false)`: its images come from the main graph, so it has nothing meaningful to report. Verified 2026-10-08 with the Player on scenes that moved Depth before Culling and GBufferOpaque before Depth: both fell back to the default order with `[Pipeline]` warnings naming the buffer read and the depth load; the default order logs nothing new. Both renderer hosts rebuild their graph when `render_pass_orders_revision` changes. Saved orders that break the frame fall back to the default order at graph build with a `[Pipeline]` warning (`SceneRendererCore::AddScenePassesToRenderGraph`). Within a column, passes record in pass-ID order ([RenderGraph.cpp](../../../Phasma/Core/Code/API/RenderGraph.cpp)).

Removed 2026-10-08, the user's decision after comparing Unity and Unreal: the Window > Pipeline Editor node graph, pin bindings (`PinTarget`), pipeline-authored images and data nodes (`PipelineData`). Not covered by the pipeline script yet: changing the shadow map size, cascade count or G-buffer format live (those apply on renderer re-init).

## Background Frame Pacing

All six Phasma windowed apps (Editor, Player, Animator, Launcher, Cook UI and Profiler) call [FrameTimer::Tick / EndFrame](../../../Phasma/Core/Code/Base/Timer.cpp) around each frame. `Tick` records the start without waiting. After rendering and presentation, `EndFrame` waits only for the remaining background frame budget (30 FPS by default; its target argument accepts other integer rates, with zero disabling the cap). One global setting turns it off for every app: `"background_fps_cap": false` in `phasma_settings.json` beside the executables, read when `FrameTimer` is created (absent or unreadable = capped). `FrameTimer::SetBackgroundCap`, from Lua `engine.set_background_fps_cap(bool)`, changes it for the running session without saving; the editor pool tests lift it that way at start-up, since their window is never focused. Verified 2026-10-07 in the editor: key false = 1258-1633 fps unfocused, key absent = 30 fps. CPU work stamps precede this wait; the next frame's delta includes it. Headless Cook/Export operations do not run the window frame loop.

The deadline advances by a fixed period on a steady clock, so late wake-ups do not accumulate into a lower average. Long stalls reset missed deadlines instead of producing a burst of catch-up frames. Any focused SDL window in the process, including a detached Editor/Animator panel, clears the background schedule. Windows uses a high-resolution waitable timer, with a standard-library wait if creating, arming or waiting on that timer fails; other platforms use the standard-library wait. Neither path spins the CPU.

The engine hosts pace after their frame pump in [Editor](../../../Phasma/Editor/main.cpp), [Player](../../../Phasma/Runtime/Code/Runtime/PlayerHost.cpp) and [Animator](../../../Phasma/Animator/main.cpp); the SDL-rendered loops in [Launcher](../../../Phasma/Launcher/main.cpp), [Cook UI](../../../Phasma/Cook/CookUI.cpp) and [Profiler](../../../Phasma/Profiler/main.cpp) pace after `SDL_RenderPresent`. Local pool test `background-fps` exercises the built shared timer with SDL's dummy video driver: 30/60 FPS averages with variable work and host overhead, uncapped main and secondary focus, no extra wait after a slow frame, and no catch-up burst. Verified 2026-10-07.

## Skinned Mesh LODs

`Scene::AddModel` generates index-only skinned LODs against the original vertex store. `Scene/MeshLod.h` converts each mesh section's positive bone influences into dense weights over a stable bone palette; numerical bone indices are never simplification attributes. PE caps the skinning palette at 16 attributes, so sections using more than 16 active bones, invalid weights/joints, or no positive influences retain only LOD0. The palette limit is per section, not per skeleton. Static mesh simplification is unchanged.

Skinned simplification targets 50%, 25% and 12% of the original indices with a 0.01 combined position/skin-attribute error limit; the error limit can stop reduction early. Bone-weight attribute importance is 0.1. Original positions, normals, UVs, bone indices and weights are retained. This is not a bound on animated screen-space error, so skinned meshes default to `lod_enabled=false` and individual validated prefabs must opt in. Geometry-sharing prefab instances reset to the same default before applying their authored LOD fields.

Both main and shadow GPU culling already select the generated index ranges. Scene serialization now preserves `shadow_lod_bias`, with 1.0 as the fallback for older scenes, allowing a scene to choose coarser shadow geometry independently. No animation cadence, gameplay timing, or shader skinning algorithm changes are required. Index-only LODs reduce submitted geometry but retain the original vertex buffers in memory.

## LOD Selection Distance

`CullingCS` and `ShadowCullCS` pick a mesh's LOD from the camera's distance to the nearest point of its world AABB, not the AABB center (`lod_distances`, `lod_bias`, per-mesh `lod_bias`/`lod_shift` unchanged). With the center, a big flat mesh dropped to a coarse LOD while the camera stood over it: AgainstTheHero's 64 m arena floor (a 32-slice cylinder) switched to LOD1 whenever the hero neared its rim, and the simplified disc's chorded edge and twisted side wall read as dark holes in the ground. Small props switch at almost the same distance as before; on the ATH native arena the A/B was within noise (old 1008 fps / 0.992 ms median, new 1036 / 0.965). Verified 2026-09-28. `CullingPass` and `CullPhase1Pass` load `Path::RuntimeAssets + "Shaders/Compute/CullingCS.hlsl"` directly ([CullingPass.cpp](../../../Phasma/Runtime/Code/RenderPasses/CullingPass.cpp), [CullPhase1Pass.cpp](../../../Phasma/Runtime/Code/RenderPasses/CullPhase1Pass.cpp)), so a project's own copy does not replace it in loose-file desktop runs; only passes that load through `Path::ResolveAsset` take a project copy (see [Storage Image Formats](#storage-image-formats); corrected 2026-09-30).

## Material Rebuilds

Material-table rebuilds resolve each pass layout by its loaded `PassInfoAsset` identity within the rebuild, avoiding a resource-ID string allocation and string hash per mesh. Shader source checks still run: `ShaderCache::ParseShader` recognizes the existing quoted-include grammar directly rather than invoking a regex on every source line. Recursive expansion and content-based cache invalidation remain unchanged; 64 runtime HLSL sources produce byte-identical expanded text. These reduce rebuild overhead but do not make new instance creation incremental. Pooled ATH respawns avoid creation/rebuild work by reusing valid parked rigs.

## Joint Palette Uploads

`Scene::UpdateUniformData` writes root-corrected joint palettes directly into the current frame's mapped storage buffer, removing the full intermediate matrix array and its second copy. Node data and skinned bounds retain their batched copies. Missing poses still upload identity matrices, and each palette range is checked against the buffer size.

Each dirty skinned node is one job (`SkinJob`): it rolls its own shown pose into the previous one (a swap, not a copy), writes both palettes and re-dirties a moving pose. At least 128 jobs run through `ThreadPool::ParallelFor` (the caller plus up to seven Update-pool workers, 64 jobs each at least); smaller batches stay serial. Workers capture a span of the caller's jobs and touch only their own node and byte range. The recycled frame's fence precedes these writes, and all jobs join before submission or error propagation. DX12 retains its existing upload-to-device-buffer copy. `Joint Palette Preparation` isolates the parallel work inside `Update Uniforms`.

The palette is bound by bytes written, not by matrix math: the storage buffer is `CPU_TO_GPU_PERSISTENT_DEVICE` (ReBAR), and a probe that skipped two thirds of the writes on the 1,000-enemy ATH fill cut the scope from 0.63 to 0.24 ms at equal load, while more chunks changed nothing (2026-10-04). Bytes written are the lever: a rig whose parts sit on separate mesh nodes uploads one palette per part, all copies of one pose (`Animation.ReusedPoses` vs `UniquePoses`). Put a skinned rig's parts on one node with `mesh_refs` instead: every mesh of a node reads the node's palette (`meshDataOffset`), so the node gets one pose, one palette and one bounds pass. Script `setColor` tints only a node's first mesh ref, so list the part that flashes first. ATH's creeps moved from 3 part nodes under an identity `_Visual` node to one node on the root (2026-10-04): reused poses ~2,000 to ~130, palette 0.60 to 0.24 ms, frame 4.65 to 2.82 ms on the 1,000-enemy fill.

`SceneSettings::cull_offscreen_animation` (off by default; `settings.set` / native `SetSetting`) skips skinned rigs outside the camera: `AnimationSystem::Update` tests each playing state's node against the active camera's frustum, using last frame's world bounds widened by 2 m (`kOffscreenMargin`). A culled state still advances its clocks, blends and root motion, but is not posed (`state.posed = false`, so a fade started meanwhile evaluates its own start). It also gets no palette upload (`UpdateUniformData` skips `viewCulled` nodes), and its `renderVisible` goes to 0, so `CullingCS` and `ShadowCullCS` skip its draws, shadows included. That suits a top-down game, where nothing off screen casts into view. `NodeRuntime::hidden` keeps the script's `SetNodeRenderVisible` choice apart from the cull. An idle pose that was culled falls through once, to be posed and shown. A rig spawned straight into view can miss one frame, since its bounds are still last frame's. AgainstTheHero turns it on at match boot. On its 1,000-enemy fill, unique poses fell from ~958 to 363-487, pose evaluation from 0.33 to 0.21-0.24 ms, and the palette from 0.24 to 0.11-0.14 ms (2026-10-04). The frame time of that run is not comparable: another game shared the GPU.

World bounds of skinned meshes (`SkinnedBounds::Pose`) skip joints with no vertices in the mesh (`used`, filled by `Build`), and posed skinned meshes no longer compute the discarded rest-pose `TransformAabb`. `UpdateNodeMatrix` queues each posed skinned mesh and `UpdateNodeMatrices` poses the queue through `ParallelFor` after the serial walk (`Build` stays serial there, since the joint boxes are shared by mesh instances), then folds the results in walk order. `Skeleton::InverseRootTransform` caches the inverse root on the main thread. On the 1,000-enemy fill, `Update Node Matrices` went 0.76 to 0.62 ms (joint skip) to 0.38 ms (parallel). The per-frame selection-flag pass returns early when no node is selected and nothing was flagged last frame (`SceneRuntimeHooks` `hasSelection`; a host without the hook keeps the full pass): 6.40 to 6.05 ms frame in that fill.

A controlled Release Vulkan test with 1,024 independently clocked ATH instances reduced uniform CPU time from 0.696 to 0.490 ms; DX12 reduced it from 0.660 to 0.471 ms. Total frame time stayed approximately 3.3 ms because that fixture was GPU-bound. A live 2,048-enemy sample reduced the same scope from 1.713 to 1.059 ms, but changing combat activity prevented a reliable overall frame-time improvement claim. CPU checks compare serial and parallel matrix bytes, fallback poses and guard ranges across batch boundaries; Vulkan validation and DX12 debug-layer crowd runs also cover the mapped-buffer path.

## Skinned Indirect Instancing

`SceneSettings::skinned_instancing` groups visible skinned meshes that share an exact index range, vertex offset and raster bucket. Grouping runs inside the existing GPU culling wave after visibility and LOD selection, including both Hi-Z phases and each shadow cascade. Each instance still resolves its own mesh constants, transform, joints and material. Main-pass transparent and transmission draws keep their individual sorted commands; selection also keeps the original individual command.

Both Vulkan and DX12 use the `PE_DRAW_ID` vertex semantic as a four-byte per-instance stream at vertex binding 1. That binding is reserved when the semantic is present. Every pass whose vertex shader takes `VS_INPUT_Depth` or `VS_INPUT_Gbuffer` must call `Scene::BindDrawIdBuffer` after binding vertices, even when the shader ignores the ID; [LinesPass.cpp](../../../Phasma/Runtime/Code/RenderPasses/LinesPass.cpp) (lines and sprite outlines) skipped it and Vulkan validation reported `VUID-vkCmdDrawIndexed-None-04007` (fixed and verified in VoxelCraft play mode 2026-10-12). A frame-local ID buffer contains an identity prefix for ordinary draws and separate remapping segments for frustum, Hi-Z A, Hi-Z B and shadow output. Shadow cascades reuse their segment only after the preceding draw finishes reading it. Buffer growth, deferred uploads and compute-to-vertex barriers follow the existing scene buffer lifecycle.

The option is off by default and can be enabled through Scene Settings or `settings.set("skinned_instancing", true)`. Scene serialization and profiler capture metadata preserve its value. Profile the target scene before enabling it: batching reduces indirect command count, but does not reduce animation evaluation, vertex skinning or pixel work. Batches stop at wave boundaries; no extra global sorting dispatch is added. Local Vulkan and DX12 compute checks reduced 1,024 identical instances to 32 commands and verified mixed geometry, LOD keys, visibility, excluded draws and partial waves. That command-count result is not an FPS claim.

A clean Release comparison on an RTX 4080 SUPER with 1,024 ATH skinned instances at 2560x1369 found essentially unchanged GPU time: Vulkan 3.224 ms off / 3.221 ms on, DX12 3.174 ms off / 3.180 ms on. Poses and gameplay were frozen to hold the render workload constant; independent animated poses were checked separately. Hi-Z comparisons also stayed within 0.5% GPU time. These measurements justify retaining the opt-in default rather than claiming a crowd-performance improvement from command reduction alone.

Visual validation remains separate from those timing checks: the September 10 DX12 ATH crowd captures show black speckling on meshes with instancing both disabled and enabled. It also reproduces with the binary preserved before the LuaJIT/parallel-pose/material-packing changes; Vulkan captures do not show it. Cause (found 2026-09-29): the G-buffer depth-tests EQUAL against the depth prepass (`standard_pbr.pass`), and `GBufferVS` computed the clip position as `p*(J*(M*VP))` while `DepthVS` used `p*((J*M)*VP)`. With a bone transform the two round apart, so skinned pixels failed the test in speckles and kept the cleared G-buffer (static meshes, J = identity, matched exactly). Fix: `GBufferVS` uses DepthVS's order and both clip positions are `precise`; pool test `depth-equal-positions` guards it. Any shader that writes depth compared EQUAL with the prepass must repeat DepthVS's maths exactly. Projects that ship copies of these shaders (materials resolve project-first) must resync them.

Standalone Quality scales the display target as well as scene targets. `CreateFSSampledImage(source)` takes its size and format from the actual source: HDR for DOF/MotionBlur/SSR, display format for ColorGrading/FXAA and editor/animator previews. This also follows the host's output policy; copying a scaled display into a native-size scratch image previously failed image-copy validation. Tone mapping samples HDR directly without a copy. Vulkan and DX12 smoke checks cover live scale transitions with post-processing enabled; image-copy size validation remains intact. Verified 2026-10-07.

## Forward+ Light Culling

Raster lighting uses `ForwardPlusLightCullingPass` before the opaque and transparent light passes when `SceneSettings::forward_plus` is enabled. The compute pass bins point and spot lights into 16x16 screen-space tiles, writing per-tile counts and compact index lists that `LightingPS.hlsl` consumes instead of looping over every local light for every pixel. Directional and area lights remain on the existing full-list paths.

The culler intentionally uses a conservative projected sphere overlap for each local light. If a tile reaches `FORWARD_PLUS_MAX_LIGHTS_PER_TILE`, the tile records an overflow bit and the pixel shader falls back to the original full point or spot loop for that light class. This preserves correctness for extreme scenes while keeping common scenes on the cheaper tiled path.

Forward+ resources are descriptor-sensitive: scene render descriptor refresh must update the culling pass before `LightPass`, because the lighting descriptor set binds the cull buffers as extra read-only resources. When the global option is disabled or the raster path is inactive, `LightPass` binds small fallback storage buffers and the shader uses the original full point/spot loops. The pass also records explicit buffer barriers between compute writes and lighting reads on both Vulkan and DX12.

The light storage buffer is replaced, not resized. `Scene::UpdateLights` destroys a frame's `lights_storage_buffer` and creates one twice as large when the enabled lights outgrow it; it starts at 1 KB, roughly 16-20 point lights. Every pass that binds it must rebind when `Scene::GetLightStorage(frame)` changes:
- `ForwardPlusLightCullingPass` already did.
- `LightOpaquePass`, `LightTransparentPass` and `RayTracingPass` did not, and kept the destroyed buffer in their sets until something else (an SSAO target, shadows, Forward+) forced a refresh. They now remember the bound buffer per frame (`m_boundLightStorage`) and rebind when it moves (2026-10-04).

Vulkan tolerated the stale binding. DX12 hung the GPU (`DEVICE_HUNG`) in the opaque lighting draw right after the Forward+ cull. AgainstTheHero's 1,000-enemy fill, whose Blast Buds each carry an ember point light, hit it within seconds with shadows on. Toggling shadows off refreshed the sets, which hid it.

DX12 debug regions now also emit D3D12 `BeginEvent`/`EndEvent`, so PIX shows pass names and DRED breadcrumbs (`PE_DX12_DRED=1`) show where each pass begins and ends. DRED did not return the event strings themselves (no breadcrumb contexts), so the failing pass is read from the event structure.

`ParticleManager::LoadTexture` refuses a 17th particle texture. `ParticlePS` binds `textures[16]` with the scene depth at binding 16, so a 17th would index past the table on DX12, and its descriptor write would overwrite the depth.

## Present Mode And Framebuffer Cache

Present-mode changes must be treated as resize work, not as an immediate mid-frame swapchain teardown. Editor/runtime requests should update the desired surface present mode, sync the stored preference to the effective supported mode, wait for idle, and queue `EventType::Resize` so swapchain, scene render targets, render-pass components, and frame resources rebuild together. Host window titles should be refreshed after the deferred swapchain recreation and after the active project binds. They should report "Phasma Editor", GPU, API, the recreated swapchain's actual present mode, the build configuration, and the active project folder. Other desktop hosts use the same spaced product name in the window title (`Phasma Player`, `Phasma Animator`, `Phasma Profiler`, `Phasma Cook`, `Phasma Engine`, `Phasma WebGPU`).

FIFO presentation is paced independently from reusable command-buffer fences. `Present()` only queues presentation so worker submissions and secondary ImGui windows are not held behind the display wait. At the start of the next frame, Vulkan prefers optional per-surface `VK_KHR_present_id2` + `VK_KHR_present_wait2` support and falls back to `VK_KHR_present_id` + `VK_KHR_present_wait` when wait2 is unavailable; either extension path works without raising the engine's Vulkan 1.2 minimum. DX12 waits on a `DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT` swapchain limited to one queued frame. Both waits use a bounded timeout so the host can pump window events and retry the same presentation instead of hanging while a display is locked or off; PhasmaWebGPU performs the same gate during `wgpuSurfaceGetCurrentTexture` and reports native `Timeout` or `Outdated` acquisition status. Immediate/tearing mode skips these waits. Vulkan completion means that the request reached or was replaced within the presentation engine; it is not a precise user-visible scanout timestamp.

Vulkan paces against the previous successful presentation ID, allowing one newer present while the next frame is prepared. Waiting for the newest present instead serialized CPU/GPU work with display refresh: the September 10 live 1,024-enemy ATH reproduction measured about 28 FPS in FIFO versus 89 FPS in Immediate. The bounded overlap restored FIFO to about 58–60 FPS; a normal Player launch without the profiler reported a 59.8 FPS median over 36 one-second log samples. This allows one additional queued frame of latency; command-buffer reuse fences, image acquisition and semaphore ownership are unchanged. Only non-error presents advance the successful-ID history, and swapchain recreation starts it empty. The 115 FPS earlier crowd result was a short uncapped capture, not a FIFO guarantee or a sustained dense-combat rate.

Editor and player swapchain recreation must destroy and recreate scene frame commands and acquire/submit semaphores around the swapchain so their arrays match the new image count. Present-mode requests from live UI or scripts are deferred through the host resize path; startup and WebGPU configuration may still use the lower-level immediate RHI operation before host frame resources exist.

Every successful swapchain creation also rebuilds the RHI deletion-queue array to the new swapchain image count. Recreating only the swapchain images while retaining the old queue count lets the new frame index address past the queue array during later scene/resource destruction; Android surface loss and resume is a common trigger because its swapchain image count can change.

Pitfall, a window with no drawable area (verified 2026-10-15): while the window is minimized Vulkan reports `currentExtent` and `maxImageExtent` as 0x0, so no swapchain size is legal, not even 1x1. A plain `ShowWindow(SW_MINIMIZE)` on the running Vulkan editor was enough to log `VUID-VkSwapchainCreateInfoKHR-imageExtent-01689`, fail the first 0x0 render target (`VulkanImageImpl`, `vmaCreateImage` -3) and exit with "Unhandled exception in editor host"; the DX12 build survived the same steps because [Dx12SwapchainImpl](../../../Phasma/Core/Code/API/DX12/Dx12SwapchainImpl.cpp) sizes from the extent it is given. SDL's `SDL_WINDOW_MINIMIZED` cannot be the guard: it changes only when the host next pumps events, and Win+D leaves it clear (observed 2026-07-25, commit `380e2379`). [Surface::IsPresentable](../../../Phasma/Core/Code/API/Surface.h) is the one predicate (Vulkan: non-zero `currentExtent`; DX12: not iconic and a non-empty client rect). The editor's `Window::IsRenderable` (SDL flag and surface) gates `App::Frame`, asked before the presentation wait and again after the event pump, and defers `EventType::Resize` until it is true; `PlayerHost` and `AnimatorApp` use the same test in their `WindowRenderable`. As the last line, [RHI::CreateSwapchain](../../../Phasma/Core/Code/API/RHI.cpp) waits for it (pumping events, one `[Swapchain]` warning), which covers a start-up with a minimized window and a resize that races the OS between its check and the creation. A DX12 frame that waited on the frame-latency object and then drew nothing keeps its slot (`Dx12SwapchainImpl::m_frameWaited`, cleared by `Present`): without it the next wait blocked forever once SDL's flag was clear while the window was minimized, because only a `Present` returns the slot. Cook's hidden window still reports a drawable extent, so its swapchain is created without waiting. Pool tests `editor-minimize-vulkan` and `editor-minimize-dx12` minimize, hide, spoof-restore (a posted `WM_SIZE` clears SDL's flag while the OS has the window minimized, as Win+D does) and burst the harness editor's own window with render-scale changes; the pre-fix Vulkan build fails them at the first minimize.

Cached framebuffers are keyed by the actual attachment `ImageView` objects captured in the backend framebuffer. Implicit render-target views must be created before cache lookup so an RTV recreation cannot reuse a framebuffer that still holds a destroyed Vulkan image view or DX12 descriptor.
Code outside PhasmaCore must clear this cache through `CommandBuffer::ClearFramebufferCache()`, not by accessing the inline static map from a header. A DLL/executable boundary can otherwise produce a separate inline-variable instance, leaving PhasmaCore's real cached framebuffer alive after its attachment view is destroyed.

DX12 scaled image blits use the shader path rather than `CopyTextureRegion`. [Dx12Blit.cpp](../../../Phasma/Core/Code/API/DX12/Dx12Blit.cpp) sets a positive-height viewport over the destination rectangle and passes the source rectangle as a positive UV scale and offset; [Dx12Blit.hlsl](../../../Phasma/Core/Code/API/DX12/Dx12Blit.hlsl)'s fullscreen triangle maps clip-space bottom to v = 1, so source and destination stay top-to-top like Vulkan's image blit. Scene geometry flips clip-space Y separately in `Structures.hlsl` under `PE_DX12`. Verified 2026-10-07.

## Camera Aspect

The camera projection's aspect must be the presented frame's, which is the RHI size. In Free mode the editor reads its display target (`EditorCameraAspect` in [App.cpp](../../../Phasma/Editor/Code/App/App.cpp)), which it keeps at full size, so that equals the RHI size. The Player's `RuntimeSceneRenderer` renders its display target at `render_scale` (`CreateRenderTargets(..., scaleOutput)`). Scaled sizes are truncated: with a 2560x1369 window and scale 0.5, the target is 1280x684 because 684.5 is truncated. Before 2026-10-19, `DefaultCameraAspect` in [Camera.cpp](../../../Phasma/Runtime/Code/Camera/Camera.cpp) read that scaled target. The Player's projection then used 1.87135 against the editor's 1.86998, so the presented frame was stretched vertically by 0.07%. On direct-present frames the Player was inconsistent with itself too: the shadow cascade fit, which reads the display target during recording, saw the full-size swapchain image. `DefaultCameraAspect` now returns `RHII.GetWidthf() / RHII.GetHeightf()`. Measured with the combined Phase 4 gate (`openpbr_phase4_combined.py`, `func-r14` to `func-r16`):
- before the fix, the exported Player differed from the editor by up to 170/255 over 7,114 pixels, on horizontal edges only;
- after it, both hosts report aspect 1.8699781 and the Player matches the editor within 1/255 on Vulkan and DX12.

The shadow cascade fit ([ShadowPass.cpp](../../../Phasma/Runtime/Code/RenderPasses/ShadowPass.cpp)) still takes its aspect from the display target, not the camera. On the Player's frames that don't present directly (screenshots, overlays) it therefore sees 1280x684 while the camera uses the RHI size. The proper choke-point fix is for the fit to use the camera's own aspect; that is not done. The editor's non-Free `scene_view_aspect_mode` values were not checked either. The Player tests in the pool that compare frames (`slang-ath-*`, `particle-emitter-spawn-sphere`) compare statistics, not stored pixels.

## Downsampler Storage Formats

[Downsampler](../../../Phasma/Core/Code/API/Downsampler/Downsampler.cpp) selects an embedded Vulkan shader matching the input view: `Rgba8` for RGBA8 UNORM, `Rg16f` for RG16F, `Rgba16f` for RGBA16F, and `Rgba32f` for HDR RGBA32F. Both the mip array and mip-6 storage image use that format. The previous single `Rgba32f` module bound to RGBA8 views produced undefined image values. Unsupported Vulkan storage formats fail explicitly; DX12 retains one DXIL shader whose typed UAV follows its view format. These variants add no storage-image read/write-without-format requirement. The RG16F variant does declare `StorageImageExtendedFormats`, requiring `shaderStorageImageExtendedFormats`; [Vulkan device creation](../../../Phasma/Core/Code/API/RHI.cpp) enables advertised core features. Regenerate the embedded modules with [generate_downsampler_shaders.py](../../../tools/generate_downsampler_shaders.py) and an explicit DXC path; the generated header records the compiler version (verified 2026-09-30).

Direct bytecode shaders must initialize their [ShaderCache](../../../Phasma/Core/Code/API/ShaderCache.cpp) identity from bytecode, entry point and stage. [PassInfo::UpdateHash](../../../Phasma/Core/Code/API/Pipeline.cpp) uses that identity for pipeline reuse. Leaving it zero made the format variants reuse the first RGBA8 pipeline even when their shader modules contained the correct formats. A desktop core-validation/GPU-AV check dispatched all four formats with eight mips and reported no storage-format mismatch after both fixes (verified 2026-09-30).

The retained DXIL path was verified with a Release Sponza smoke on DX12/display 1 and the D3D12 debug layer: the embedded downsampler initialized, scene rendering was visually checked, and no debug-layer error or device loss was reported. This smoke validates the rebuilt bytecode path, not performance or Android stability (verified 2026-09-30).

VVL 1.4.363.0 contains the same-invocation race-report fix from [PR 12418](https://github.com/KhronosGroup/Vulkan-ValidationLayers/pull/12418), but still reports adjacent-invocation races in SPD. The observed `spdIntermediateA` load/store pair maps to the wave-based `SpdDownsampleMip_2` path in [ffx_spd.h](../../../Phasma/Core/Code/API/Downsampler/Shaders/ffx_spd.h): shared reads, subgroup shuffles, then an in-place quad-leader store. No same-invocation reports appeared in the newer-layer run. This confirms that upgrading alone does not clear the warnings; it does not settle whether subgroup-dependent accesses are a real hazard or a remaining instrumentation limitation. No speculative barrier was added (verified 2026-09-30). A diagnostic build with `SPD_NO_WAVE_OPERATIONS` removed every report (four-format downsample check and a 180 s ATH Map 1 run: 10 to 0 each), and every report maps to the wave load, subgroup shuffle and in-place quad-leader store in `SpdDownsampleMip_2`/`SpdDownsampleMip_3`. The layer's shared-memory race instrumentation does not model `OpGroupNonUniformShuffle`, so a detector limitation is the likelier explanation; shuffles are not memory barriers, though, and settling it needs an upstream VVL reproducer and a memory-model ruling. The diagnostic change was not kept (verified 2026-09-30).

## Storage Image Formats

Contract: every Vulkan storage image declares the format of the view its pass binds. [SceneRenderTargets.cpp](../../../Phasma/Runtime/Code/Render/SceneRenderTargets.cpp) creates viewport and emissive as R8G8B8A8_UNORM by default, or R16G16B16A16_SFLOAT when `SceneUsesHDR()` is true; a separate `hdrDisplay` exists only in HDR. TAA history and bloom follow the active scene format. Display, screenshot, albedo and srm remain R8G8B8A8_UNORM, independent of the swapchain; full-screen copies derive their format and dimensions from their source. `BlitSceneImageToSwapchain` converts to the swapchain (`vkCmdBlitImage` converts; DX12's blit cannot, but the DX12 swapchain is always R8G8B8A8). Vulkan `CopyImage` does not convert, so each source/destination pair must match. Direct present hands the swapchain image to passes built for the display format, so [RuntimeSceneRenderer](../../../Phasma/Runtime/Code/Render/RuntimeSceneRenderer.cpp) uses it only when the formats match; a B8G8R8A8 desktop surface falls back to the blit. Frames with a pending screenshot also skip direct present and copy the offscreen display: copying the swapchain after its PRESENT barrier left it in COPY_SOURCE at Present (D3D12 debug-layer error 538), and a Vulkan swapchain only has TRANSFER_SRC when the surface supports it (screenshot guard verified 2026-09-30; HDR formats verified 2026-10-07).

Shaders declare formats with `[[vk::image_format]]`: `rgba16f` for TAA `out_color` and RayTrace `output` with `HDR_SCENE`, otherwise `rgba8`; RCAS `out_color` always uses `rgba8`; `r16f` for SSAO `RawAO`/`FilterInput` and blur `FilterOutput`, `r8` for the upsample `FilterOutput` (`SSAO_UPSAMPLE_PASS`). Undeclared `float4`/`float` images compile to `Rgba32f`/`R32f`; that matched the RGBA32F cubemaps and R32F depth pyramid and `rtDepth`, but not these views, and VVL 1.4.363.0 reported `Undefined-Value-StorageImage-FormatMismatch-ImageView` for TAA, RCAS and SSAO. `r16f`/`r8` add `StorageImageExtendedFormats`, like the downsampler's RG16F variant. DX12 typed UAVs follow the view format. These passes load `Path::RuntimeAssets + "Shaders/..."`, not `Path::ResolveAsset`: in loose-file desktop runs `[Shader] Compile(hlsl) -> source=` names the build tree's `RuntimeAssets`, so a project `Assets/Shaders` copy does not replace them there (a game pack maps these paths to its `RuntimeAssets/` entries, [GamePack.cpp](../../../Phasma/Core/Code/Base/GamePack.cpp) `ToPackPath`; HDR declarations verified 2026-10-07).

## Vulkan Descriptor Heaps

Vulkan 1.4 devices automatically use `VK_EXT_descriptor_heap` when the extension, `descriptorHeap` and buffer device addresses are present. `VK_KHR_shader_untyped_pointers` is not required: the registry lists only maintenance5 and buffer device addresses as dependencies, and untyped pointers matter only to SPIR-V that addresses heaps directly, while the engine's shaders go through binding mappings (SDK 1.4.350 `vk.xml` and `validusage.json`, checked 2026-10-18). Extension declarations come from the bundled Vulkan headers; support is determined at runtime through device extension enumeration and feature queries, without extension-name preprocessor guards or an environment override. Earlier API versions and unsupported devices keep descriptor sets. The engine's Vulkan 1.2 minimum is unchanged. Device selection and feature enablement live in [VulkanRhiImpl.cpp](../../../Phasma/Core/Code/API/Vulkan/VulkanRhiImpl.cpp) and [RHI.cpp](../../../Phasma/Core/Code/API/RHI.cpp). Verified 2026-10-18.

[VulkanDescriptorHeap.cpp](../../../Phasma/Core/Code/API/Vulkan/VulkanDescriptorHeap.cpp) owns stable, persistently mapped resource and sampler heaps, including the implementation-reserved ranges. Freed descriptor ranges coalesce and sampler objects own reusable sampler slots. Resource heaps are capped at 32 MiB and sampler heaps at 128 KiB, each further limited by device properties. Heap writes require coherent host memory. Heap buffers also carry uniform usage, because indirect-index mappings read per-set index tables from the heap through a pushed address and `VUID-vkCmdDraw-None-11437` requires that address to come from a uniform buffer. The bit is added in [VulkanBufferImpl.cpp](../../../Phasma/Core/Code/API/Vulkan/VulkanBufferImpl.cpp)'s Vulkan usage translation: `Buffer` rejects engine uniform buffers larger than `maxUniformBufferRange` (64 KiB on the RTX 4080 SUPER). Standard validation never reported the missing bit, so this is a conformance fix checked against SDK 1.4.350 `validusage.json` (2026-10-18). [VulkanHeapDescriptor.cpp](../../../Phasma/Core/Code/API/Vulkan/VulkanHeapDescriptor.cpp) handles buffer ranges, image views, combined image/sampler arrays and acceleration structures. Each binding's resource and sampler counts are checked against its capacity before writing (verified 2026-10-18; local pool test `vulkan-descriptor-heap-bounds`). Storage-image updates can carry an unused null sampler from `SetImageView`; only sampler and combined-image-sampler bindings consume sampler entries. Only sampler and combined-image-sampler bindings get index tables; the other bindings use push indices and reserve none. Sampler tables start zeroed (sampler slot 0); a sampler-only binding's single table must not receive resource-heap offsets, which lie past the 128 KiB sampler heap. A null view, buffer or acceleration structure leaves an empty (zeroed) descriptor and a null sampler uses slot 0, matching the descriptor-set path, which writes `VK_NULL_HANDLE`; neither is valid without `nullDescriptor`, which the engine does not enable. Verified 2026-10-18 by local pool test `vulkan-descriptor-heap-null-parity`: the build before this change threw `Descriptor heap image binding is null` from `Descriptor::Update`.

Existing SPIR-V and the public descriptor API remain shared. [VulkanPipelineImpl.cpp](../../../Phasma/Core/Code/API/Vulkan/VulkanPipelineImpl.cpp) supplies binding mappings for graphics, compute and ray tracing. Buffer and separate-image bindings use direct push indices; sampler and combined-image-sampler arrays use per-set index tables so different elements can share sampler slots. Push data bytes 0–127 hold shader constants, followed by per-set table addresses and resource offsets. Layouts with unsupported binding types, push descriptors or too many sets for `maxPushDataSize` use native descriptor-set pipelines.

Native clients, including ImGui and PhasmaWebGPU, can still request descriptor sets: [VulkanDescriptorImpl.cpp](../../../Phasma/Core/Code/API/Vulkan/VulkanDescriptorImpl.cpp) materializes them on demand and updates them thereafter. [Descriptor.cpp](../../../Phasma/Core/Code/API/Descriptor.cpp) merges partial array updates into its resource snapshot, preserving untouched elements for delayed native replay. Omitted buffer offsets and ranges reset only the updated prefix to their defaults. Verified 2026-10-18 by local pool test `vulkan-descriptor-native-replay`, which executes the current snapshot and native replay methods with mocked Vulkan calls. [VulkanCommandBufferImpl.cpp](../../../Phasma/Core/Code/API/Vulkan/VulkanCommandBufferImpl.cpp) rebinds both heaps and the set data before engine descriptor use, since native descriptor commands invalidate heap state. Push data has no bind point, unlike descriptor sets and push constants (VUID-vkCmdDraw-None-08600/08601) and D3D12's separate graphics and compute root arguments, so the command buffer keeps each bind point's (graphics, compute, ray tracing) last set data and push constants as plain bytes. `BindDescriptors`, `PushConstants` and `BindPipeline(..., false)` on a heap pipeline re-push that bind point's state when another bind point, or nothing known, last wrote the push data. `BeginPass`, `EndPass` and native descriptor commands mark it unknown, because raw Vulkan recorded around passes (ImGui) and native sets invalidate heap state. Verified 2026-10-18 by local pool test `vulkan-descriptor-heap-bind-points` (graphics bind, compute bind and dispatch, `cmd:bind_pipeline(gfx, false)`, draw): before the change heaps drew cyan, the compute pass's green buffer and blue constant, where descriptor sets drew red; after it both draw red. ## Scene Texture Table

Scene textures live in one unbounded `Texture2D pe_textures[]` (`register(t0, space100)` on D3D12). A set whose only binding is that array is replaced in `PassInfo::ReflectDescriptors` ([Pipeline.cpp](../../../Phasma/Core/Code/API/Pipeline.cpp)) by `RHI::GetTextureTable(frame)`, one RHI-owned descriptor per frame in flight ([RHI.cpp](../../../Phasma/Core/Code/API/RHI.cpp)); `Descriptor::Destroy` leaves these shared tables alone and `RHI::Destroy` frees them after the deletion queues flush, because retired PassInfos still name them. Depth, DepthLate, GBuffer, ObjectId, VisibilityDebug and MaterialShade declare it as set 2 binding 0, MaterialMask and MaterialThin as set 1 binding 0, and none of them writes scene textures any more: `Scene::UpdateImageViews` ([SceneBuffers.cpp](../../../Phasma/Runtime/Code/Scene/SceneBuffers.cpp)) writes every frame's table. Ray tracing (set 0 binding 12; plain RT uses sets 0-1 and its GI variants set 2, so set 3 would leave a gap) mixes the array with other bindings, so each of its descriptors keeps its own copy and `RayTracingPass` still calls `SetImageViews`, rewriting its whole set 0 on every geometry change. MaterialShade did the same until 2026-10-18: its pipeline uses the four descriptor sets Vulkan guarantees (`maxBoundDescriptorSets` is 4 on many Android GPUs and in `VP_ANDROID_vulkan_profile_2025`), so the array shared set 2 with the skybox cube, the environment and the graph samplers, and every textured graph rewrote its own full copy every frame. Those bindings now sit in set 3 above ProbeVolume's (see the OpenPBR Bindings note); LightingPS keeps the cube in its set 2 and MaterialShade declares its own fog cube. Graphs that sample no texture strip `pe_textures` and leave set 2 empty below set 3: reflection returns null there, Vulkan compute pipelines get an empty set layout for it (graphics already did, [VulkanPipelineImpl.cpp](../../../Phasma/Core/Code/API/Vulkan/VulkanPipelineImpl.cpp)), and D3D12 skips null sets when binding ([Dx12CommandBufferImpl.cpp](../../../Phasma/Core/Code/API/DX12/Dx12CommandBufferImpl.cpp) `BindDescriptorTables`, which raised `PE_ERROR` before). On D3D12 the shared root signature gains one unbounded SRV range in space 100 (`DX12_TEXTURE_TABLE_ROOT_INDEX`, 42 DWORDs in all), bound from whichever descriptor carries space 100; reflection accepts space 100 at register 0 whatever the Vulkan set and binding.

Reflection marks unbounded image arrays `bindless` (variable descriptor count, last binding of their set) and declares them at `caps.maxBindlessTextures`; an unbounded array that is not a `Texture2D pe_textures[]` is an error. Only those arrays grow; a bindless array built by hand (the Lua descriptor API) keeps its declared size. Vulkan derives that limit from the descriptor-indexing limits (the update-after-bind ones when the device supports update-after-bind), keeps a quarter of a small limit (at most 256) for other images, and clamps it to 2^20: 1,048,320 on the RTX 4080 SUPER and the Intel UHD 770, 96 under the `VP_LUNARG_desktop_baseline_2024` limits (128 sampled images per stage). D3D12 requires resource binding tier 3 and uses the 1,000,000-entry shader-visible heap minus 65,536 for everything else: 934,464. Arrays start at 256 entries and grow together ([Descriptor.cpp](../../../Phasma/Core/Code/API/Descriptor.cpp) `ResizeBindless`): `RHI::ReserveBindlessTextures` asks for the next power of two, then the exact count, only while twice the new size of every bindless array fits `caps.bindlessBudget` (three quarters of the Vulkan resource heap in sampled-image descriptors, three quarters of `maxUpdateAfterBindDescriptorsInAllPools` for update-after-bind descriptor sets, the D3D12 limit above), since a resize keeps the old copies until their frames retire. `SetVariableCount` builds the new pool and backend, retires the old ones through the deletion queue and leaves the new descriptor empty: its records may name resources freed since they were written (a cleared scene's views, the buffers of a disabled ray-tracing pass), and the native descriptor-set path replays records as it allocates. Every owner rewrites after a resize, which only `Scene::UpdateImageViews` requests before it bumps the geometry version. Growth has no rollback: arrays that grew before a failure keep their size, and the scene table is capped at `RHI::GetBindlessTextureCapacity`, the size every array still holds. Backends throw without logging when a range does not fit (`VulkanDescriptorHeap::TryAllocate`, `Dx12DescriptorHeap::TryAllocateRange`) so a failed growth keeps the previous table; a new descriptor that does not fit still fails with `PE_ERROR`. Past the table's capacity `BuildImageViewTable` rebuilds with the white view first and every later view sharing index 0, logs `[Scene] N textures exceed the C-entry texture table`, and `m_imageViewIndices` gives `TryBindCachedTexture` and `BuildOpenPBRBytes` the same index for each view.

## GPU Object Lifetimes

Local pool tests `gpu-object-lifetimes` (Vulkan), `gpu-object-lifetimes-dx12` and `gpu-object-retention` run `.testpool/tests/gpu_object_lifetimes.py`: two churn cycles (300 then 600 uniquely textured cubes; raster, hybrid and ray-traced modes; OpenPBR, GI, shadows; a render-scale resize; `scene.clear()` and the startup settings restored), then `engine.quit()`. Every live GPU image and buffer is listed through the editor MCP (`Image::GetHandles` / `Buffer::GetHandles`; `PE_TRACK_RESOURCES` is always defined in [Core/CMakeLists.txt](../../../Phasma/Core/CMakeLists.txt)) at startup and after each unload. Resources of a name that grow from one cycle to the next are a leak; resources alive after unload that startup did not have are GPU memory kept alive while unused, reported by name with an estimated size in `gpu_lifetimes_<api>.json`. Shutdown must exit 0 with no validation or debug-layer error; Vulkan's object tracker reports, at `vkDestroyDevice`, every object never destroyed (the device is destroyed before the debug messenger in [RHI.cpp](../../../Phasma/Core/Code/API/RHI.cpp)). The engine requests no D3D12 live-object report, so D3D12 leaks at exit are not detected; allocator-retained empty blocks and descriptor-heap capacity (the grow-only scene texture table) are not measured.

Measured 2026-10-18 (RTX 4080 SUPER, Release), before and after the release below: retention went from 198.1 MB kept alive after unload (Vulkan heaps 263 resources at startup and 316 after; D3D12 315 and 375) to none: Vulkan heaps 263 and 263, Vulkan descriptor sets 261 and 261, D3D12 315 and 315, each with no per-cycle growth and a clean shutdown. What had stayed alive was what a pass creates when first enabled: screen probes (`SP_*`, 15 MB each at render resolution), Lumen reflections (`LR_*`), the GI atlases (`GI_*`, RGBA32F, 8 MB each), `rtDepth`, `Tonemap_Resolved` (window size), RT uniforms and shader binding tables, and `MeshInfo_Buffer` kept at the size of the largest scene so far. Saved Sponza rendered the same in raster, hybrid, ray tracing and raster again after the modes (pixel-identical on both APIs; hybrid with GI differs in 0.03 to 0.04% of pixels, its accumulation), with no perf regression (`tools/compare_snapshots.py`, immediate present, 10 snapshots: Vulkan 1813 against 1870 fps, D3D12 2124 against 2263, GPU time unchanged), and `render_warnings.py` passed on both APIs.

Disabled passes give their GPU objects back. `InitEnabledSceneRenderGraphPassComponents` stamps every enabled pass with the RHI frame counter, and `ReleaseDisabledSceneRenderGraphPassComponents` ([SceneRenderGraph.cpp](../../../Phasma/Runtime/Code/Render/SceneRenderGraph.cpp), called from `SceneRendererCore::UpdateRenderGraphPassStates`) destroys an initialized pass that has not been enabled for `kSceneRenderGraphPassReleaseFrames` (30) frames and for more frames than are in flight, so every frame that recorded it has been waited for. The release retires the pass's cached pipelines through the deletion queue (`CommandBuffer::RetirePipelines`; ray-tracing pipelines own their shader binding tables), runs `Destroy()` with `RHI::SetDeferDestroy` on so each Image and Buffer it frees goes through the deletion queue, drops its shaders (shader reload then skips it, as it skips a pass never initialized) and clears the framebuffer cache, whose entries are keyed by attachment view pointers and are now always destroyed through the deletion queue. A released pass initializes again the next time it is enabled, as on first use: re-enabling costs a target allocation, descriptor reflection and pipeline creation. The 30 frames only keep a toggle that flickers for a frame or two from rebuilding the pass. `MeshInfo_Buffer` is retired with the TLAS ([SceneRayTracing.cpp](../../../Phasma/Runtime/Code/Scene/SceneRayTracing.cpp) `BuildTLASFromInstances`), so an empty scene keeps none.

The first attempt (5b9298a6) destroyed disabled passes after `WaitDeviceIdle`, and b291aa7e reverted it after intermittent device loss and alternating-frame flicker on render-mode toggles, so the GPU being done was not the problem; state that outlives a pass was:
- Depth, late depth and both G-buffer passes bind their geometry set only when the scene's geometry version changes, so a re-initialized pass drew with empty descriptors. Their `Destroy()` now resets the version.
- Consumers that rebind when a producer's pointer changes (the light and ray-tracing passes, screen probes, reflections, sharpening, the profiler's render-target previews) are fooled when a re-created resource lands at a freed address while another frame's descriptor set still names the old one. Deferred frees keep the old memory allocated through the frames in flight, and the profiler drops its preview cache whenever a scene target is destroyed (`GetSceneRenderTargetGeneration` in [SceneRenderTargets.cpp](../../../Phasma/Runtime/Code/Render/SceneRenderTargets.cpp)), freeing the dropped ImGui textures only once the frames in flight that may still draw them are done.
- TAA nulls its viewport pointer and zeroes its jitter on `Destroy()`: cameras call `TAAPass::GenerateJitter` and read the jitter from `Scene::Update`, before a re-enabled TAA initializes.
- Code outside the graph refreshes passes whether or not they are initialized (scene load and sky reload in [SceneRuntimeHooks.cpp](../../../Phasma/Runtime/Code/Scene/SceneRuntimeHooks.cpp), shadow and Forward+ edits in the editor's pipeline panel). `LightOpaquePass`, `LightTransparentPass` and `RayTracingPass::UpdateDescriptorSets` return while the pass has no uniforms.
- Lazy initialization passes no command buffer, so `ParticleManager::InitTextures` loads its default texture once per scene instead of on every particle-pass initialization.
- `RayTracingPass` and `SelectionOutlinePass` destroy their named targets (`rtDepth`, `selectionMask`); the GI, screen-probe and reflection passes derive from `RayTracingPass` but null `m_rtDepth`, so they leave it alone.

## Cached Pipelines

- `CommandBuffer::GetPipeline()` caches `Pipeline` objects globally from a `PassInfo` hash. Some callers, such as skybox HDR-to-cubemap conversion, build transient `PassInfo` instances and destroy them after the command buffer finishes.
- A cached `Pipeline` must treat the source `PassInfo` as construction-only state. Runtime command recording should use immutable metadata copied into `Pipeline` at creation time, such as pipeline type and push-constant ranges, instead of reading through the original `PassInfo` reference.
- Vulkan descriptor auto-binding must still run when rebinding resources for the same cached pipeline. Skipping descriptor binds just because the pipeline object is already current can leave stale descriptor sets in place for repeated transient passes.

## Shader Compilers: DXC And Slang

Runtime HLSL is compiled by DXC (default) or Slang. Pick Slang with `--shader-compiler slang` on the Editor, Player or Animator command line, or `"shader_compiler": "slang"` in `phasma_settings.json` ([GraphicsApiSelection.cpp](../../../Phasma/Core/Code/API/GraphicsApiSelection.cpp) `ResolveShaderCompiler`; the log says `Selected shader compiler: ...` and every `[Shader] Compile(hlsl)` line ends with `compiler=`). The choice salts the shader-cache hash ([ShaderCache.cpp](../../../Phasma/Core/Code/API/ShaderCache.cpp)), so the compilers never reuse each other's bytecode. Builds without the runtime shader compiler (Android) ignore it. Slang runs slangc from the `PE_SLANGC_PATH` CMake cache variable (a STRING, default `slangc` on PATH, slashes normalised; defined whenever the runtime compiler is on), one process per shader ([SlangCompiler.cpp](../../../Phasma/Core/Code/API/SlangCompiler.cpp) `CompileWithSlang`). Each slangc start costs about 170 ms before it compiles anything (`slangc -v` median 168 ms; measured 2026-10-12 with another build running), while the compile itself is on par with DXC's (LightingPS 1.1 s through slangc against 1.4 s through the DXC command line). Compiles run in parallel on the loader threads and later starts read the cache. The in-process Slang API would remove the start cost, at the price of shipping `slang-compiler.dll` (25 to 30 MB) beside the engine. Runtime cost is the same: a heavy fullscreen SDF pass over saved Sponza (local `.testpool/tests/slang_stress_pass.py`, Release, immediate present, GPU timers, profiler `avg_ms` over 10 snapshots) took 1.315 against 1.322 ms (Slang against DXC) and 1.316 against 1.328 ms on Vulkan, and 1.261 against 1.280 ms on DX12 (2026-10-12). Whole frames showed no compiler effect: totals swung 10 to 25% between runs, and an intermittent 0.6 to 2 ms DX12 GPU stall between two passes hit the Slang runs with the stress pass but the DXC runs on plain Sponza. A shader may also be written in Slang's own language: slangc only parses that syntax from a `.slang` file, so `CompileWithSlang` keeps a `.slang` source's extension for its temporary copy, and such a shader compiles only with `--shader-compiler slang` (DXC cannot read it). Keep its `[[vk::binding]]` and `[[vk::push_constant]]` declarations on one line each, because the DX12 path rewrites them line by line. The same SDF scene written with interfaces, generic shape combinators and autodiff normals (local `.testpool/tests/slang_native_pass.py`) rendered the same frame and took 1.281 against 1.31 ms on Vulkan and 1.225 against 1.265 ms on DX12 next to its HLSL version under slangc (2026-10-12).

Slang compiles the same expanded source and defines as DXC, at `-O3`. For Vulkan it targets SPIR-V 1.6 (1.5 when the caps pick Vulkan 1.2) with `-fvk-use-entrypoint-name` and `-fvk-use-dx-layout`, which reproduces DXC's cbuffer and push-constant packing; Slang's default std140/std430 puts a `float2` after a `float` at offset 8 where DXC puts it at 4. On SPIR-V 1.6 it also passes `-g`, as DXC always passes `-Zi` (`PE_DEBUG_MODE` is 1 in [Defines.h](../../../Phasma/Core/Code/Base/Defines.h)): Slang's debug info is `NonSemantic.Shader.DebugInfo.100`, which needs `VK_KHR_shader_non_semantic_info`, core only from Vulkan 1.3. On LightingPS it added 0.6% instructions and made the module 3.9 times larger (2026-10-12). DXC's DX12 objects carry no debug part (through the API it goes to a PDB the engine drops), so Slang's DXIL gets none either. For DX12 it compiles the rewritten source (registers and `PE_DX12`) to `sm_6_6` DXIL through the process's own `dxcompiler.dll` (`-dxc-path`), with `-no-mangle`: otherwise Slang appends `_0` to every resource name and DX12 reflection, which maps names back to `[[vk::binding]]`, rejects the shader. The DXIL gets the same private source part as DXC's. Slang drops resources and push blocks a shader does not use, as DXIL always did. Binding one the shader dropped logs `[Descriptor] Binding N not found` ([Descriptor.cpp](../../../Phasma/Core/Code/API/Descriptor.cpp)) and push constants go only to reflected ranges; no engine pass hit that in the Slang runs, because each uses what it declares. A storage image must declare `[[vk::image_format]]`: Slang leaves an undeclared one `Unknown`, which needs the without-format device features, where DXC infers it. DepthPyramidCS, EquirectangularToCubemap, PrefilterCubemap and RayTrace's `rtDepth` were annotated on 2026-10-12 with exactly what DXC inferred, so DXC's output did not change. StructuredBuffer elements are not a Slang trap: with `-fvk-use-dx-layout` Slang's SPIR-V strides equal D3D's (DXIL from either compiler) on nine probe structs, while DXC's own SPIR-V differs wherever a `float3`, or a `float2` after a `float`, meets its relaxed std430 (strides 48/16/32/32 against 36/12/20/24; measured 2026-10-12). An element struct that renders the same on DXC's Vulkan and DX12 therefore does under Slang too, and the validator compares structured strides.

Slang's SPIR-V differs from DXC's in four ways the engine depends on, and `CompileWithSlang` ([SlangCompiler.cpp](../../../Phasma/Core/Code/API/SlangCompiler.cpp)) patches each in the binary, so cached modules stay alike. Slang's DXIL needed none of them.
- Input names: Slang names stage inputs after their struct fields (`input.id`), while the engine finds the per-draw ID by DXC's `in.var.PE_DRAW_ID` ([VulkanReflection.cpp](../../../Phasma/Core/Code/API/Vulkan/VulkanReflection.cpp), [VulkanPipelineImpl.cpp](../../../Phasma/Core/Code/API/Vulkan/VulkanPipelineImpl.cpp)). `NameInputsBySemantic` renames each input to `in.var.<SEMANTIC>` from slangc's `-reflection-json`. The JSON gives `TEXCOORD0` as `TEXCOORD`, so a restored or renamed `TEXCOORD0` reads `in.var.TEXCOORD`; only `PE_DRAW_ID` is matched by name.
- Unused vertex inputs: Slang leaves them out of the module even with `-preserve-params` (only `-O0` keeps them); DXC keeps them (`-fspv-preserve-interface`). [Reflection.cpp](../../../Phasma/Core/Code/API/Reflection.cpp) `GetVertexBindings`/`GetVertexAttributes` lay out a vertex buffer from the vertex shader's inputs (stride = sum of input sizes, offsets in location order), so ShadowsVS's unused `uv` shifted joints, weights and draw IDs, the shadow map turned to garbage and a shadowed scene went dark. `RestoreDroppedInputs` declares each dropped input again at its location from the JSON. It handles 32-bit scalars and vectors; any other type logs `[Slang] ... is not restored` and the layout differs from DXC's.
- `precise`: Slang drops it from SPIR-V (no `NoContraction`; `-fp-mode precise` does not add it, and its DXIL keeps it). GBufferVS depth-tests EQUAL against DepthVS's position, so skinned meshes the driver fused differently in each shader failed the test and rendered black and speckled. `KeepPreciseMaths` puts `NoContraction` on every float operation of a module whose source uses the `precise` keyword (DepthVS and GBufferVS today; a name like ParticleVS's `preciseFrameIndex` does not count), a superset of DXC's per-value marking.
- `SV_VertexID`/`SV_InstanceID`: Slang lowers them the D3D way (`VertexIndex - BaseVertex`, `InstanceIndex - BaseInstance`); DXC reads the raw Vulkan index. On Vulkan the voxel shaders take their draw ID from `SV_InstanceID`'s `firstInstance` (DX12 uses `PE_DRAW_ID`), so `UseRawDrawIndices` rewrites each such subtraction as `index | index`. Slang's lowering needs `DrawParameters`; the engine enables every supported device feature ([RHI.cpp](../../../Phasma/Core/Code/API/RHI.cpp)).
Sponza never showed the last three: its saved scene has shadows off, no skinned meshes and no voxels. A skinned, shadowed game scene with project shaders found them on 2026-10-12.

Hot reload compiles through the same path: a GBufferVS edit recompiled with slangc 0.2 s after the save and the editor answered 0.59 s later; the module had the debug info, the `in.var` names and `NoContraction`, and passed `spirv-val` (2026-10-12). slangc's errors reach the log, but they point into the expanded copy under `ShaderCache/_slang`, which is deleted after the compile. An edit to TonemapPS in the Sponza editor probe triggered no reload, but not because reload missed it: with an empty cache TonemapPS never compiled at startup there, so that run never built the pass's shaders. In the Player on a scene with tonemapping on, the same edit recompiled through slangc 0.7 s after the save. A syntax error saved during a Slang reload logs slangc's error and the editor keeps running (2026-10-12, after the fix described below).

A shader save that fails to compile used to kill the editor (`Error in function: VulkanShaderImpl`, then `Unhandled non-standard exception in editor host`). The cause was Jolt's `_HAS_EXCEPTIONS=0` reaching Runtime and the editor, see [Runtime 3D Physics](runtime/runtime-3d-physics.md#build-jolts-exception-define). Now the compiler's error and a `Failed to compile` line reach the log, and [RenderPassShaderReload.cpp](../../../Phasma/Runtime/Code/Render/RenderPassShaderReload.cpp) restores each pass's previous shaders, so the viewport doesn't change. [ReflectMaterialLayout](../../../Phasma/Runtime/Code/Scene/MaterialReflection.cpp) keeps the last material layout until the next save, so a scene rebuild while the file is still broken survives too. The next valid save then reloads normally. Verified 2026-10-12 with Vulkan and DX12, DXC and Slang, in the editor and the Player; pool tests `shader-reload-broken-vulkan` / `-dx12`.

`TexSamplerDecl`/`CubeSamplerDecl` ([Common.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/Common/Common.hlsl)) put `tex` and `sampler_tex` on one binding with `[[vk::combinedImageSampler]]`, so DXC emits one combined variable and every stage reflects a COMBINED_IMAGE_SAMPLER; DX12's `Dx12ShaderImpl` rewrites the pair to `t<bind>`/`s<bind>` and [Reflection.cpp](../../../Phasma/Core/Code/API/Reflection.cpp) merges it back into one combined binding. Slang ignores the attribute and emits a separate image and sampler on the binding, which Vulkan backs with the same combined descriptor and Reflection.cpp merges the same way. Do not drop the attribute to make DXC match (checked 2026-10-12 with DXC 1.9.0.5347): a stage that only `Load`s the texture (GridPS) then leaves the sampler out of its entry-point interface and reflects SAMPLED_IMAGE, and a vertex shader sharing a file with its pixel shader starts reflecting the pixel shader's bindings and push constants. A half-used pair is still one descriptor: `MergeDescriptors` ([Shader.cpp](../../../Phasma/Core/Code/API/Shader.cpp)) lets a stage's COMBINED binding absorb another stage's SAMPLED_IMAGE or SAMPLER half. DX12 needs that even with the attribute, because DXIL drops the unused sampler register: before 2026-10-12 a pipeline whose vertex stage sampled a pair its pixel stage only loaded threw "Descriptor binding type mismatch during merge" and killed the editor (pool tests `merge-pair-stages-dx12`/`-vulkan`). Unused `[[vk::push_constant]]` declarations were removed from DepthPS, ObjectIdPS and VoxelGBufferVS; push ranges come from reflection (verified 2026-10-11 with VVL on Vulkan).

`-DPE_SLANG_VALIDATION=ON` (default OFF; it needs the runtime shader compiler and DXC, and CMake warns when they are off) also compiles every shader DXC compiles with slangc and logs `[Slang] ... matches DXC` or a `reflection mismatch` warning; DXC output is still what the engine uses, and nothing is validated while Slang is the compiler. It salts the cache too, so turning it on checks every shader once. The comparison covers the resources the entry point uses: set, binding, kind and array count; image dimension and storage-image format; subpass input index; and for uniform, storage and push blocks the member offsets, array and matrix strides and size. On DXIL it compares the D3D bind type and count, cbuffer variable offsets and structured strides. Nesting is flattened on both, because Slang wraps some arrays and cbuffer contents in a struct DXC does not. A texture slot is one key whether it is combined, a separate image plus sampler, or an image alone. Comparing only used resources is deliberate: DXC's `-fspv-preserve-bindings` keeps unused declarations, but Slang leaves them out of the entry point's interface even with `-preserve-params -O0`, and SPIRV-Cross (the engine's reflection too) hides resources missing from that list in SPIR-V 1.4+. A binding no stage uses passes unchecked. Any failure (reflection, filesystem, a define that is not UTF-8, a slangc error or timeout) logs a warning and never fails the DXC compile; a slangc that cannot start warns once and later shaders skip validation. A mismatch keeps the shader's source in `ShaderCache/_slang`. [Process.cpp](../../../Phasma/Core/Code/Base/Process.cpp) `RunProcess` underpins both: its timeout applies while the child runs (Windows drains output on a thread, POSIX polls), concurrent spawns cannot inherit each other's pipes (a spawn lock on Windows, close-on-exec on POSIX), and on POSIX a failed exec reports `started = false`.

## Solid-Color Skybox Fallback

When no HDR path is configured, `SkyBox::LoadSolidColor()` builds a 1x1 cubemap. On Vulkan that fill is a transfer clear of all six faces (`vkCmdClearColorImage`), not six `vkCmdCopyBufferToImage` regions. Some ICDs (Mesa Dozen on WSL) report `minImageTransferGranularity = (0,0,0)`, which requires a whole-subresource copy; a per-face 1x1x1 copy then fails `VUID-vkCmdCopyBufferToImage-imageOffset-07738`. A clear is legal on every Vulkan queue, including Android. DX12 has no matching clear without an RTV, so it keeps a packed 6-layer buffer upload. The HDR equirect-to-cubemap path is compute and is unchanged.

## Skybox Runtime Reload

Runtime `skybox.load(...)` exercises this path: `SkyBox::LoadSkyBox()` loads an equirect HDR, dispatches `EquirectangularToCubemap.hlsl` into cubemap mip 0, then dispatches `PrefilterCubemap.hlsl` through another transient compute `PassInfo` to fill roughness-filtered mips for IBL. Startup and runtime reloads should both produce nonzero cubemap memory; a black cubemap after runtime reload points first at descriptor/pipeline binding and transient-pass lifetime.

IBL specular sampling expects those roughness-filtered cubemap mips, with roughness mapped linearly to the mip range (`ComputeIBL_Common()` uses `mip = roughness * (mipCount - 1)`).

A bright HDR sun is a sub-texel, very-high-radiance delta. Naive GGX importance-sampling of it during prefiltering lights up isolated texels on a regular lattice (the sample set is identical per texel, so the sun falls into the same fixed sample slots everywhere), which the floor reflection magnifies into a grid of bright squares. `PrefilterCubemap.hlsl` suppresses this with three load-time measures:

- **`MAX_PREFILTER_RADIANCE`** — clamps per-sample radiance so the delta sun has no high-contrast spike to expose.
- **`SOURCE_MIP_BIAS`** — biases each sample toward a blurrier (pre-averaged) source mip, scaled by roughness, so the integral converges to a smooth blur (low roughness stays sharp). This is the main lever; raise it if squares/blotches return, lower it if rough reflections over-blur.
- **`PrefilterSampleCount`** (in `Skybox.cpp`) — generous counts (64/128/256/512); load-time only.

Per-texel jitter was tried and removed — once the mip bias converges the integral, jitter only trades the grid for swimming grain. The prefilter is a one-time bake at skybox load/reload (`LoadSkyBox` → `PrefilterSkyboxMips`), not a per-frame pass; per-frame IBL is a single `SampleLevel` of the baked mips. If the prefilter failed to compile/run, the mips are black.

## Skinned Motion Vectors

The G-buffer's velocity follows a skinned mesh's bones, not only its node's transform and the camera. Each skinned node's joint tail holds the current pose and then the previous rendered frame's pose (`NodeGpuData.jointCount`, byte 136, tells the shader where the second block starts; the node's data is `sizeof(NodeGpuData) + 2 * jointCount * sizeof(mat4)`). `Scene::UpdateUniformData` rolls `prevJointMatrices` from the last uploaded pose on the node's first upload of a frame (the late script catch-up uploads again without rolling) and keeps a moving node dirty for one more frame, so a pose that stops reads zero motion instead of its last step. `GBufferVS.hlsl` skins `prevPositionCS` with that previous pose; before this TAA smeared animated limbs, whose velocity carried only the camera and node motion (verified 2026-09-29: [Scene.cpp](../../../Phasma/Runtime/Code/Scene/Scene.cpp), [SceneBuffers.cpp](../../../Phasma/Runtime/Code/Scene/SceneBuffers.cpp), [GBufferVS.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/Gbuffer/GBufferVS.hlsl)). Depth, shadow and ray-tracing passes read only the current block at unchanged offsets.

## Motion Blur Sampling

The shared `MotionBlurPS.hlsl` filter converts the existing frame-time-normalized velocity to source-image pixels before choosing its sample count. Samples use symmetric midpoint positions and tent weights. The blur span is capped at the configured sample budget (16 pixels at the default 16 samples, at most 32), keeping adjacent taps no more than one pixel apart. Stretching a fixed number of taps over an unbounded span made thin silhouettes appear as separate translucent copies during fast camera rotation. Longer blur would require a reconstruction filter rather than merely increasing the velocity multiplier.

Color fetches use explicit mip level zero and clamp to half-texel-inset image bounds, so the repeat sampler cannot pull the opposite edge into the blur. Zero strength/blend, a one-sample budget, subpixel motion, and invalid velocity retain the sharp color; filtering preserves its alpha. The effect remains enabled by the normal scene settings, including in the Animator.

Skybox pixels have zero depth and no mesh velocity. `MotionBlurPass` supplies a rotation-only reprojection from the current camera view to its previous view, using the same perspective sky rays as lighting (including its virtual perspective sky for orthographic cameras). The shader uses this for zero-depth pixels instead of skipping them. Camera translation and projection jitter are excluded, so an infinitely distant sky blurs during rotation but remains sharp during translation or stationary TAA jitter. Geometry continues to use the existing velocity buffer.

## Lines And Script Passes

The editor/Animator grid is an analytic world-aligned plane at Y=0 (`GridPass`, `Utilities/GridPS.hlsl`). It alpha-blends into the full-resolution display target after TAA, upsampling and motion blur, with destination alpha preserved. Both the pass-wide and attachment blend switches must be enabled; disabling the former replaces the background with transparent grid pixels and produces a black footprint in the viewport.

Grid spacing follows the projected pixel footprint, cross-fading between world-space decades with persistent major lines. Each line family is antialiased and suppressed before its cells become subpixel; only grazing-angle opacity fades toward the horizon, with no fixed-radius cutoff. Rays start at each pixel's near-plane point and use two finite reverse-Z depths, supporting perspective with an infinite far plane and orthographic cameras. Scene-depth rejection uses the matching jittered depth texel at its own resolution; zero depth is sky. Derivatives are evaluated before divergent discards so object edges cannot corrupt the AA footprint.

- `RenderType::Lines` is reserved for hardware line-strip meshes from `Primitives::CreatePolyline(...)` / Lua `scene.attach_lines(node, {vec3...}, closed)`. These meshes are skipped by the indirect raster buckets, shadow cull/draw, mesh-constants culling path, and ray-tracing BLAS/TLAS triangle path. `LinesPass` draws them directly from the position stream after `LightTransparent` and before TAA, using node uniform data for transforms and material emissive (or base color) for color.
- Lua registers frame-graph callbacks with `render_graph.add_pass{name = ..., order = ..., reads = {...}, writes = {...}, fn = function(cmd) end}` (order in the table since 2026-10-09) and removes them with `render_graph.remove_pass(name)`. `reads` are render targets sampled in the fragment stage (the graph issues their barriers), `writes` the targets the pass renders into; both enter the order checks, and a script pass that declares them may share a column. A scene's `render_pass_orders` key `script:<name>` overrides it; a pass without either runs in its own column after the built-in passes (`kScriptRenderPassUnplacedOrder`). `render_graph.add_fullscreen_pass` adds a native fullscreen shader pass (no Lua per frame). C++ scripts' fullscreen passes keep their `order`; `render_graph.has_pass(name)` also sees C++ scripts' passes (ABI 12), which a Lua reload keeps. Editor and player renderers watch the script-pass registry revision and rebuild the graph before command recording when scripts add/remove passes. The callback receives the frame `CommandBuffer`; `render_graph.get_target(name)` resolves current render targets such as `viewport`, `display`, and `depthStencil` for passes that need to record their own barriers/blits/attachments. Lua `cmd:begin_pass(...)` copies its attachment table into thread-local storage that remains valid until `cmd:end_pass()`, so scripts can safely record manual render passes without owning C++ attachment vectors.

## Ray Tracing Cameras And Geometry

- Full ray tracing must build camera rays differently for perspective and orthographic projections. Perspective rays originate at the camera and use the unprojected per-pixel direction. Orthographic rays originate from the unprojected per-pixel view position and share the engine's positive view-Z forward direction; Hybrid depth clamps are measured from that per-pixel origin. Using perspective-style ray origins for orthographic cameras makes 2D quads/sprites appear as giant screen-filling surfaces in full RT.
- When geometry changes, the RT descriptor set must refresh every resource whose backing object can be recreated: TLAS, scene uniforms, mesh constants, combined geometry buffer, MeshInfo buffer, material table, and image views. A rebuild with no ray-traced instances (every mesh removed or skinned) leaves the TLAS null, but these updates never see it: `RuntimeSceneRenderer::Update` ([RuntimeSceneRenderer.cpp](../../../Phasma/Runtime/Code/Render/RuntimeSceneRenderer.cpp)) runs `Scene::Update` first and then enables `RayTracingPass` and `GlobalIlluminationPass` only while `GetTLAS()` is non-null. Verified 2026-10-18: deleting the last ray-traced cube in ray-traced mode with descriptor heaps kept the editor running on a build whose heap writer dereferenced the acceleration structure without a null check. Primitive-cache hits share their immutable scene-source metadata but still create an instance mesh index and require a BLAS rebuild, because `m_blasByMesh` is keyed by scene mesh index. Deleted, unreferenced mesh slots and owned material instances are reclaimed; a primitive cache entry promotes another live mesh with the same source before its old slot is recycled. The merged BLAS buffer size must be computed with the same align-before-place math as the build loop so later BLAS ranges stay inside the allocation.
- Render visibility reaches ray tracing through the TLAS instance mask (fixed 2026-10-15). `node:set_visible(false)` (`Scene::SetNodeRenderVisible`) and the off-screen animation cull only clear `renderVisible` for `CullingCS`/`ShadowCullCS`; the TLAS kept those instances. In the default Hybrid mode (`RenderMode::Hybrid`, `Settings.h`) `RayTracingPass` traces transparent instances (mask 0x80) over the raster frame, so hidden transmission/alpha-blend meshes kept drawing, and refraction, shadow, GI and full-RT rays still hit hidden nodes. `Scene::WriteRTInstances` ([SceneRayTracing.cpp](../../../Phasma/Runtime/Code/Scene/SceneRayTracing.cpp)) now writes mask 0 for a node whose `renderVisible` is 0, keeping its transform and BLAS so the in-place refit stays valid. `Scene::UpdateRenderVisible` ([SceneNode.cpp](../../../Phasma/Runtime/Code/Scene/SceneNode.cpp)) sets `m_tlasMasksDirty` when the node owns RT instances, and `UpdateTLASTransformations` refits on that flag as well as on moved nodes: at most one refit per frame, the cost a moved node already pays. Pool test `transmission-hidden-rt` (Vulkan and DX12). The two raster passes that do not read the cull lists skipped the flag as well: `LinesPass` drew every Lines/SpriteOutline node, and `ShadowPass` with `frustum_culling` off drew every mesh from `IndirectAll`. `LinesPass` now skips nodes whose `renderVisible` is 0, and `ShadowPass` always runs `ShadowCullCS`, with keep-everything planes when frustum culling is off. Pool test `hidden-node-passes`, verified 2026-10-15.
- Transmissive emissive in ray tracing (fixed 2026-10-15): `RayTrace.hlsl` closesthit added emissive to the surface term before the glass mix (`lerp(lighting, glass, transmissionFactor)`), so at transmission factor 1 a glowing cube kept only the Fresnel share of its glow in Hybrid (932 px at G 82, against 8,676 px at G 153 in raster). It now adds emissive after the mix, once at the entry face, as `LightingPS.hlsl` adds it after its transmission lerp. Same pool test.

## Global Illumination And Cluster Geometry

PE has engine-native probe GI and resident cluster rendering; these use published algorithms and the existing RHI. Both are opt-in scene settings, saved in `.pescene` and exposed in Scene Settings and Lua. Verified 2026-10-07.

### Dynamic Diffuse GI

[GlobalIlluminationPass](../../../Phasma/Runtime/Code/RenderPasses/GlobalIlluminationPass.cpp) traces an 8×8×8 probe grid with 256 importance-sampled rays per probe (directions and pdfs from the probe radiance cache, see the pitfall below), integrates directional irradiance (RGBA32F) and distance moments into bordered octahedral atlases, keeps a 16×16 octahedral radiance map per probe, and keeps separate histories. [ProbeVolume.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/GlobalIllumination/ProbeVolume.hlsl) gathers eight neighbouring probes with trilinear weights, normal bias, distance-based visibility and backface classification. Placement: when the static mesh bounds (enabled, visible mesh nodes; refit on geometry changes, grow-only per scene generation) span at most 7 cells of 4× `gi_probe_spacing` per axis, one volume is fitted to them with per-axis spacing (Sponza about 5×2×3 m) and no edge fade; otherwise four cascades follow the camera from `gi_probe_spacing` up (see Cascades below), the last fading into environment lighting over its outer cell, each remapping overlapping atlas tiles when the camera crosses one of its cells (only newly exposed probes start fresh). Pitfall, the bright band: before 2026-10-08 the grid always followed the camera, so with IBL on everything past about 6–8 m fell back to unoccluded sky light. In Sponza's covered aisle the floor jumped from 17 to 63 (the GI-off value) at the box edge, and the edge moved in 2 m steps as the camera flew. With the fitted volume the same aisle stays at 9–18. Pool test `gi-fitted-volume-vulkan`/`-dx12` checks a 40 m covered corridor stays flat (far/near 1.14) and, as a self-check, that a 1 m camera-following box still shows the band (1.53 with world probes alone, 1.36 with screen probes; threshold 1.25 since 2026-10-10). Scene replacement, spacing or placement changes and a frame rendered without a probe update (GI toggled off, no TLAS; counted by `SceneRendererHost::GetRenderedFrames`, see the skipped-frame pitfall under Screen Probes) discard history, but lighting still samples the newly updated atlas on that frame. This history is independent of TAA. Verified 2026-10-08.

The pass runs after the G-buffer and before opaque lighting. [LightPass](../../../Phasma/Runtime/Code/RenderPasses/LightPass.cpp) consumes the cache for transparent lighting and, through screen probes (below), for opaque lighting; valid probes replace the diffuse environment term while environment specular remains. [RayTrace.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/RayTracing/RayTrace.hlsl) supplies emissive/direct hit radiance, alpha-cut visibility and probe feedback for additional diffuse bounces, and samples the same cache in hybrid/full RT shading. Probe rays ignore alpha-blend/transmission surfaces; shadow rays retain their existing behaviour.

Controls are `global_illumination` (default false), `gi_probe_spacing` (2 world units; the finest camera-following cascade's spacing and the fitted-volume limit), `gi_intensity` (1) and `gi_hysteresis` (0.999: how fast a probe texel follows a detected lighting change, restarting its average at 1 / (1 - h) frames, 4 to 49; noise keeps averaging up to 1000 frames whatever the value).

Cascades (Lumen roadmap step 5, [spec](../../superpowers/specs/2026-10-10-gi-cascades-design.md), 2026-10-10): a camera-following volume is 4 nested 8x8x8 cascades at `gi_probe_spacing` x 1, 2, 4, 8 (+-7, 14, 28, 56 m at 2 m), each snapped to its own spacing and scrolling on its own, as Lumen's radiance cache clipmaps; a fitted volume stays one cascade (`GlobalIlluminationPass::kCascades`, shader `GI_MAX_CASCADES`). Probes are numbered across cascades (cascade x 512 + cell), so every atlas holds four bands stacked downward and the tile maths is unchanged; the uniforms carry per-cascade origin, history origin and spacing plus `gi_cascadeCount`, and ray length (16 spacings), normal bias (0.1) and far-field start (1.75) follow each probe's cascade (`ProbeVolume.hlsl`: `ProbeCascade`, `ProbeIndex`, `ProbeCascadeAt`, `ProbeCascadeIrradiance`). Lighting and the screen probes' far-field hand-off use the finest cascade around the point and blend into the next over its outer cell; only the last fades into sky light. The probe trace only covers the active cascades (`RayTracingPass::m_traceHeight`). Measured 2026-10-10 by pool test `gi-cascades-vulkan`/`-dx12` (linear viewport image): the floor under a 40x40 m roof 12 m up, 40 m from the camera, reads 92.8 against 92.4 for a reference with 1 km screen probe rays; one volume read 102.1 (sky leaking in past it). Re-measured 2026-10-11 after the switch to L2 SH (reference recaptured with L2): 89.2 against 88.9, open ground 107.5 against 104.7 (limit 3, a thin margin that predates L2). Pitfall: a 100 m covered corridor looked like a failure (the floor brightens from 52 to 87 down the corridor) until the same reference showed that rise too, since the far floor nears the open end: check expectations against a traced reference before tuning. A corridor narrower than the coarse spacing has no probes inside it in the coarse cascades; screen probe rays (2 x far-field start, up to 56 m) still see its walls. Converge before reading: under GPU contention the first reads (79 for a 52 floor) came from GI that had not settled. Cost: every cascade is traced and updated every frame (Lumen amortises distant clipmaps), about four times the world probe pass in camera-following scenes; not yet measured on a quiet GPU.

Pitfall, GI trembling (2026-10-07 to 2026-10-10): a probe's per-frame estimate is noisy wherever a few rays catch a small bright surface (sunlit patches, emissives). A fixed history blend lets that noise through (candle flicker at 0.95); the 2026-10-08 progressive average fixed the steady state, but `gi_hysteresis` 0.85 still left about 30% of pixels trembling, and every light, transform or geometry change restarted all probes at 49 frames (15-22% trembling for about 3 s). The probe radiance cache (Lumen roadmap step 2, [spec](../../superpowers/specs/2026-10-10-gi-radiance-cache-design.md)) removes both. [ProbeSample.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/GlobalIllumination/ProbeSample.hlsl) importance-samples the 256 rays of each probe from last frame's radiance ([ProbeRadiance.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/GlobalIllumination/ProbeRadiance.hlsl); texel probability 0.75 x flux share + 0.25 x sphere share, stratified, jittered inside the texel, pdf through the octahedral Jacobian |p|^3); [ProbeUpdate.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/GlobalIllumination/ProbeUpdate.hlsl) weights every ray by 1/pdf (self-normalised importance sampling, so uniform rays give the old estimator) and keeps per irradiance texel the mean, the sample count (distance.z) and the variance of the per-frame change statistic (distance.w, negative when the last frame was outside the noise). The statistic is the largest per-channel difference to the mean, so colour-only changes count. Two frames in a row beyond 4 sigma + 2%, or a visibility change (active flag flipped, mean hit distance beyond its spread), hold that texel's average at 1 / (1 - gi_hysteresis) frames (4-49) while the change continues; a single frame is not enough, since an emitter's heavy-tailed noise makes outliers, and frames outside the noise are left out of its estimate so a change cannot raise its own threshold. Everything else averages up to 1000 frames, capped at 200 after a known change (reset bit 1: `Scene::GetGiInputVersion` from the light hash, TLAS builds and refits, plus geometry and the settings that shade ray hits) instead of today's drop of every probe to 49. Measured 2026-10-10 on an RTX 4080 SUPER by pool tests `gi-noise-vulkan`/`-dx12` (PrintWindow grabs of the viewport; flicker = pixels leaving a 5-frame median trend by more than 4/255): GI on equals GI off at 0.999, at 0.85 and after a light change (Cornell box 0.25-0.31% against 0.26-0.27%, small emitter 0.02-0.03% against 0.01%). By plain max-min over 3 s, 0.85 fell from 28.7%/33% to 0.4-0.5% (Cornell/emitter) while the window after a change reads 7.3%/20% (from 15%/22%): that is the fade of the change itself (a light 4 -> 6, an emitter orange -> green) settling inside the window, not trembling, which the trend-based figure above shows. Converged region colours match the pre-change binary within 3%. Cost on Sponza with GI on (medians of 10 snapshots, two runs each, measured before the final history fixes, which only add a few ALU operations per texel): GPU frame 0.407 -> 0.516 ms on Vulkan and 0.484 -> 0.632 ms on DX12, the sample pass 0.008/0.014 ms. Measure flicker with OS-level grabs, not MCP captures: those bump the geometry version.

Pitfall, Vulkan sync validation (fixed 2026-10-10): the GI probe pass and the hybrid ray-tracing pass both run `RayTracingPass::ExecutePass`, which refits the TLAS when a ray-traced node moved; the second refit wrote the TLAS while the first pass's trace rays could still read it. `Scene::UpdateTLASTransformations` now refits once per frame (`m_tlasRefitFrame`), and `UpdateVulkanTLAS` issues a barrier just before the in-place build (ray-tracing, compute and fragment acceleration-structure reads to the build); DX12 already had `PrepareBuildBarriers`. Barrier ranges must cover the whole bound buffer: `Buffer` rounds storage sizes up (`AlignStorage`) and descriptors bind the whole buffer, so a barrier sized from a count (shadow-cull indirect buffers at `indirectSize`, the object-ID `ObjectIdNodeVis` at capacity x 24) left the tail unsynchronised between per-cascade dispatches; those barriers now use `Buffer::Size()`, in place, just before each dispatch. The main culling pass still sizes its indirect barriers from `indirectSize` but runs once per frame and is not flagged. Pool tests `gi-flicker`/`gi-fitted-volume`/`gi-scroll`/`cluster-instances`/`cooked-clusters`-vulkan cover them.

Local Vulkan/DX12 checks confirm emissive colour transfer, resizing, toggles and raster/hybrid/full RT operation without GPU validation errors. The algorithm is based on [ray-traced irradiance fields](https://jcgt.org/published/0008/02/01/) and [production DDGI](https://jcgt.org/published/0010/02/01/).

### Screen Probes

[ScreenProbePass](../../../Phasma/Runtime/Code/RenderPasses/ScreenProbePass.cpp) (render graph `ScreenProbes`, order 470, between `GlobalIllumination` and `LightOpaque`) is Lumen's screen probe gather (roadmap step 3, [spec](../../superpowers/specs/2026-10-10-screen-probes-design.md)). It runs whenever GI does in raster or hybrid mode; there is no separate setting. Per frame: [ScreenProbePlace.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/GlobalIllumination/ScreenProbePlace.hlsl) puts one probe on each 16×16 tile at a jittered G-buffer pixel and aims 64 rays over 8×8 world-space octahedral bins (0.25 × cosine share + 0.75 × cosine × last frame's bin radiance, read from the probe at the reprojected tile when it lies on the same surface); [RayTrace.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/RayTracing/RayTrace.hlsl) (`SCREEN_PROBES` raygen) traces them, shading hits as world probe hits; [ScreenProbeIntegrate.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/GlobalIllumination/ScreenProbeIntegrate.hlsl) turns the bins into L2 SH (9 coefficients, a texel each; L1 until 2026-10-11, see the pitfall below); [ScreenProbeFilter.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/GlobalIllumination/ScreenProbeFilter.hlsl) averages each direction bin with the same bin of its 3×3 neighbours on the same surface where the neighbour's hit along it, seen from this probe, lies within 10° (Lumen's angle check, unverified default; bins carry their mean hit distance in alpha) and projects the result onto the L2 SH; [ScreenProbeResolve.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/GlobalIllumination/ScreenProbeResolve.hlsl) blends the four nearest probes per pixel (bilinear × plane distance × normal), evaluates their SH for the pixel normal and averages over time (camera reprojection, history taps kept when their packed normal and distance match, up to 32 frames). `LightingPS.hlsl` reads that irradiance in the opaque pass where screen probes cover the pixel and world probes elsewhere (`cb_screenProbes`, set 3 binding 4).

Pitfall, the hand-off (2026-10-10): screen rays run 2 × `ProbeFarFieldStart()` (3.5 world probe spacings) and then take the world probes' radiance. Looking that up at the ray's end was blotchy (cell-sized patches, mean error 1.8/255 in the Cornell indirect view against a reference with 50 m screen rays); at the ray's origin with `ProbeLighting`'s weights it was smooth (1.07) but leaked through a 5 cm wall (2.9/255 on the closed side, GI off 0), because distance-moment visibility fails for probes that see the wall at a grazing angle. Lumen's answer is used: the world probe rays continue past their interpolation footprint (`ProbeFarFieldStart()`, 1.75 spacings; `GI_FarRays`, averaged into `GI_FarRadiance` by `ProbeRadiance.hlsl`), so a world probe on the far side of a thin wall sees past it; the screen rays must reach that far plus the distance to the farthest interpolated probe, or they skip surfaces in between (2 spacings left the tall block's open face 34% too dark). Result: leak 1/255, error 1.05.

Ray hits are lit diffuse-only, as Lumen's surface cache (see Reflections below), and the histories follow the unjittered camera motion (same section).

Pitfall, fireflies (2026-10-10): projecting the rays onto SH with 1/pdf weights blows up at grazing angles, where the cosine pdf vanishes (single-frame red/green/white blobs on dark faces, frame-to-frame p99.9 jump 23/255). The SH is built from the bins instead (mean radiance × solid angle; a bin no ray reached keeps last frame's value, or the mean of the filled bins), as Lumen does: p99.9 jump 4/255.

Measured 2026-10-10 on an RTX 4080 SUPER by pool tests `gi-screen-probes-vulkan`/`-dx12` (PrintWindow grabs): against the 50 m-ray reference the Cornell view differs by 0.45/255 on average (world probes alone 1.0; they over-bleed wall colour onto the blocks), the contact view by 0.95-0.99 (world probes 2.6), Cornell and small-emitter regions within 6% (most within 2%; world probes put the floor next to the emitter at 106 against 165), and the closed side of the thin wall stays at 1/255. `gi-noise` flicker stays within 0.2 points of GI off (baseline recaptured for screen probes); orbiting the Cornell box 0.3° per frame gives 3.8% trend-leaving pixels against 3.7-4.0% for GI off and world probes (edges and the editor grid). Ray guiding cuts the small-emitter indirect flicker from 0.18% to 0.01%. Cost on Sponza (viewport 1472×841, medians of 10 snapshots, two runs): screen probes 0.22 ms Vulkan / 0.27 ms DX12, world probes 0.18 -> 0.24/0.30 ms with the far-field rays; GPU frame 0.52 -> 0.81 ms Vulkan and 0.63 -> 0.99 ms DX12. Scaled by pixels to 1440p that is about +0.7/+0.9 ms (not measured at 1440p: the editor's render scale caps at 1). Memory at 1440p is about 130 MB (per-pixel irradiance and packed-geometry histories 88 MB, per-ray targets 37 MB). Object motion and adaptive probes were added later the same day (below and under Reflections).

Adaptive probes (Lumen's adaptive placement, 2026-10-10, [ScreenProbeAdaptive.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/GlobalIllumination/ScreenProbeAdaptive.hlsl)): after the uniform placement, a group per 8×8 sub-tile checks its jittered pixel; where the four uniform probes' bilinear × plane × normal weight (`ScreenProbeWeight`) sums under 0.25, the point where the resolve's coverage starts handing the pixel to world probes, the sub-tile takes a probe of its own. Slots come from an atomic counter (a 4-byte storage buffer) and live in extra rows of every probe image (`adaptiveRows` = half the tile rows, Lumen's default fraction; slot k at `(k % tilesX, tilesY + k / tilesX)`), so tracing, integration and history copies cover them unchanged. `SP_AdaptiveMap` (slot + 1 per sub-tile, cleared by the uniform placement) lets `ScreenProbeGatherSH` add the four nearest sub-tiles' adaptive probes (bilinear on the 8 px grid) to the uniform ones, in the resolve and in the rough reflection path. Their 64 rays are cosine-distributed (no history guides them) and the spatial filter leaves them as traced. One level only; Lumen also refines at 4 px. Measured 2026-10-10 on Sponza (Vulkan, coverage view, geometry pixels only): pixels with coverage under 0.5 fell from 5.2% to 0.8%, under 0.9 from 25.7% to 10.2%; the remainder is thin geometry (chains, foliage, mouldings) below 8 px. Placement is the same on both APIs (Cornell box: edges and corners only, far below the slot cap). Lit Sponza: GI flicker 0.12% of pixels with adaptive probes against 0.18% without, frames differing by 0.21/255 on average (99th percentile 2.8), no visible blotches; on Sponza's walls sub-tiles hold a probe only part of the time (per-frame jitter, possibly the slot cap; the counter is not read back). Cost, measured 2026-10-11 on a free RTX 4080 SUPER (Sponza, viewport 1472x841, medians of 10 snapshots, `perf_sp.py`, L2 SH): GPU frame 1.08 ms Vulkan / 1.27 ms DX12; world probes 0.27/0.31 ms, screen probes 0.34/0.38 ms of which adaptive probes 0.07/0.07 ms, reflections 0.12/0.14 ms. Scaled by pixels to 1440p, screen probes plus reflections come to roughly 1.4 ms (not measured at 1440p). Reproduced after Godot closed, with GPU users logged every 2 s (Cursor up to 35%, the Battle.net launcher up to 45%, Chrome up to 16%, all intermittent): every pass within 0.01 ms, the frame median 1.16 ms Vulkan (so read it as +-0.1). Earlier that day Godot held 80% of the GPU and every timing was noise (GPU frame 13-27 ms): check `nvidia-smi pmon` before timing.

Pitfall, skipped frames reset GI history (2026-10-11): the editor and player advance the RHI frame counter and then skip the frame when the swapchain is not ready (`Swapchain::WaitForNextFrame` timed out, which DX12's frame-latency wait does under GPU load). The GI passes reset their history when the counter jumped by more than one since their last update, so every skipped frame threw away the screen probes' guided-ray and per-pixel histories: the whole frame dimmed by 5-10% and crept back over about 2 s (Cornell box, DX12, 3-4 times per 30 grabs, 26-31% "flickering" pixels in `gi-reflections-dx12`). Adaptive probes made DX12 frames heavy enough to expose it. The world probe, screen probe and reflection passes now count scene render graph executions instead (`SceneRendererCore::GetRenderedFrames`, through `SceneRendererHost`), so only a frame that rendered without the pass breaks history: flicker 0.17% against 0.15% on Vulkan, no resets logged. Use rendered frames, not `RHI::GetFrameCounter`, for any "did I miss a frame" check.

Pitfall, L1 SH (2026-10-11): screen probes kept L1 SH, which weighs light arriving along a surface at a quarter of its value (the cosine gives none) and under-weighs light from straight ahead (0.75). Against the per-pixel reference below (Cornell box, indirect only, linear, TAA off) the floor near the camera read -13.5% and the ceiling around the lamp +20.5%; integrating each probe's bins exactly at its normal instead matched the floor to 0.0%. Lumen keeps 9 coefficients (L2; per a third-party walkthrough of UE5, the original page now gone, so unverified), and L2 tracks the exact integral: floor +1.6%, side walls -6% to -2%, the Cornell tall block +1%, the contact view's block faces within 5%, the emitter scene's wall glow +0.2% (floor near it -8%, L1 was further off). Two residuals stay, both of the probe design rather than the SH: misses read the world far-field cache, whose 16x16 texels mix the lamp with directions that escape the open front (back wall +7-9%: a 50 m-ray run still gets 5.2 of 65 through misses where the true sky is black, and nearest-texel sampling only takes it to 4.6), and a probe sitting on the lamp's thin hot edge spreads it over its footprint (ceiling +15-17%; total light over the lamp area +11% against the reference, world probes +0%). Lumen documents the same small-emissive weakness. Pool tests `gi-diffuse-reference-vulkan`/`-dx12` hold floor and side walls within 8%, back wall 13%, ceiling 22%; the `gi-noise` and `gi-screen-probes` baselines were recaptured with L2 (their probe-based references shared the L1 bias; the old ones are kept in the session scratchpad only). The cost is stability under motion: orbiting the Cornell box 0.3° per frame (Vulkan, no grid, 2026-10-11), 1.67-1.83% of pixels leave their 5-frame trend with L2 against 1.49% with band 2 dropped at evaluation (L1-equivalent) and 0.98% with GI off, at silhouettes and along the back wall's corners where per-pixel history restarts; damping band 2 would trade floor accuracy back for that.

Short-range AO (2026-10-11), kept for Lumen parity: Lumen adds a full-resolution screen-space AO and bent normal to its screen probe gather for contact detail the probes miss. Built here as 4 cosine rays per pixel per frame marching 6 steps of the depth buffer up to 2% of the screen (Lumen's default, unverified), thickness-limited, applied before the temporal average, with SSAO taken off the screen probe indirect. Against the per-pixel reference (Cornell, indirect only, linear, TAA off) it made the image worse: mean absolute error over 8 px blocks 7.3% without it, 10.0% with it, because the probes already hold crease occlusion (left wall/floor crease -4.5% without, -16% with). A second version measured the reach along the surface (range / max(view cosine, 0.2)) and applied only the pixel's AO beyond its probes' own (16 rays per probe in `normals.w`, ratio clamped to 1): the floor band in front of the short block went from +38% to +20%, but creases stayed over-dark (-18%) and the total error was 10.1%. First removed for those numbers, then restored in its first form (absolute AO and bent normal, SSAO off the screen probe indirect in `LightingPS.hlsl`) because the target is Lumen's method, not a path-traced image (the user's definition of correct): with it and the angle-checked filter the Cornell total error against the per-pixel reference is 9.5% (7.3% without), static flicker 0.02%, orbit flicker 1.81%. With both kept, the `gi-noise`, `gi-screen-probes` and `gi-cascades` baselines were recaptured (their references run the same probe pipeline) and all 24 GI and render pool tests pass on Vulkan and DX12 (2026-10-11). Why: AO treats whatever blocks a direction as black, but the Cornell walls that close a crease are lit and return about as much light as they hide, so the probes were already right there; the short block's front face is in shadow, so the floor in front of it really is darker. Matching that band needs short-range radiance (an SSGI-style gather of nearby surfaces), not occlusion. A looser adaptive-probe trigger (total weight under 0.6 instead of 0.25) did not move the band (17.0 against a reference of 12.4) or the total error (7.3%). Switching the 3x3 SH spatial filter off bounds what a Lumen-style per-direction filter (neighbour radiance reused only where its hit point is seen from the centre probe within a small angle, unverified) could recover: band 17.0 -> 15.9, total error 7.30% -> 7.07%, at ten times the flicker (0.01% -> 0.10% of pixels); the rest of the band comes from interpolating floor probes that sit further out. Built the same day and kept for Lumen parity: filtering each direction bin with a 10° hit-angle check (bins carrying their mean hit distance) took the Cornell total error to 6.91% and the ceiling halo 34.8 -> 34.0 at 0.02% flicker, but the emitter scene got worse (9.78% -> 10.02%; floor next to the emitter -8.3% -> -13.5%, pool test `gi-noise` floor_near 187 -> 182): within a bin, a neighbour ray that missed the near emitter passes the check and one that hit it does not, so the kept samples lean dark. Deciding with a hit distance smoothed over frames instead (Cornell 7.02%, emitter 9.89%, floor -12.0%) did not beat the whole-SH filter either; the per-frame form is kept, as Lumen's (unverified). Test note: `gi_screen_probes.py --baseline` still looked for the pre-cascade `ProbeFarFieldStart()` until 2026-10-11 and could not recapture; fixed then. Lumen's own screen space AO may darken creases the same way, unverified.

Pitfall, per-pixel diffuse reference (2026-10-11): judging screen probes against "every pixel traces one cosine ray a frame, averaged" (a build-tree patch of the `REFLECTIONS` raygen and resolve) read 30% darker than both probe estimators at first. The fault was the reference: a running average in the RGBA16F reflection target with weight 1/2049 rounds away the many small upward steps while the rare full-size steps from black-sky misses land, so it drifts low the longer it runs (back wall 55 after 40 s, 47 after 60 s). With a 64-frame window it is unbiased over a region: Cornell box indirect, TAA off, linear viewport capture, interior mean 32.0 for screen probes against 32.8; by region -3% (back wall), -5% (side wall), -13.5% (floor near the camera, probes darker), +20.5% (ceiling, probes brighter). Also compare in linear space with TAA off: tonemapped means of a noisy reference read low, and TAA's clamp pulls a noisy image darker. With all ray radiance forced to 1 both chains read exactly pi, so those regional gaps come from what the rays see or from interpolation, not the estimators (not yet traced).

### Reflections

[ReflectionPass](../../../Phasma/Runtime/Code/RenderPasses/ReflectionPass.cpp) (render graph `Reflections`, order 480, after `ScreenProbes`) is Lumen Reflections (roadmap step 4, [spec](../../superpowers/specs/2026-10-10-gi-reflections-design.md)); it runs with the screen probes, and, as in Unreal, the SSR pass is off while it does. [RayTrace.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/RayTracing/RayTrace.hlsl) (`REFLECTIONS` raygen) traces one GGX visible-normal ray per pixel ([ReflectionCommon.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/GlobalIllumination/ReflectionCommon.hlsl)) for pixels below roughness 0.4 (Lumen's `MaxRoughnessToTrace`), 10 km long, hits lit like the other probe rays, misses taking the sky. [ReflectionResolve.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/GlobalIllumination/ReflectionResolve.hlsl) reuses the rays of up to 8 neighbours within 1-4 px on the same surface, each weighted by this pixel's GGX lobe over the pdf it was drawn with (it regenerates their directions, nothing extra is stored); rougher pixels evaluate the screen probes' SH along the reflection direction (a cosine-wide lobe at most), with a fade over 0.3-0.4; the history follows the unjittered camera motion and averages up to 24 frames (traced) or 32 (screen probe path), clamped to this frame's ray range below roughness 0.15. `LightingPS.hlsl` multiplies it by the split-sum term in place of the cubemap specular (`cb_reflections`, set 3 binding 5; `ImageBasedLighting`'s `specularWeight`).

Pitfall, fireflies from mirrors (2026-10-10): with a mirror floor, GI rays from the walls hit its sharp highlights and the walls flickered (6.5% of pixels). Every probe-type ray (`GI_PROBES`: world probes, screen probes, reflections) now lights its hit as Lumen's surface cache does, diffuse only with the specular colour folded into the albedo (Unreal's `EnvBRDFApproxFullyRough`: + 0.45 x F0): 0.5%.

Pitfall, history blur under TAA (2026-10-10): reprojecting with the jittered previous view-projection lands every frame between pixels, so the bilinear history blurs a little more each frame (a 1000-frame reference blurred a mirror floor). All three histories (screen probe placement and resolve, reflections) move the pixel by its unjittered motion (`ScreenProbePreviousCoord`): the G-buffer velocity, which `SceneNeedsVelocityRT` now creates whenever GI runs in raster, as Lumen reprojects with velocity, or the camera motion (`sp_viewProj` from `Camera::GetProjectionNoJitter`) without it. The screen probe history's distance test allows a moving surface's own motion (its velocity beyond the camera's, in pixels, times the pixel size at that depth). Measured 2026-10-10 with the Cornell box's short block sliding every frame (node script): surface flicker (edges excluded) 0.18% with GI on against 0.02% off, on the wall the block keeps uncovering (fresh history each reveal), none on the block itself; camera-only reprojection measured the same at that speed.

Measured 2026-10-10 by pool tests `gi-reflections-vulkan`/`-dx12` (Cornell box, metal floor at roughness 0.02 / 0.3 / 0.6, editor grid hidden): the floor is 0.2 / 2.7 / 1.6 per 255 from a reference with every pixel traced, no reuse and a 1000-frame average (at 0.3 the 24-frame result reads ~9% brighter in the tonemapper's toe from residual noise; at 1000 frames it matches within 1%; an 8 px reuse radius had biased it 9%); surface flicker 0.00-0.04% against 0.00% with GI off (edges excluded: TAA flickers them with or without GI); the floor mirrors the red wall (R 57 vs G 1; black before). Sponza cost (two runs, viewport 1472x841, half-resolution tracing): 0.07 ms Vulkan / 0.09 ms DX12; per-pixel tracing could not be measured cleanly (another process held a third of the GPU; DX12 read 1.75 ms against Vulkan 0.14-0.21, to recheck). Memory at 1440p: three RGBA16F full-resolution targets, 88 MB. Not done: screen-space traces first, hit-distance reprojection for mirrors, specular occlusion, reflections on translucency.

### Resident Cluster Geometry

[ClusterGeometry.cpp](../../../Phasma/Runtime/Code/Scene/ClusterGeometry.cpp) uses meshoptimizer v1.3's maintained [clusterlod.h](https://github.com/zeux/meshoptimizer/blob/v1.3/demo/clusterlod.h), including position/normal/UV/colour attributes, to build clusters of at most 128 triangles and a refinement hierarchy. [ModelAssetCooked.cpp](../../../Phasma/Runtime/Code/Scene/ModelAssetCooked.cpp) writes bounds, simplification errors, refinement links and cluster indices in `.pemesh` v8 only when requested: `PhasmaCook source output --clusters`, `PhasmaCook --batch manifest --clusters`, or the editor's Cook Cluster Geometry checkbox. Default cooking remains v7 without cluster generation. Versions 3–7 build a hierarchy only when the scene enables clusters. Cluster payloads are range checked and reject nonfinite bounds/errors and invalid refinement links. Re-saving a model without `--clusters` (Animator timeline save, rig bake) keeps each hierarchy that still validates against its mesh and drops it when the mesh became skinned, non-opaque or changed vertex count, because the reader rejects the whole file when a skinned mesh carries clusters; the file is v8 only while some mesh keeps a hierarchy. No automated check covers this path (no headless re-save; verified by build and review 2026-10-07).

[Scene](../../../Phasma/Runtime/Code/Scene/Scene.cpp) builds/uploads resident cluster metadata and extra indices only while the scene enables clusters. `Scene::UpdateClusterGeometry` rebuilds the store on every full geometry upload: meshes that share a geometry range (instances) share one uploaded hierarchy, deleted meshes drop out, and generated hierarchies are cached by `{vertexOffset, vertexCount, indexOffset, indexCount}` because the geometry stores are append-only until the scene clears. Before 2026-10-07 every instance appended its own copy and deleted meshes kept theirs while clusters were on; pool test `cluster-instances-vulkan` checks that ten sphere instances and spawn/delete churn keep the one-sphere size (1,984 bytes). With the feature off, the cluster binding has a 64-byte placeholder and indirect capacity follows normal meshes; disabling it releases cluster CPU storage and recreates GPU geometry/indirect buffers without the extra data. Allocator pools can retain freed GPU memory. [CullingCS.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/Compute/CullingCS.hlsl) assigns one workgroup to each instance while cluster rendering is enabled, spreads cluster selection across 64 threads, and selects a consistent hierarchy cut by projected pixel error. Bounds conservatively cover nonuniform scale and shear. Frustum/Hi-Z tests emit ordinary indexed indirect draws, including both depth phases; depth, G-buffer and [object-ID perception](../../../Phasma/Runtime/Code/Render/ScenePerception.cpp) draw limits use expanded indirect capacity. The original geometry remains available for shadows and BLAS.

Controls are `cluster_geometry` (default false) and `cluster_error_pixels` (1 pixel). The path handles static opaque meshes. Skinned, alpha-cut, blended, terrain and voxel geometry retain their existing paths. All hierarchy/index data stays resident; there is no imported-mesh page streaming, visibility-buffer material resolve, software rasterizer or mesh-shader dependency. A GPU memory budget and demand paging are required before treating it as virtualized geometry for assets larger than VRAM. Vulkan still advertises `caps.meshShaders=false`.

Local checks cover hierarchy selection (7,938 to 122 triangles on a curved test mesh), malformed payload rejection, opt-in v8/default v7 cooking, object-ID coverage, off/on/off allocation sizes and Vulkan/DX12 frustum-only and two-phase Hi-Z culling. Small scenes can spend more time on cluster selection and draw setup than they save in rasterization; profile before enabling it.

Sponza Release comparisons on an RTX 4080 SUPER use immediate presentation and ten snapshots one second apart. Fresh feature-off controls against the fixed original LDR baseline changed FPS -0.3% on Vulkan and -0.1% on DX12, GPU time -0.058/-0.039 ms and application VRAM +14/0 MB, within the project thresholds. A separate cluster-only off/on/off run, with no preceding HDR allocations, added 11/13 MB application VRAM and 11.7/14.8 MiB resident buffers. This includes about 5.0 MiB of extra indices, 0.25 MiB of metadata and expanded indirect/storage buffers. First activation on legacy v7 Sponza assets took 313/328 ms from the setting request to visible uploaded metadata, including CPU generation, GPU buffer rebuilding and frame/MCP scheduling. `Scene::UpdateClusterGeometry` has a CPU profiler scope. Disabling restored the initial application VRAM and buffer sizes. Earlier cluster comparisons had included those allocations in the disabled baseline and understated their cost. Verified 2026-10-07.

### HDR Boundary

[SceneRenderTargets.cpp](../../../Phasma/Runtime/Code/Render/SceneRenderTargets.cpp) uses RGBA8 by default. The saved/Lua `hdr` setting defaults to false; hardware-RT GI also activates HDR so indirect radiance is preserved. In HDR, lighting, emissive, TAA history and bloom use RGBA16F. [SceneRenderGraph.cpp](../../../Phasma/Runtime/Code/Render/SceneRenderGraph.cpp) orders TAA or upsampling, bloom, DOF and motion blur before [TonemapPass.cpp](../../../Phasma/Runtime/Code/RenderPasses/TonemapPass.cpp), which converts to RGBA8. RCAS, FXAA, colour grading and overlays run afterwards. The conversion pass also runs with ACES disabled; disabling tone mapping changes the curve, while display conversion remains necessary. TAA history is copied before bloom and tone mapping; RCAS receives tone-mapped values. Live HDR changes resize targets and rebuild format-dependent pipelines and graph order on both hosts. LDR retains its previous pass order and allocation formats.

The [Player](../../../Phasma/Runtime/Code/Render/RuntimeSceneRenderer.cpp) defers LDR bloom and colour grading until after runtime UI, preserving existing HUD bloom. HDR scene bloom runs before tone mapping and UI; only colour grading is deferred. Player checks verify this distinction on Vulkan/DX12. RGBA8 lighting clips radiance above 1.0 before ACES; opt-in HDR range checks distinguish emissive 2 from 4 with TAA/RCAS on and off. The display image is retained across same-size HDR changes, and target creation uses exact names so the LDR `hdrDisplay` lookup fallback cannot substitute an RGBA8 allocation. Pipeline refresh preserves compute descriptors that do not depend on scene colour. A Vulkan saved-Sponza check covers uncached TAA compilation and HDR switches without validation instrumentation. Verified 2026-10-07.

RGBA16F doubles per-pixel storage for converted images; GI has additional caches/history. Against the fixed original LDR Sponza baseline, optional HDR changed FPS -5.2%/-4.4% and application VRAM +96/+128 MB on Vulkan/DX12. GI with clusters and HDR changed FPS -14.3%/-14.0% and VRAM +125/+158 MB; these are total enabled-path costs, not GI alone. Optional paths exceed the default regression budgets. Several DX12 runs, including cold feature-off controls, contained a two-second stall inside `Present`; failed raw captures were retained, and complete ten-snapshot controls were repeated rather than trimming samples. The fresh controls above passed. These numbers are scene/hardware specific; Android HDR/GI and in-game bloom remain unverified. Verified 2026-10-07.

### Linear Colour

Without `linear_color` nothing decodes sRGB colour inputs or encodes the image: albedo is lit as stored bytes, the sky is linear, and the UNORM display target goes to the UNORM swapchain unchanged (survey 2026-10-10). The per-scene `linear_color` setting (default false; saved, Lua, a Pipeline-panel checkbox next to HDR) follows Unreal's model and forces HDR scene colour ([SceneRenderTargets.cpp](../../../Phasma/Runtime/Code/Render/SceneRenderTargets.cpp) `SceneUsesHDR`, `SceneUsesLinearColor`, `SceneColor`). Spec and plan: [design](../../superpowers/specs/2026-10-10-linear-color-design.md), [plan](../../superpowers/plans/2026-10-10-linear-color.md).

- Textures: RGBA8/BGRA8/BC1/2/3/7 UNORM images are created with `mutableFormat` (Vulkan `MUTABLE_FORMAT | EXTENDED_USAGE`, DX12 typeless resource) and `Image::GetSrgbSRV` makes a second, sample-only sRGB view ([Image.cpp](../../../Phasma/Core/Code/API/Image.cpp), [VulkanImageViewImpl.cpp](../../../Phasma/Core/Code/API/Vulkan/VulkanImageViewImpl.cpp), [Dx12ImageImpl.cpp](../../../Phasma/Core/Code/API/DX12/Dx12ImageImpl.cpp)). `Scene::UpdateImageViews` keys the bindless table by view and gives base colour (slot 0) and emissive (slot 4) the sRGB view when the scene is linear ([SceneBuffers.cpp](../../../Phasma/Runtime/Code/Scene/SceneBuffers.cpp) `MaterialSlotView`); raster, ray-traced and GI probe hits share that table. Named textures of custom passes keep the UNORM view. Mips stay averaged in encoded space.
- Authored colours (material factors, vertex colours, light colours in `UpdateLights`, sprite tints, lines, AABBs, selection outline, fallback sky) stay stored as picked (sRGB) and are decoded where they enter the frame; values above 1 keep their brightness (`SrgbToLinearHdr`: the colour over its largest channel is decoded, then scaled back).
- The 8-bit G-buffer albedo is stored sRGB-encoded (`GBufferPS`, terrain, voxel) and decoded by `LightingPS` and `SSRPS`, as Unreal's sRGB GBufferC; emissive goes linear into the RGBA16F target.
- `TonemapPS` ends with the single `LinearToSrgb`; Sharpen, FXAA, colour grading, grid, particles, runtime UI and ImGui stay after it on display values. Terrain layers, skyboxes and the voxel atlas were already linear and are unchanged.
- Toggling rebuilds the table (`m_linearColorViews` in `Scene::Update`), reloads the sky only while the solid fallback shows (`SceneSkyIsFallback`) and repacks lights, which restarts GI averaging. In a linear scene every resident colour texture's sRGB view is also in the table (`Image::CanSampleAsSrgb`), so `TryBindCachedTexture` hits for sprite and material swaps instead of forcing a texture rebuild. Vertex colour and base-colour factor are decoded separately (the sRGB curve does not distribute over a product). Lua `create_image` colour images are mutable too.
- Mutable colour images are typeless resources on DX12: `Dx12BlitImage` and `Dx12ImageImpl::Blit` compare and build pipelines from the typed view format. Open (2026-10-10): `MUTABLE_FORMAT` on every colour texture may disable compression on some drivers (AMD DCC, Mali AFBC) even with the switch off; only an RTX 4080 SUPER was measured, and a `VkImageFormatListCreateInfo` limited to the UNORM/sRGB pair would keep it on but would break WebGPU textures that declare other view formats. WebGPU textures with extra view formats also become typeless on DX12; the WebGPU suites were not run.

Pitfalls: scene render targets had no transfer-source usage until 2026-10-14, so `capture_image_resource` could not read `rt:emissive`/`rt:normal` on Vulkan; `CreateSceneRenderTarget` now adds `TRANSFER_SRC` to every colour target. `take_scene_screenshot` `target: viewport` returns `rt:viewport`, the scene colour before Tonemap. The pool test reads `rt:display` cropped to the `Viewport` panel from `query_imgui_windows` (window origin = `##MainMenuBar` corner). Normal maps on primitives render black (no tangents) with or without linear colour (2026-10-10).

Verified 2026-10-10 by pool tests `linear-color-vulkan`/`-dx12`: emissive colours, an HDR emissive (G/B 158/80 at factor 1.6, 0.8, 0.4) and an sRGB-128 emissive texture show as authored across on/off toggles; a lit plane matches values derived from off mode within 2/255; a base-colour texture equals the decoded factor while a metallic-roughness texture is not decoded; a (1, 0.5, 0.25) point light decodes to G/R 0.214; GI bounce is brighter once encoded; with the switch off, Sponza and a mixed scene match the pre-change binary byte for byte at the scene-colour target. Cost on an RTX 4080 SUPER, Sponza editor, immediate present, medians of 10 snapshots in both run orders: linear on versus `hdr` on changed the G-buffer pass by 0.000 ms (Vulkan) / -0.002 to -0.009 ms (DX12), the whole GPU frame by +0.000 to +0.003 ms, Tonemap by +0.001 ms; mutable/typeless colour textures with the switch off changed the frame by -0.001 ms (Vulkan) / +0.003 ms (DX12). Editor FPS at these rates varied 546-746 between identical runs, so the first spike-skewed average (-6.3%) was not a regression.

Published architecture references: [Lumen Technical Details](https://dev.epicgames.com/documentation/en-us/unreal-engine/lumen-technical-details-in-unreal-engine), [Lumen SIGGRAPH 2022](https://advances.realtimerendering.com/s2022/SIGGRAPH2022-Advances-Lumen-Wright%20et%20al.pdf), [Nanite Technical Details](https://dev.epicgames.com/documentation/en-us/unreal-engine/nanite-technical-details) and [Nanite SIGGRAPH 2021](https://advances.realtimerendering.com/s2021/Karis_Nanite_SIGGRAPH_Advances_2021_final.pdf).

Phase 1 representation and evaluation (source verified 2026-10-14):

- **Visibility payload and caps gate.** The depth and late prepasses write RGBA32_UINT `(drawId + 1, v0, v1, v2)`, with three global vertex indices obtained through `GetAttributeAtVertex`. Zero denotes a legacy or uncovered surface; terrain and voxels clear it where they win depth. `SceneUsesOpenPBR()` requires the switch, desktop, fragment barycentrics, compute quad derivatives and at least seven colour attachments; unsupported paths warn once and use legacy rendering. See [VisibilityPS.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/Depth/VisibilityPS.hlsl) and [SceneRenderTargets.cpp](../../../Phasma/Runtime/Code/Render/SceneRenderTargets.cpp).
- **Base vertex.** Vulkan's vertex index already includes the base vertex. DX12's `SV_VertexID` excludes it, so the visibility variant adds `IndirectAll[drawId].vertexOffset`; the default DepthVS variant is unchanged. See [DepthVS.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/Depth/DepthVS.hlsl).
- **Quad-exact evaluation and tangent fallback.** Four compute lanes evaluate one pixel's triangle at their own aligned 2×2 quad pixel centres, including extrapolated helper lanes. Perspective-correct weights come straight from clip space (`PeClipBarycentrics`: b ∝ cross(x − pₓw, y − p_yw), no per-vertex 1/w), so vertices on or behind the camera plane stay finite; quad derivatives drive implicit texture LOD. The material passes never write a non-finite result over the raster value (fixed 2026-10-14; `check_camera_plane_reconstruction` puts a vertex at w = 0: the old per-vertex divide gave NaN). `PeSurfaceAt` derives dP/du when stored tangents are zero and chooses a tangent perpendicular to the normal if UVs are degenerate. The Sponza reconstruction and voxel-occluder gates pass on both APIs, including the LOD/cluster/two-phase Hi-Z combinations. See [VisibilityCommon.slang](../../../Phasma/Runtime/RuntimeAssets/Shaders/MaterialX/VisibilityCommon.slang), [VisibilityDebug.slang](../../../Phasma/Runtime/RuntimeAssets/Shaders/MaterialX/VisibilityDebug.slang) and `.testpool/tests/openpbr_vis.py`.
- **Override layout.** MaterialX library includes are root-relative (`libraries/...`): overrides live under `pe_overrides/libraries/...`, and the search path is `pe_overrides`, then the MaterialX root containing `libraries/`, then the material document's folder. Registering `libraries/` itself fails with `Could not find include file: 'libraries\stdlib\genslang\lib\mx_math.slang'`. See [MaterialXGen.cpp](../../../Phasma/Cook/Code/MaterialX/MaterialXGen.cpp).
- **DX12 limits that shape the resolve shaders:** four descriptor spaces (`DX12_DESCRIPTOR_SPACE_COUNT`), one-line `[[vk::binding]]` declarations (the register rewrite and the reflection regex are per line), quoted `#include` only (no Slang `import`). A missing descriptor binding logs `[Descriptor] Binding N not found`, so resolve passes guard every write with `HasBinding`.
- **Packed raster inputs must stay live (source verified 2026-10-18).** [Reflection.cpp](../../../Phasma/Core/Code/API/Reflection.cpp) derives binding stride and attribute offsets from reflected inputs. Storage-buffer attribute loads can let optimization remove POSITION or UV from the 52-byte depth stream, shifting the remaining fields. [MaterialMaskVS.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/MaterialX/MaterialMaskVS.hlsl) therefore uses raster POSITION and UV directly while loading the other attributes from storage. The pinned Slang compiler requires the mask's `GetAttributeAtVertex` reads at the actual pixel entry point; passing plain vertex IDs into surface helpers avoids its `ResolveVaryingInputRef` lowering failure.
- **Depth alpha constants need scalar-edit refresh (verified 2026-10-18 on Vulkan and DX12).** The `Mesh_Constants` prefix contains `alphaCut` and `baseColorAlpha`; refreshing only `MaterialGpuData` leaves depth coverage stale after alpha or cutoff edits. A disabled MaterialX instance can report alpha 1 while its legacy depth remains invisible until a texture change rebuilds constants. [SceneBuffers.cpp](../../../Phasma/Runtime/Code/Scene/SceneBuffers.cpp) refreshes the eight-byte prefix in the existing dirty-material node/reference loop, before parent dirty flags clear, using each reference's indirect slot. Unchanged values skip the upload and DX12 mirror; changed values also synchronize fragment-shader reads. `.testpool/tests/material_alpha_constants.py` reproduced the failure before the fix and passes both APIs after the Release rebuild, including repeated alpha/cutoff restores without texture rebinding. Full generated-mask acceptance remains pending.
- **Mask shadow gates must keep cell edges off the shadow-sample grid (diagnosed 2026-10-19).** Bilinear opacity is exactly 0.5 on a checker cell boundary, and the cutoff test keeps it (`opacity >= alphaCut`, as in DepthPS). The physical quads that serve as the reference follow raster fill rules instead. So wherever a shadow-map sample lands on a boundary, the two references resolve the tie differently. In `openpbr_mask.py`'s sprite-shadow case, cascade 1 (radius 12.75 m, 12.45 mm texels) put the x = 0.75 boundary 0.015 texel from a sample. Cutoff 0.5 then differed at one corner (3/255 on 2 pixels, on both APIs). Cutoff 0.51 flipped the tie along the whole edge (149 pixels, up to 44/255). The fixture shifts the sprite and the physical checker together in x (`SPRITE_SHADOW_SHIFT_X` in `.testpool/tests/openpbr_mask_cases.py`). On the old camera-following grid, −3.3 mm kept every inner boundary at least 0.2 texel from a sample, and the full masks gate passed on DX12 and the sprite, attribute, fallback and frame groups on Vulkan. On the world-fixed grid (below), −3.3 mm left x = +0.75 only 0.095 texel from a sample, so the shift is now −5.2 mm. That puts the x boundaries at 0.388/0.205/0.203 texel and the y boundaries at 0.265/0.5, read back from the cascade-1 matrix in `Shadows_uniform_buffer` (2026-10-19). With a 45° sun and 0.75 m cells, no x shift gets past 0.204 texel. The sprites group then passed on Vulkan and DX12 with 0 differing pixels and clean logs. The grid no longer depends on where the camera is or which way it faces. The sun direction, `shadow_map_size`, and anything that changes a cascade's radius (FOV, aspect, near plane, split lambda, `shadow_distance`) still move it, so a new fixture needs the same check.
- **Cascade texel snap (fixed 2026-10-19).** [ShadowPass.cpp](../../../Phasma/Runtime/Code/RenderPasses/ShadowPass.cpp) `CalculateCascades` used to snap the frustum centre in a light view built around that same centre. The centre is always x = y = 0 in that view, so the `floor` did nothing and the shadow-texel grid followed the camera. It now snaps in a rotation-only light view, `lookAt(0, lightDir, lightUp)`, whose origin is fixed in world space. `texelSizeWorld` is unchanged, so `GetCascadeTexelSizeWorld` and the shadow normal bias still match.
  - **Grid stays fixed.** Verified on saved Sponza (Release, RTX 4080 SUPER, Vulkan and DX12) by reading the cascade matrices back from `Shadows_uniform_buffer`. The saved file has shadows off, so the test added a scene-settings node and turned shadows on. It also turned TAA off and rotated the sun to [−55, 30, 0], and kept the scene's 1024 map, 3 cascades and 0.005 near plane. Over eight quarter-texel camera steps across the sun, plus a 0.0005 rad yaw, every cascade's world origin stayed within 0.0001 texel of a texel corner. Before the fix, cascade 0's phase drifted 0.25 texel per step.
  - **Shimmer gone.** A near-plane nudge (+0.0005 per step) moves the cascade centres by fractions of a texel without moving the view. Before the fix, 145–278 shadow-edge pixels changed by more than 2/255 (up to 28/255). After it, 0–1 pixels changed until the 1/16 m radius rounding stepped once. That step changed about 330 pixels, as expected: a new radius means a new texel size.
  - **Perf neutral.** The shadow passes held at 0.098–0.105 ms. Frame totals stayed within run-to-run noise across three Release Sponza A/B pairs.

- **Sprite time must advance once per RHI frame (diagnosed 2026-10-18).** [RendererSystem.cpp](../../../Phasma/Editor/Code/Systems/RendererSystem.cpp) can call `Scene::Update()` again for late script mutations. Advancing the full frame delta on both calls doubles sprite playback: a fresh fixture advanced 10.774 seconds within at most 5.781 seconds of wall time, while a control taking only the regular update advanced normally. - **A reloaded sprite must re-apply its saved frame (fixed 2026-10-19).** Scene load rebuilds a sprite quad from its primitive source with full-texture UVs. `RestoreSpriteNode` in [SceneSerializer.cpp](../../../Phasma/Runtime/Code/Scene/SceneSerializer.cpp) restored `frameIndex` and `uvRect` without applying them. `ApplySpriteFrame` in [SceneSprite.cpp](../../../Phasma/Runtime/Code/Scene/SceneSprite.cpp) skips a frame whose rect already matches the stored state, so even `set_frame` to the saved frame left the whole atlas on screen. This affected legacy and generated materials alike. `RestoreSpriteNode` now applies the saved rect and a zero frame blend to the quad, which covers scene load, prefabs and the undo and play/stop snapshot restores. The local pool tests `sprite-reload-frame` and `sprite-reload-frame-dx12` (`.testpool/tests/sprite_reload_frame.py`) failed at 255/255 without the fix and pass on both APIs with it. - **PE primitives store zero tangents.** Normalising them is NaN in MaterialX's tangent frame; the resolve derives the UV tangent dP/du, as MaterialX's own mesh loader does.
- **Black limb pixels on faceted meshes: MaterialX flips, PE bends.** Where an interpolated smooth normal faces away from the viewer (N.V < 0 on a front-facing facet, the silhouette ring of a low-poly sphere), every MaterialX BSDF flips it with `mx_forward_facing_normal`, so a top-lit limb normal ends up facing away from its light and the pixel shades black. MaterialX's own `GlslRenderer` produces the same pixels: for the default sphere (640x342, front light) all 84 pixels with float64 N.V < 0 are black in the reference, and PE's black set agreed once the projection used PE's window aspect (2560/1369; the harness reference uses 640/342, a 0.1 px shift that moves about 20 ring pixels). The legacy pipeline has no such pixels (unflipped N.L). A renderer that wants a lit limb bends the normal just enough to face the eye instead, so pass 2 does: `PeBendLimbNormal` ([VisibilityCommon.slang](../../../Phasma/Runtime/RuntimeAssets/Shaders/MaterialX/VisibilityCommon.slang)) raises N.V to 0.01 when the facet faces the eye (the facet normal oriented like the shading normal has positive N.V) and re-orthogonalises T and B. The back face of a double-sided mesh keeps MaterialX's flip, and pass 1's G-buffer normal stays the interpolated one, as the legacy G-buffer's. The only pixels that differ from MaterialX are the artifact pixels (about 80 per sphere, inside the parity harness's 3 px rim). `openpbr_parity.py` counts black pixels on the lit default sphere's 2 px silhouette ring and must find 0 (86 before the bend, 0 after on Vulkan, 2026-10-15). Found by marking pass 2's early-outs and N.V in a build-tree copy of `MaterialShade.slang` (no NaN, no `vis == 0`, no zero colour at these pixels) and a float64 replay of the sphere mesh.
- **Old cooks carry skin weight 1 on static meshes.** Before `eaa05195` (2026-09-06) the cook gave every boneless vertex weight 1. Visibility eligibility therefore copies DepthVS's skinning test (`pc.jointsCount > 0 && weightSum > 0`), not the weights alone. Weights alone gave a Sponza cooked 2026-07-19 0% visibility coverage (found 2026-10-13, `DepthVS.hlsl`).
- **Pass `Update()` runs in parallel.** `UpdateSceneRenderGraphPassComponents` runs every pass's `Update` on `ThreadPool::Update` at once (`SceneRenderGraph.cpp`), so a pass must not read another pass's members that the other rewrites in its `Update` (for example LightOpaque's shadow fallbacks, which `EnsureLightShadowFallbackResources` reassigns). `MaterialShadePass` owns its own fallbacks for that reason; data set only in `Init` is safe to share (found by review 2026-10-14).
- **Quad-exact compute is not bit-exact against raster on textured surfaces.** Under the default 16× anisotropic sampler, about 1e-4 of Sponza pixels differ by 2–6/255 on Vulkan and DX12, and about 10% differ by exactly 1/255. With anisotropy off, 2 pixels differ by 2/255. Textured identity gates must therefore be fraction-based (`openpbr_vis.py` `assert_reconstruction`), not `max ≤ 1` (measured 2026-10-13).

Phase 3.1a modules (source verified 2026-10-16; [contract](../../superpowers/plans/2026-10-16-openpbr-phase3.md)):

- **Registry and generation.** A module owns generated code and its validated byte layout, keyed by the FNV-1a hash of the generated Slang text. Index 0 remains build-time `PeOpenPBRDefault`, with its additional pinned 37-input / 220-byte / thin check. A material source is a `.mtlx` path (relative paths resolve like any asset, `Path::ResolveAsset`) plus material name and retains its own JSON defaults: identical code shares pipelines without sharing values. Live import runs `PhasmaCook --mtlx <document> <tempOutDir>` beside the executable through `RunProcess` with a 60-second timeout, then writes the cooked source under the project's `Assets/MaterialX/Cooked/` (3.3b below). Source/content mappings, including failures, last one process. Generation/load failures, matrix and string inputs fail with an `[OpenPBR]` Lua diagnostic and one warning naming the document. See [OpenPBRMaterial.cpp](../../../Phasma/Runtime/Code/Scene/OpenPBRMaterial.cpp) (`ReadLayout`, `Registry`, `GenerateSource`, `LoadOpenPBRMaterial`).
- **Names, types and Lua.** `material.use_mtlx(node, path, materialName)` enables the source on that material instance; `material.use_openpbr(node, true)` selects the default module again. `set_openpbr` / `get_openpbr` use qualified identities such as `gate_glow.in2`; bare names alias only the OpenPBR surface's own inputs. Overrides are stored under qualified names. Bool, integer, float and float2/3/4 retain their types through parsing, Lua, resolution and packing. Legacy mirrors read that instance's source values; a connected input leaves its legacy field unchanged. These assignments and values persist through the scene JSON (3.3a below). See [MaterialBindings.cpp](../../../Phasma/Runtime/Code/Script/Bindings/Material/MaterialBindings.cpp) and [Material.cpp](../../../Phasma/Runtime/Code/Scene/Material.cpp). `use_mtlx`, `use_openpbr` and `set_openpbr` return no Lua values; errors raise, so rejection tests use `pcall` rather than asserting a returned boolean (source verified 2026-10-17).
- **Wrappers and pipeline lifetime.** The default wrappers and cached `<hash>.thin.slang` / `<hash>.shade.slang` include a pass head, generated module and pass main. Cached wrappers use absolute paths with forward slashes. [ShaderCache.cpp](../../../Phasma/Core/Code/API/ShaderCache.cpp) (`ParseShader`, `Init`) expands those includes and hashes the expanded text, so module code changes the cache key. [SceneRendererCore.cpp](../../../Phasma/Runtime/Code/Render/SceneRendererCore.cpp) reconciles both passes every frame with `Scene::GetOpenPBRModules()`, the modules the material byte packing last wrote records for (so a module change takes effect through the forced repack; nothing scans the scene per frame). Each pass dispatches each module once, indirectly, over the tiles MaterialThin binned for it (see Tile binning below); `GetPassInfos` exposes all pipelines, and reload retains each `PassInfo` object. Hot reload watches wrapper files, not their included files. See [MaterialThinPass.cpp](../../../Phasma/Runtime/Code/RenderPasses/MaterialThinPass.cpp), [LightPass.cpp](../../../Phasma/Runtime/Code/RenderPasses/LightPass.cpp) and [MaterialShadeHead.slang](../../../Phasma/Runtime/RuntimeAssets/Shaders/MaterialX/MaterialShadeHead.slang).
- **Tile binning (2026-10-19).** Before, each module's pass 1 and pass 2 dispatched over the whole visibility buffer (2x resolution, 8x8 groups) and early-outed off its pixels, so every graph cost a full-screen pass. Now `MaterialThinPass::ExecutePass` first runs [MaterialClassify.slang](../../../Phasma/Runtime/RuntimeAssets/Shaders/MaterialX/MaterialClassify.slang): one 8x8 group per 8x8-pixel tile reads each pixel's module (`PeModuleOf`), maps it to a bin through a per-frame module-to-bin table (bin = position in `Scene::GetOpenPBRModules()`), and the first thread holding each bin (a groupshared first-occurrence scan, so wave size does not matter) appends the tile once. A bin is `uint4(groups x, groups y, 1, tile count)` then its packed tiles, all in one GPU buffer (`MaterialClassify_bins`) that `SyncBins` sizes on the main thread before the passes' parallel `Update`. Both passes then run `CommandBuffer::DispatchIndirect` per module ([Command.cpp](../../../Phasma/Core/Code/API/Command.cpp); Vulkan `vkCmdDispatchIndirect`, D3D12 `ExecuteIndirect` with a dispatch command signature), four 8x8-thread groups per tile, and `PeBinThread` turns each group back into the full-screen dispatch's thread IDs, so quads, lanes and per-pixel maths are unchanged. MaterialShade reads MaterialThin's bins (both are enabled by the same condition) and skips when they were not filled this frame (`MaterialThinPass::BinsReady`). Pitfalls: D3D12 caps a dispatch at 65,535 groups per dimension (also Vulkan's guaranteed minimum; NVIDIA's Vulkan driver allows far more, so a one-row grid of 4 groups per tile passes there and breaks on D3D12 past about 16k tiles), hence rows of 64 tiles (`PE_BIN_ROW_TILES`); `FillBuffer` zeroes every arguments word, so the classify dispatch rewrites x and z itself; and the bins hold 4 bytes per tile per module (121 KiB per module at a 1920x1026 viewport, 506 KiB at 4K), marked `ponytail:` in `SyncBins` with the count / prefix-sum / scatter upgrade. Phase 3.2 textures (source verified 2026-10-16; [contract](../../superpowers/plans/2026-10-16-openpbr-phase3.md)):

- **Files belong to the material.** PhasmaCook writes each image input's filename into the `.json` (`"file"`, resolved the MaterialX way: next to the document, `fileprefix` honoured, made absolute) and `[0]` for int inputs MaterialX leaves empty (`layer`, `framerange`). A material source loads its own images (`OpenPBRMaterialSource::textures`, keyed by input identity), never the shared layout, so documents with identical code share pipelines and sample their own files. A file that does not load fails the source (`use_mtlx` raises the `[OpenPBR]` error naming the image). See `JsonFile` in [MaterialXGen.cpp](../../../Phasma/Cook/Code/MaterialX/MaterialXGen.cpp) and `LoadSourceImages` in [OpenPBRMaterial.cpp](../../../Phasma/Runtime/Code/Scene/OpenPBRMaterial.cpp).
- **Raw views, MaterialX's colour transform.** An image tagged `srgb_texture` gets MaterialX's own `srgb_texture -> lin_rec709` node after the sample, so textures join the scene's image-view table (`Scene::CollectOpenPBRImages`, before `UpdateImageViews`) as raw (UNORM) views in both `linear_color` modes; `BuildOpenPBRBytes` packs the raw view's table index. The table grows to the device limit (see Scene Texture Table): a source that would exceed `caps.maxBindlessTextures` is refused, and past a full table later views sample white. See [SceneBuffers.cpp](../../../Phasma/Runtime/Code/Scene/SceneBuffers.cpp).
- **Texture reference contract (verified 2026-10-17).** Legacy base-colour sampling uses an sRGB view under `linear_color`, decoding before filtering; MaterialX samples UNORM then decodes. Flat texels agree, but interpolated colour boundaries can differ substantially (48/255 in the sprite atlas gate). Compare generated sprite endpoints against the same MaterialX graph on rigid geometry, then blend those evaluated linear inputs for intermediate frames. Keep legacy off/fallback identity as a separate check; do not change MaterialX's filtering to satisfy a legacy-image reference. Sources: `MaterialSlotView` in [SceneBuffers.cpp](../../../Phasma/Runtime/Code/Scene/SceneBuffers.cpp), `BuildOpenPBRBytes` in [OpenPBRMaterial.cpp](../../../Phasma/Runtime/Code/Scene/OpenPBRMaterial.cpp), and the generated image/color-management call order from [MaterialXGen.cpp](../../../Phasma/Cook/Code/MaterialX/MaterialXGen.cpp).
- **Samplers.** `samplerIndex` picks one of 18 fixed samplers (`Scene::CreateOpenPBRSamplers`): u and v address mode {clamp, periodic, mirror} x filter {closest, linear}, linear with the scene sampler's mips and anisotropy. Limits: MaterialX's `constant` address mode samples as clamp and `cubic` as linear.
- **Bindings.** DX12 gives a resource binding N register N and an array N..N+size-1 (`Dx12ShaderImpl.cpp:566`, `Dx12DescriptorImpl.cpp:419`), and an unbounded array must be its set's last binding. Pass 1: `pe_textures[]` alone in set 1, `pe_samplers[18]` at set 0 b9 (s9-s26). Pass 2 holds `pe_textures[]` alone in set 2 (the shared scene texture table, see [Scene Texture Table](#scene-texture-table)) and puts the rest above `ProbeVolume.hlsl`'s set-3 bindings 0-5: its own fog cube `pe_fogCube` (b6: t6/s6, the skybox cube LightingPS keeps in its set 2), the environment sampler (b7: s7), `pe_samplers[18]` (b8: s8-s25) and the environment textures (b9/b10). A space's DX12 sampler table spans s0 to its highest register, so single samplers go below the array; set 3 rather than set 0 (bindings 0-20 taken) keeps that growth to 2 sampler slots per graph per frame (derived 2026-10-18 from the table sizing in [Dx12DescriptorImpl.cpp](../../../Phasma/Core/Code/API/DX12/Dx12DescriptorImpl.cpp), not measured). See [MaterialShadeHead.slang](../../../Phasma/Runtime/RuntimeAssets/Shaders/MaterialX/MaterialShadeHead.slang) and [MaterialThinHead.slang](../../../Phasma/Runtime/RuntimeAssets/Shaders/MaterialX/MaterialThinHead.slang).
- **Pitfall: the reference's bitangent.** MaterialX's OBJ loader builds the bitangent as `cross(N, T)` without handedness (MaterialXRender `Mesh.cpp:190`, `generateBitangents`); PE follows the UV handedness (mikktspace / glTF convention, `PeSurfaceAt`). On a mesh with left-handed UVs (the gate plane: u +X, v +Z, N +Y) a normal map's green channel therefore tilts the opposite way in `GlslRenderer`. Measured 2026-10-16: PE vs the reference worst 68/255 in the map's green-tilted corner only; vs a reference given the green-flipped map worst 3/255 at texel edges. `openpbr_textures.py` hands the reference the flipped map (`REFERENCE_DOCS`).
- **Parity.** `.testpool/tests/openpbr_textures.py`: asymmetric images, magnified texels, a same-code / different-image pair in one frame, a missing image refused, pass-1 readback of each image's flat centre block. Texel-edge pixels differ from OpenGL's bilinear by up to 3/255 (5 display-referred), so textured cases have their own measured limits (`TEXTURE_TOLERANCE`).

OpenPBR environment resources (source verified 2026-10-15): [Skybox.cpp](../../../Phasma/Runtime/Code/Skybox/Skybox.cpp) builds, only while `SceneUsesOpenPBR()` is true, an RGBA32F **lat-long radiance pyramid** (the kind of map MaterialX's FIS was written for) and a 128x64 lat-long irradiance map. [OpenPBREnvPyramid.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/Compute/OpenPBREnvPyramid.hlsl) writes each mip as the plain average of the mip-0 texels it covers, what `glGenerateMipmap` gives MaterialX; mip 0 is the sky's own HDR equirect when the load had one (width <= 4096), else the legacy cube resampled to 4F x 2F (`PE_ENV_FROM_CUBE`: six-face and solid-colour skies, wider HDRs). [OpenPBREnvIrradiance.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/Compute/OpenPBREnvIrradiance.hlsl) integrates `max(dot(N, w), 0) * dOmega / pi` over the pyramid's 256x128 mip, MaterialX's radiance-equivalent convention. Both images use PE's equirect convention (`u = atan2(z, x) / 2pi + 0.5`, `v = 0.5 - asin(y) / pi`, [EquirectangularToCubemap.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/Compute/EquirectangularToCubemap.hlsl)), which is MaterialX's rotated a quarter turn. Turning OpenPBR on reloads the sky (`SceneRendererCore::SyncOpenPBREnvironment`) so the pyramid is built from the file's equirect; any sky load rebuilds it. Missing resources skip pass 2 for that frame.

[MaterialXGen.cpp](../../../Phasma/Cook/Code/MaterialX/MaterialXGen.cpp) selects `SPECULAR_ENVIRONMENT_FIS`; the search-path override [mx_environment_fis.glsl](../../../Phasma/Runtime/RuntimeAssets/MaterialX/pe_overrides/libraries/pbrlib/genglsl/lib/mx_environment_fis.glsl) is MaterialX 1.39.5's file with only the sample count, mip count, LOD, sky lookup and irradiance swapped for the `pe_*` hooks in [PePrelude.slang](../../../Phasma/Runtime/RuntimeAssets/Shaders/MaterialX/PePrelude.slang), plus a seam where ReflectionPass's trace replaces every lobe wherever it has data. `pe_env_samples()` is `openpbr_env_samples` (default 32, clamped 1-512 where it is consumed and in scenes; 0 when IBL is off, which skips the integral), `pe_env_lod` is MaterialX's own `mx_latlong_compute_lod` (offset 1.5, distortion), `pe_env_lookup` applies the IBL intensity and SSAO. Pass 2 binds radiance, irradiance and a repeat-U/clamp-V trilinear sampler at set 3 bindings 9/10/7; push-constant dword 22 carries the sample count.

Environment pitfalls (verified 2026-10-15):
- Legacy [PrefilterCubemap.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/Compute/PrefilterCubemap.hlsl) clamps samples to 16 and biases LOD by `roughness * 8`; its mips are roughness-filtered and cannot feed FIS. The legacy diffuse lookup at `levels - 3` is not a cosine convolution.
- A cube pyramid is not a lat-long pyramid. FIS over a cube pyramid with a tuned LOD offset left -7% / +6% brightness biases on rough metal at equal sample count (plane); the lat-long pyramid brings those to under 1/255. Building the lat-long pyramid from the *legacy cube* instead of the file's equirect is still about 2% too bright overall (the cube decimates the equirect without prefiltering at high latitudes and loses about 10% of the sun's peak), which is why the pyramid reads the equirect.
- `san_giuseppe_bridge.hdr` has a 35840 sun holding 43% of the energy: FIS at 16-128 samples is far from converged on it, MaterialX's own included (N=16 vs N=1024: 46/255 on rough metal). RGBA32F keeps suns above 65504 that RGBA16F cannot.
- A 64x32 source for the irradiance is up to 3% off at the zenith, 256x128 within 0.3% (numpy replica, `hdr_io.py`). MaterialX's shipped irradiance map matches the exact convolution to 0.4% on average, but any lat-long map's top row ripples with azimuth (the shipped map's row 0 runs 0.676-0.695, a 128x64 map's +-3%), and a pole direction has no azimuth: `atan2(0, 0)` differs between SPIR-V and DXIL, so a flat floor (N exactly +Y) read +2.7% on Vulkan and +1.9% on DX12 until PE's irradiance rows were placed on the poles (row 0 = zenith exactly; `PeIrradianceUv`) and the pole azimuth fixed to 0. MaterialX's own lookup lands on one arbitrary column of its top row (the maximum, +1.1% over the exact zenith value).
- The pyramid shader's UAV array holds 13 mips (4096 wide).

Facts about the legacy material path, read from source 2026-10-13:

- **Two GPU copies of every material.** `materialTable` is the hand-written `MaterialGpuData` in [Material.h](../../../Phasma/Runtime/Code/Scene/Material.h); ray tracing and GI read it. `materialBytes` is reflected through the `standard_pbr.pass` annotation; `GBufferPS` reads it when `materialByteOffset` is set. A new parameter needs the annotation token, both `Sync*` functions and `BuildGpuData` together.
- **The BRDF is copied 8 times:** four light functions in [Lighting.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/Gbuffer/Lighting.hlsl), four `RT_*` in [RayTrace.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/RayTracing/RayTrace.hlsl). [PBR.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/Gbuffer/PBR.hlsl) `V_SmithGGXCorrelated` uses a2 = r² (α) while `DGGX` uses α² = r⁴, so the legacy correlated-Smith term is off. The fallback `#define PI 3.1415628` is masked because `Common.hlsl` defines PI first.
- **The DFG LUT** `RuntimeAssets/Objects/ibl_brdf_lut_rg16f_256.bin` is 256×256 RG16F with rows = perceptual roughness and columns = NdotV (.x scale, .y bias). There is no generator in the repo.
- **The transparent G-buffer pass blends its attachments.** Normal, albedo, srm, velocity and emissive use `BlendState::Default` (SRC_ALPHA over each target's own alpha); `transparency` uses its own `"transparency"` mode ([standard_pbr.pass](../../../Phasma/Runtime/RuntimeAssets/PassInfo/standard_pbr.pass) `transparent.colorBlendAttachments`; the pass-level `blendEnable` is ANDed in). An integer or bit-packed target needs a blend-disabled attachment, or it is garbage on alpha-blend pixels.
- **A pass's `Resize` re-inits descriptors only.** Pipelines are rebuilt by `ResizeInitializedSceneRenderGraphPassComponents` when `SceneRendererCore::m_colorFormatChanged` is set. HDR and effective OpenPBR changes set that flag, including when a toggle coincides with render-scale resizing. The G-buffer passes compare their own format lists and rebuild themselves, but a setting that switches shader defines in lighting, ray tracing or SSR must set that flag.

## ImGui Platform Windows

Editor and Animator panels dragged outside the main window become their own OS windows (ImGui multi-viewport) on Vulkan and DX12. [GUIBackend::ConfigureIO](../../../Phasma/Editor/Code/GUI/Backends/GUIBackend.cpp) sets `ImGuiConfigFlags_ViewportsEnable`, but ImGui silently clears the flag each frame unless both the platform and the renderer backend report `...HasViewports`. The vendored `imgui.cpp` is the docking branch (upstream `a4ebe3d5`), while the old `third_party/imgui/imgui_impl_vulkan.cpp` was the master-branch file with no viewport code, so floating panels never left the window on Vulkan. Both renderer backends now live in [Runtime/Code/UI/Backends](../../../Phasma/Runtime/Code/UI/Backends/): `imgui_impl_vulkan` is the docking-branch file from that same upstream commit, and `imgui_impl_dx12` is PE's adapted copy. When updating the vendored ImGui, take both backends from the matching docking commit. [GUIBackend::RenderPlatformWindows](../../../Phasma/Editor/Code/GUI/Backends/GUIBackend.cpp) wraps `UpdatePlatformWindows`/`RenderPlatformWindowsDefault` in the main queue's submit mutex because the upstream backends call `vkQueueSubmit`, `vkQueuePresentKHR` and `vkDeviceWaitIdle` directly while worker threads submit through `pe::Queue`. Pool test `editor-viewports-vulkan` floats the Console via `imgui.ini` and checks for its OS window. Verified 2026-10-05: Vulkan (with validation, zero errors) and DX12 floating windows render, and the platform window survives a module hot reload.
