# Rendering And RHI Notes

The render path is split between PhasmaRuntime's shared scene renderer and PhasmaCore's backend-neutral RHI wrappers. Code remains the source of truth; use this page for cross-cutting pitfalls that are easy to miss when reading one file at a time.

## Scene Pipeline Script

A scene's pipeline is its render path (render mode, HDR, dynamic rendering: plain controls), its pipeline script, and the values that script exposes: culling/LOD/cluster, shadows, lighting and GI, the default post-process profile and G-buffer formats, plus any passes the script adds. Since 2026-10-09 (the user's plan C, replacing the pass list and `.pepipeline` assets) the script is the pack: [ScriptSystem.cpp](../../../Phasma/Runtime/Code/Script/ScriptSystem.cpp) `LoadPipelineScript` runs `SceneSettings::pipeline_script` (Assets-relative; empty = [default_pipeline.lua](../../../Phasma/Runtime/RuntimeAssets/Scripts/Pipeline/default_pipeline.lua)) at every scene load in the editor and the player, in edit and play mode, whether or not the scene has a Scene Settings node.

- `exposed {...}` declares its values. One named after a scene setting (`settings.get/set` names, plus `lod_distance_1..3` and `depth_bias_constant/_clamp/_slope` for the two arrays) mirrors that setting: a loaded scene keeps its own saved value, and the script's literal applies only when the script is picked in the editor (`ReloadPipelineScript`). Its other values persist in `SceneSettings::pipeline_values` (scene JSON `pipeline_values`).
- `init()` adds its passes (`render_graph.add_fullscreen_pass`, `render_graph.add_pass`); it runs at load and again when one of its own values changes. Passes added from the pipeline script belong to it (`SetLuaRenderPassOwner`) and are cleared when the scene or the script changes, or on a Lua reload, which runs the script again.
- `pipeline.base()` returns a fresh table of the default script's values, so a project script extends the engine's instead of copying it: `local p = exposed(pipeline.base()); p.ink = 0.8`. Its `exposed_when` nesting comes along.
- `exposed_when { cas_sharpness = "cas_sharpening" }` nests a value under a bool value: the panel shows it indented under that switch and hides it while the switch is off (the default script nests every pass's settings under its switch, and CAS under TAA). Node scripts' Exposed Variables honour it too, and both panels label values readably (`ui::ExposedLabel`: `cas_sharpness` -> "Cas Sharpness", `IBL_intensity` -> "IBL Intensity").
- C++ (2026-10-09, ABI 28): `pipeline_script` may name `cpp:<Type>`, a `ScriptKind::Pipeline` script in the game module (`PHASMA_PIPELINE_SCRIPT`). It is constructed at load and again after one of its own values changes; `ExposeNumber` / `ExposeBool` / `ExposeBase` feed the same panel and values (`ScriptSystem::ExposePipelineValue`); its passes belong to the pipeline, so Play Stop keeps them (`CppScriptSystem::CreatePipeline`). The script is created once the module has loaded (`ModuleLoads`), and again after a live module reload. AgainstTheHero's C++ scene uses `cpp:AthPipeline`; its Lua scenes use `ath_pipeline.lua` with the same ink values.
- `render_graph.add_fullscreen_pass{name, shader, order, params, thickness_at_1080, min_thickness}` records natively every frame ([FullscreenPasses.cpp](../../../Phasma/Runtime/Code/Render/FullscreenPasses.cpp), shared with the C++ scripts' `AddFullscreenPass`), so a pipeline needs no Lua per frame. `render_graph.add_pass` takes `order` again.
- Scene Settings > Pipeline ([PipelineControls.cpp](../../../Phasma/Editor/Code/GUI/Widgets/PipelineControls.cpp)): the render path, a script picker (Engine default, a .lua under `Scripts/Pipeline`, or a `cpp:` pipeline script from the game module) and every exposed value (`DrawExposedValues`: readable labels, nested under their switch, otherwise name order; no ranges or colour pickers). The Animator has no script system and shows only the render path. `render_pass_orders` still loads from scenes; nothing edits it.
- The values stay in `SceneSettings` in memory, so the renderer, post-process zones (which override the default profile), Lua `settings.*` and the Animator read them as before. One pipeline is active per frame.

Verified 2026-10-09: `.testpool/tests/pipeline_script.py` (Player, temp project: a script extending `pipeline.base()` kept the scene's saved `bloom`, restored its own `tint` from `pipeline_values`, and its fullscreen pass compiled its shader; a scene without one loaded the default and kept its settings); AgainstTheHero's `ath_pipeline.lua` draws the ink paper and outlines in editor edit mode, during Play and after Stop, in the C++ match on Vulkan and DX12 and in the Lua game; the editor viewport of `spud_fields_3d_v1` was unchanged (0 px) between the engine runner landing and the pass list's removal. Removed with it: the pass list (drag, sort numbers, Add Pass, minus buttons), templates, `.pepipeline` load/save and the scene `"pipeline"` key (old assets on disk are inert), `script_passes`, `RenderGraph::OrderConflict`. "Forward+" is tiled light culling for the deferred lighting passes; the engine has no forward-lit opaque path.

Columns and checks (2026-10-08): passes with equal sort numbers form a column; `RenderGraph::Execute` issues a multi-pass column's input barriers as one deduplicated batch, then records its passes in pass-id order. `RenderGraph::Compile` records problems (`GetProblems`): a read with no earlier writer (a pass reading an image it also writes, such as TAA and GI history, counts only when a later pass writes it too), two passes of one column sharing a resource that one writes, or a pass sampling an image it renders into. `RenderGraph::NewProblems` compiles the graph at the current and the proposed orders and lists what a move adds. Problems already present at the current orders do not count. The light passes read the shadow maps under the Shadow pass's own condition, `shadows` with an active Scene Settings node (`ShadowsActive` in [LightPass.cpp](../../../Phasma/Runtime/Code/RenderPasses/LightPass.cpp)); before 2026-10-10 they sampled maps the Shadow pass had not rendered while the node was inactive. Pool tests `render-warnings-vulkan`/`-dx12` fail on any `[Descriptor]` or `[RenderGraph]` warning through GI toggles, resizes, render modes, occlusion culling and a reload (verified 2026-10-10). `RGBuilder::ReadBuffer/WriteBuffer` only record ordering, with no barriers. The cull draw lists (counters buffers of the frustum set, set A and set B), the Forward+ tile buffer and the particle buffer are declared by their producers and consumers. Those declarations resolve `GetActiveScene()`, not the pass's `m_scene`: the graph compiles outside recording, and Depth, DepthLate, both G-buffer passes and SelectionOutline clear `m_scene` after recording, so until 2026-10-08 their buffer reads were invisible to the checks. An attachment a pass LOADs (`IRenderPassComponent::DeclareOutputs` passes `loadOp == PE_LOAD_OP_LOAD`; script-pass writes count as loads) also orders the pass after the image's writer, again without a barrier. With no earlier writer it is a problem only when a later pass writes the image; otherwise it is last frame's contents. Passes with their own `DeclareOutputs` do not carry the flag. The Player's deferred graph (LDR bloom and colour grading after the UI) compiles with `Compile(false)`: its images come from the main graph, so it has nothing meaningful to report. Verified 2026-10-08 with the Player on scenes that moved Depth before Culling and GBufferOpaque before Depth: both fell back to the default order with `[Pipeline]` warnings naming the buffer read and the depth load; the default order logs nothing new. Both renderer hosts rebuild their graph when `render_pass_orders_revision` changes. Saved orders that break the frame fall back to the default order at graph build with a `[Pipeline]` warning (`SceneRendererCore::AddScenePassesToRenderGraph`). Within a column, passes record in pass-ID order ([RenderGraph.cpp](../../../Phasma/Core/Code/API/RenderGraph.cpp)).

Removed 2026-10-08, the user's decision after comparing Unity and Unreal: the Window > Pipeline Editor node graph, pin bindings (`PinTarget`), pipeline-authored images and data nodes (`PipelineData`). Not covered by the pipeline script yet: changing the shadow map size, cascade count or G-buffer format live (those apply on renderer re-init).

## Background Frame Pacing

All six Phasma windowed apps (Editor, Player, Animator, Launcher, Cook UI and Profiler) call [FrameTimer::Tick / EndFrame](../../../Phasma/Core/Code/Base/Timer.cpp) around each frame. `Tick` records the start without waiting. After rendering and presentation, `EndFrame` waits only for the remaining background frame budget (30 FPS by default; its target argument accepts other integer rates, with zero disabling the cap). One global setting turns it off for every app: `"background_fps_cap": false` in `phasma_settings.json` beside the executables, read when `FrameTimer` is created (absent or unreadable = capped). `FrameTimer::SetBackgroundCap`, from Lua `engine.set_background_fps_cap(bool)`, changes it for the running session without saving; the editor pool tests lift it that way at start-up, since their window is never focused. Verified 2026-10-07 in the editor: key false = 1258-1633 fps unfocused, key absent = 30 fps. CPU work stamps precede this wait; the next frame's delta includes it. Headless Cook/Export operations do not run the window frame loop.

The deadline advances by a fixed period on a steady clock, so late wake-ups do not accumulate into a lower average. Long stalls reset missed deadlines instead of producing a burst of catch-up frames. Any focused SDL window in the process, including a detached Editor/Animator panel, clears the background schedule. Windows uses a high-resolution waitable timer, with a standard-library wait if creating, arming or waiting on that timer fails; other platforms use the standard-library wait. Neither path spins the CPU.

The engine hosts pace after their frame pump in [Editor](../../../Phasma/Editor/main.cpp), [Player](../../../Phasma/Runtime/Code/Runtime/PlayerHost.cpp) and [Animator](../../../Phasma/Animator/main.cpp); the SDL-rendered loops in [Launcher](../../../Phasma/Launcher/main.cpp), [Cook UI](../../../Phasma/Cook/CookUI.cpp) and [Profiler](../../../Phasma/Profiler/main.cpp) pace after `SDL_RenderPresent`. Local pool test `background-fps` exercises the built shared timer with SDL's dummy video driver: 30/60 FPS averages with variable work and host overhead, uncapped main and secondary focus, no extra wait after a slow frame, and no catch-up burst. Verified 2026-10-07.

## Skinned Mesh LODs

`Scene::AddModel` generates index-only skinned LODs against the original vertex store. `Scene/MeshLod.h` converts each mesh section's positive bone influences into dense weights over a stable bone palette; numerical bone indices are never simplification attributes. PE caps the skinning palette at 16 attributes, so sections using more than 16 active bones, invalid weights/joints, or no positive influences retain only LOD0. The palette limit is per section, not per skeleton. Static mesh simplification is unchanged.

Skinned simplification targets 50%, 25% and 12% of the original indices with a 0.01 combined position/skin-attribute error limit; the error limit can stop reduction early. Bone-weight attribute importance is 0.1. Original positions, normals, UVs, bone indices and weights are retained. This is not a bound on animated screen-space error, so skinned meshes default to `lod_enabled=false` and individual validated prefabs must opt in. Geometry-sharing prefab instances reset to the same default before applying their authored LOD fields.

Both main and shadow GPU culling already select the generated index ranges. Scene serialization now preserves `shadow_lod_bias`, with 1.0 as the fallback for older scenes, allowing a scene to choose coarser shadow geometry independently. No animation cadence, gameplay timing, or shader skinning algorithm changes are required. Index-only LODs reduce submitted geometry but retain the original vertex buffers in memory.

## LOD Selection Distance

`CullingCS` and `ShadowCullCS` pick a mesh's LOD from the camera's distance to the nearest point of its world AABB, not the AABB center (`lod_distances`, `lod_bias`, per-mesh `lod_bias`/`lod_shift` unchanged). With the center, a big flat mesh dropped to a coarse LOD while the camera stood over it: AgainstTheHero's 64 m arena floor (a 32-slice cylinder) switched to LOD1 whenever the hero neared its rim, and the simplified disc's chorded edge and twisted side wall read as dark holes in the ground. Small props switch at almost the same distance as before; on the ATH native arena the A/B was within noise (old 1008 fps / 0.992 ms median, new 1036 / 0.965). Verified 2026-09-28. `CullingPass` and `CullPhase1Pass` load `Path::RuntimeAssets + "Shaders/Compute/CullingCS.hlsl"` directly ([CullingPass.cpp](../../../Phasma/Runtime/Code/RenderPasses/CullingPass.cpp), [CullPhase1Pass.cpp](../../../Phasma/Runtime/Code/RenderPasses/CullPhase1Pass.cpp)), so a project's own copy does not replace it in loose-file desktop runs; only passes that load through `Path::ResolveAsset` take a project copy (see [Storage Image Formats](#storage-image-formats); corrected 2026-09-30).

## Material Rebuilds

Material-table rebuilds resolve each pass layout by its loaded `PassInfoAsset` identity within the rebuild, avoiding a resource-ID string allocation and string hash per mesh. Shader source checks still run: `ShaderCache::ParseShader` recognizes the existing quoted-include grammar directly rather than invoking a regex on every source line. Recursive expansion and content-based cache invalidation remain unchanged; 64 runtime HLSL sources produce byte-identical expanded text. These reduce rebuild overhead but do not make new instance creation incremental. Pooled ATH respawns avoid creation/rebuild work by reusing valid parked rigs.

## Joint Palette Uploads

`Scene::UpdateUniformData` writes root-corrected joint palettes directly into the current frame's mapped storage buffer, removing the full intermediate matrix array and its second copy. Node data and skinned bounds retain their batched copies. Missing poses still upload identity matrices, and each palette range is checked against the buffer size.

Each dirty skinned node is one job (`SkinJob`): it rolls its own shown pose into the previous one (a swap, not a copy), writes both palettes and re-dirties a moving pose. At least 128 jobs run through `ThreadPool::ParallelFor` (the caller plus up to seven Update-pool workers, 64 jobs each at least); smaller batches stay serial. Workers capture a span of the caller's jobs and touch only their own node and byte range. The recycled frame's fence precedes these writes, and all jobs join before submission or error propagation. DX12 retains its existing upload-to-device-buffer copy. `Joint Palette Preparation` isolates the parallel work inside `Update Uniforms`.

The palette is bound by bytes written, not by matrix math: the storage buffer is `CPU_TO_GPU_PERSISTENT_DEVICE` (ReBAR), and a probe that skipped two thirds of the writes on the 1,000-enemy ATH fill cut the scope from 0.63 to 0.24 ms at equal load, while more chunks changed nothing (2026-10-04). Bytes written are the lever: a rig whose parts sit on separate mesh nodes uploads one palette per part, all copies of one pose (`Animation.ReusedPoses` vs `UniquePoses`). Put a skinned rig's parts on one node with `mesh_refs` instead: every mesh of a node reads the node's palette (`meshDataOffset`), so the node gets one pose, one palette and one bounds pass. Script `setColor` tints only a node's first mesh ref, so list the part that flashes first. ATH's creeps moved from 3 part nodes under an identity `_Visual` node to one node on the root (2026-10-04): reused poses ~2,000 to ~130, palette 0.60 to 0.24 ms, frame 4.65 to 2.82 ms on the 1,000-enemy fill.

`SceneSettings::cull_offscreen_animation` (off by default; `settings.set` / native `SetSetting`) skips skinned rigs outside the camera: `AnimationSystem::Update` tests each playing state's node against the active camera's frustum, using last frame's world bounds widened by 2 m (`kOffscreenMargin`). A culled state still advances its clocks, blends and root motion, but is not posed (`state.posed = false`, so a fade started meanwhile evaluates its own start). It also gets no palette upload (`UpdateUniformData` skips `viewCulled` nodes), and its `renderVisible` goes to 0, so `CullingCS` and `ShadowCullCS` skip its draws, shadows included. That suits a top-down game, where nothing off screen casts into view. `NodeRuntime::hidden` keeps the script's `SetNodeRenderVisible` choice apart from the cull. An idle pose that was culled falls through once, to be posed and shown. A rig spawned straight into view can miss one frame, since its bounds are still last frame's. AgainstTheHero turns it on at match boot. On its 1,000-enemy fill, unique poses fell from ~958 to 363-487, pose evaluation from 0.33 to 0.21-0.24 ms, and the palette from 0.24 to 0.11-0.14 ms (2026-10-04). The frame time of that run is not comparable: another game shared the GPU.

World bounds of skinned meshes (`SkinnedBounds::Pose`) skip joints with no vertices in the mesh (`used`, filled by `Build`), and posed skinned meshes no longer compute the discarded rest-pose `TransformAabb`. `UpdateNodeMatrix` queues each posed skinned mesh and `UpdateNodeMatrices` poses the queue through `ParallelFor` after the serial walk (`Build` stays serial there, since the joint boxes are shared by mesh instances), then folds the results in walk order. `Skeleton::InverseRootTransform` caches the inverse root on the main thread. On the 1,000-enemy fill, `Update Node Matrices` went 0.76 to 0.62 ms (joint skip) to 0.38 ms (parallel). The per-frame selection-flag pass returns early when no node is selected and nothing was flagged last frame (`SceneRuntimeHooks` `hasSelection`; a host without the hook keeps the full pass): 6.40 to 6.05 ms frame in that fill.

A controlled Release Vulkan test with 1,024 independently clocked ATH instances reduced uniform CPU time from 0.696 to 0.490 ms; DX12 reduced it from 0.660 to 0.471 ms. Total frame time stayed approximately 3.3 ms because that fixture was GPU-bound. A live 2,048-enemy sample reduced the same scope from 1.713 to 1.059 ms, but changing combat activity prevented a reliable overall frame-time improvement claim. CPU checks compare serial and parallel matrix bytes, fallback poses and guard ranges across batch boundaries; Vulkan validation and DX12 debug-layer crowd runs also cover the mapped-buffer path.

## Skinned Indirect Instancing

`SceneSettings::skinned_instancing` groups visible skinned meshes that share an exact index range, vertex offset and raster bucket. Grouping runs inside the existing GPU culling wave after visibility and LOD selection, including both Hi-Z phases and each shadow cascade. Each instance still resolves its own mesh constants, transform, joints and material. Main-pass transparent and transmission draws keep their individual sorted commands; selection also keeps the original individual command.

Both Vulkan and DX12 use the `PE_DRAW_ID` vertex semantic as a four-byte per-instance stream at vertex binding 1. That binding is reserved when the semantic is present. A frame-local ID buffer contains an identity prefix for ordinary draws and separate remapping segments for frustum, Hi-Z A, Hi-Z B and shadow output. Shadow cascades reuse their segment only after the preceding draw finishes reading it. Buffer growth, deferred uploads and compute-to-vertex barriers follow the existing scene buffer lifecycle.

The option is off by default and can be enabled through Scene Settings or `settings.set("skinned_instancing", true)`. Scene serialization and profiler capture metadata preserve its value. Profile the target scene before enabling it: batching reduces indirect command count, but does not reduce animation evaluation, vertex skinning or pixel work. Batches stop at wave boundaries; no extra global sorting dispatch is added. Local Vulkan and DX12 compute checks reduced 1,024 identical instances to 32 commands and verified mixed geometry, LOD keys, visibility, excluded draws and partial waves. That command-count result is not an FPS claim.

A clean Release comparison on an RTX 4080 SUPER with 1,024 ATH skinned instances at 2560x1369 found essentially unchanged GPU time: Vulkan 3.224 ms off / 3.221 ms on, DX12 3.174 ms off / 3.180 ms on. Poses and gameplay were frozen to hold the render workload constant; independent animated poses were checked separately. Hi-Z comparisons also stayed within 0.5% GPU time. These measurements justify retaining the opt-in default rather than claiming a crowd-performance improvement from command reduction alone.

Visual validation remains separate from those timing checks: the September 10 DX12 ATH crowd captures show black speckling on meshes with instancing both disabled and enabled. It also reproduces with the binary preserved before the LuaJIT/parallel-pose/material-packing changes; Vulkan captures do not show it. Cause (found 2026-09-29): the G-buffer depth-tests EQUAL against the depth prepass (`standard_pbr.pass`), and `GBufferVS` computed the clip position as `p*(J*(M*VP))` while `DepthVS` used `p*((J*M)*VP)`. With a bone transform the two round apart, so skinned pixels failed the test in speckles and kept the cleared G-buffer (static meshes, J = identity, matched exactly). Fix: `GBufferVS` uses DepthVS's order and both clip positions are `precise`; pool test `depth-equal-positions` guards it. Any shader that writes depth compared EQUAL with the prepass must repeat DepthVS's maths exactly. Projects that ship copies of these shaders (materials resolve project-first) must resync them.

Standalone Quality scales the display target as well as scene targets. `CreateFSSampledImage(source)` takes its size and format from the actual source: HDR for DOF/MotionBlur/SSR, display format for ColorGrading/FXAA and editor/animator previews. This also follows the host's output policy; copying a scaled display into a native-size scratch image previously failed image-copy validation. Tone mapping samples HDR directly without a copy. Vulkan and DX12 smoke checks cover live scale transitions with post-processing enabled; image-copy size validation remains intact. Verified 2026-10-07.

## Forward+ Light Culling

Raster lighting uses `ForwardPlusLightCullingPass` before the opaque and transparent light passes when `SceneSettings::forward_plus` is enabled. The compute pass bins point and spot lights into 16x16 screen-space tiles, writing per-tile counts and compact index lists that `LightingPS.hlsl` consumes instead of looping over every local light for every pixel. Directional and area lights remain on the existing full-list paths.

The culler intentionally uses a conservative projected sphere overlap for each local light. If a tile reaches `FORWARD_PLUS_MAX_LIGHTS_PER_TILE`, the tile records an overflow bit and the pixel shader falls back to the original full point or spot loop for that light class. This preserves correctness for extreme scenes while keeping common scenes on the cheaper tiled path.

Forward+ resources are descriptor-sensitive: scene render descriptor refresh must update the culling pass before `LightPass`, because the lighting descriptor set binds the cull buffers as extra read-only resources. When the global option is disabled or the raster path is inactive, `LightPass` binds small fallback storage buffers and the shader uses the original full point/spot loops. The pass also records explicit buffer barriers between compute writes and lighting reads on both Vulkan and DX12.

The light storage buffer is replaced, not resized. `Scene::UpdateLights` destroys a frame's `lights_storage_buffer` and creates one twice as large when the enabled lights outgrow it; it starts at 1 KB, roughly 16-20 point lights. Every pass that binds it must rebind when `Scene::GetLightStorage(frame)` changes:
- `ForwardPlusLightCullingPass` already did.
- `LightOpaquePass`, `LightTransparentPass` and `RayTracingPass` did not, and kept the destroyed buffer in their sets until something else (an SSAO target, shadows, Forward+) forced a refresh. They now remember the bound buffer per frame (`m_boundLightStorage`) and rebind when it moves (2026-10-04).

Vulkan tolerated the stale binding. DX12 hung the GPU (`DEVICE_HUNG`) in the opaque lighting draw right after the Forward+ cull. AgainstTheHero's 1,000-enemy fill, whose Blast Buds each carry an ember point light, hit it within seconds with shadows on. Toggling shadows off refreshed the sets, which hid it.

DX12 debug regions now also emit D3D12 `BeginEvent`/`EndEvent`, so PIX shows pass names and DRED breadcrumbs (`PE_DX12_DRED=1`) show where each pass begins and ends. DRED did not return the event strings themselves (no breadcrumb contexts), so the failing pass is read from the event structure.

`ParticleManager::LoadTexture` refuses a 17th particle texture. `ParticlePS` binds `textures[16]` with the scene depth at binding 16, so a 17th would index past the table on DX12, and its descriptor write would overwrite the depth.

## Present Mode And Framebuffer Cache

Present-mode changes must be treated as resize work, not as an immediate mid-frame swapchain teardown. Editor/runtime requests should update the desired surface present mode, sync the stored preference to the effective supported mode, wait for idle, and queue `EventType::Resize` so swapchain, scene render targets, render-pass components, and frame resources rebuild together. Host window titles should be refreshed after the deferred swapchain recreation and after the active project binds. They should report "Phasma Editor", GPU, API, the recreated swapchain's actual present mode, the build configuration, and the active project folder. Other desktop hosts use the same spaced product name in the window title (`Phasma Player`, `Phasma Animator`, `Phasma Profiler`, `Phasma Cook`, `Phasma Engine`, `Phasma WebGPU`).

FIFO presentation is paced independently from reusable command-buffer fences. `Present()` only queues presentation so worker submissions and secondary ImGui windows are not held behind the display wait. At the start of the next frame, Vulkan prefers optional per-surface `VK_KHR_present_id2` + `VK_KHR_present_wait2` support and falls back to `VK_KHR_present_id` + `VK_KHR_present_wait` when wait2 is unavailable; either extension path works without raising the engine's Vulkan 1.2 minimum. DX12 waits on a `DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT` swapchain limited to one queued frame. Both waits use a bounded timeout so the host can pump window events and retry the same presentation instead of hanging while a display is locked or off; PhasmaWebGPU performs the same gate during `wgpuSurfaceGetCurrentTexture` and reports native `Timeout` or `Outdated` acquisition status. Immediate/tearing mode skips these waits. Vulkan completion means that the request reached or was replaced within the presentation engine; it is not a precise user-visible scanout timestamp.

Vulkan paces against the previous successful presentation ID, allowing one newer present while the next frame is prepared. Waiting for the newest present instead serialized CPU/GPU work with display refresh: the September 10 live 1,024-enemy ATH reproduction measured about 28 FPS in FIFO versus 89 FPS in Immediate. The bounded overlap restored FIFO to about 58–60 FPS; a normal Player launch without the profiler reported a 59.8 FPS median over 36 one-second log samples. This allows one additional queued frame of latency; command-buffer reuse fences, image acquisition and semaphore ownership are unchanged. Only non-error presents advance the successful-ID history, and swapchain recreation starts it empty. The 115 FPS earlier crowd result was a short uncapped capture, not a FIFO guarantee or a sustained dense-combat rate.

Editor and player swapchain recreation must destroy and recreate scene frame commands and acquire/submit semaphores around the swapchain so their arrays match the new image count. Present-mode requests from live UI or scripts are deferred through the host resize path; startup and WebGPU configuration may still use the lower-level immediate RHI operation before host frame resources exist.

Every successful swapchain creation also rebuilds the RHI deletion-queue array to the new swapchain image count. Recreating only the swapchain images while retaining the old queue count lets the new frame index address past the queue array during later scene/resource destruction; Android surface loss and resume is a common trigger because its swapchain image count can change.

Cached framebuffers are keyed by the actual attachment `ImageView` objects captured in the backend framebuffer. Implicit render-target views must be created before cache lookup so an RTV recreation cannot reuse a framebuffer that still holds a destroyed Vulkan image view or DX12 descriptor.
Code outside PhasmaCore must clear this cache through `CommandBuffer::ClearFramebufferCache()`, not by accessing the inline static map from a header. A DLL/executable boundary can otherwise produce a separate inline-variable instance, leaving PhasmaCore's real cached framebuffer alive after its attachment view is destroyed.

DX12 scaled image blits use the shader path rather than `CopyTextureRegion`. [Dx12Blit.cpp](../../../Phasma/Core/Code/API/DX12/Dx12Blit.cpp) sets a positive-height viewport over the destination rectangle and passes the source rectangle as a positive UV scale and offset; [Dx12Blit.hlsl](../../../Phasma/Core/Code/API/DX12/Dx12Blit.hlsl)'s fullscreen triangle maps clip-space bottom to v = 1, so source and destination stay top-to-top like Vulkan's image blit. Scene geometry flips clip-space Y separately in `Structures.hlsl` under `PE_DX12`. Verified 2026-10-07.

## Downsampler Storage Formats

[Downsampler](../../../Phasma/Core/Code/API/Downsampler/Downsampler.cpp) selects an embedded Vulkan shader matching the input view: `Rgba8` for RGBA8 UNORM, `Rg16f` for RG16F, `Rgba16f` for RGBA16F, and `Rgba32f` for HDR RGBA32F. Both the mip array and mip-6 storage image use that format. The previous single `Rgba32f` module bound to RGBA8 views produced undefined image values. Unsupported Vulkan storage formats fail explicitly; DX12 retains one DXIL shader whose typed UAV follows its view format. These variants add no storage-image read/write-without-format requirement. The RG16F variant does declare `StorageImageExtendedFormats`, requiring `shaderStorageImageExtendedFormats`; [Vulkan device creation](../../../Phasma/Core/Code/API/RHI.cpp) enables advertised core features. Regenerate the embedded modules with [generate_downsampler_shaders.py](../../../tools/generate_downsampler_shaders.py) and an explicit DXC path; the generated header records the compiler version (verified 2026-09-30).

Direct bytecode shaders must initialize their [ShaderCache](../../../Phasma/Core/Code/API/ShaderCache.cpp) identity from bytecode, entry point and stage. [PassInfo::UpdateHash](../../../Phasma/Core/Code/API/Pipeline.cpp) uses that identity for pipeline reuse. Leaving it zero made the format variants reuse the first RGBA8 pipeline even when their shader modules contained the correct formats. A desktop core-validation/GPU-AV check dispatched all four formats with eight mips and reported no storage-format mismatch after both fixes (verified 2026-09-30).

The retained DXIL path was verified with a Release Sponza smoke on DX12/display 1 and the D3D12 debug layer: the embedded downsampler initialized, scene rendering was visually checked, and no debug-layer error or device loss was reported. This smoke validates the rebuilt bytecode path, not performance or Android stability (verified 2026-09-30).

VVL 1.4.363.0 contains the same-invocation race-report fix from [PR 12418](https://github.com/KhronosGroup/Vulkan-ValidationLayers/pull/12418), but still reports adjacent-invocation races in SPD. The observed `spdIntermediateA` load/store pair maps to the wave-based `SpdDownsampleMip_2` path in [ffx_spd.h](../../../Phasma/Core/Code/API/Downsampler/Shaders/ffx_spd.h): shared reads, subgroup shuffles, then an in-place quad-leader store. No same-invocation reports appeared in the newer-layer run. This confirms that upgrading alone does not clear the warnings; it does not settle whether subgroup-dependent accesses are a real hazard or a remaining instrumentation limitation. No speculative barrier was added (verified 2026-09-30). A diagnostic build with `SPD_NO_WAVE_OPERATIONS` removed every report (four-format downsample check and a 180 s ATH Map 1 run: 10 to 0 each), and every report maps to the wave load, subgroup shuffle and in-place quad-leader store in `SpdDownsampleMip_2`/`SpdDownsampleMip_3`. The layer's shared-memory race instrumentation does not model `OpGroupNonUniformShuffle`, so a detector limitation is the likelier explanation; shuffles are not memory barriers, though, and settling it needs an upstream VVL reproducer and a memory-model ruling. The diagnostic change was not kept (verified 2026-09-30).

## Storage Image Formats

Contract: every Vulkan storage image declares the format of the view its pass binds. [SceneRenderTargets.cpp](../../../Phasma/Runtime/Code/Render/SceneRenderTargets.cpp) creates viewport and emissive as R8G8B8A8_UNORM by default, or R16G16B16A16_SFLOAT when `SceneUsesHDR()` is true; a separate `hdrDisplay` exists only in HDR. TAA history and bloom follow the active scene format. Display, screenshot, albedo and srm remain R8G8B8A8_UNORM, independent of the swapchain; full-screen copies derive their format and dimensions from their source. `BlitSceneImageToSwapchain` converts to the swapchain (`vkCmdBlitImage` converts; DX12's blit cannot, but the DX12 swapchain is always R8G8B8A8). Vulkan `CopyImage` does not convert, so each source/destination pair must match. Direct present hands the swapchain image to passes built for the display format, so [RuntimeSceneRenderer](../../../Phasma/Runtime/Code/Render/RuntimeSceneRenderer.cpp) uses it only when the formats match; a B8G8R8A8 desktop surface falls back to the blit. Frames with a pending screenshot also skip direct present and copy the offscreen display: copying the swapchain after its PRESENT barrier left it in COPY_SOURCE at Present (D3D12 debug-layer error 538), and a Vulkan swapchain only has TRANSFER_SRC when the surface supports it (screenshot guard verified 2026-09-30; HDR formats verified 2026-10-07).

Shaders declare formats with `[[vk::image_format]]`: `rgba16f` for TAA `out_color` and RayTrace `output` with `HDR_SCENE`, otherwise `rgba8`; RCAS `out_color` always uses `rgba8`; `r16f` for SSAO `RawAO`/`FilterInput` and blur `FilterOutput`, `r8` for the upsample `FilterOutput` (`SSAO_UPSAMPLE_PASS`). Undeclared `float4`/`float` images compile to `Rgba32f`/`R32f`; that matched the RGBA32F cubemaps and R32F depth pyramid and `rtDepth`, but not these views, and VVL 1.4.363.0 reported `Undefined-Value-StorageImage-FormatMismatch-ImageView` for TAA, RCAS and SSAO. `r16f`/`r8` add `StorageImageExtendedFormats`, like the downsampler's RG16F variant. DX12 typed UAVs follow the view format. These passes load `Path::RuntimeAssets + "Shaders/..."`, not `Path::ResolveAsset`: in loose-file desktop runs `[Shader] Compile(hlsl) -> source=` names the build tree's `RuntimeAssets`, so a project `Assets/Shaders` copy does not replace them there (a game pack maps these paths to its `RuntimeAssets/` entries, [GamePack.cpp](../../../Phasma/Core/Code/Base/GamePack.cpp) `ToPackPath`; HDR declarations verified 2026-10-07).

## Cached Pipelines

- `CommandBuffer::GetPipeline()` caches `Pipeline` objects globally from a `PassInfo` hash. Some callers, such as skybox HDR-to-cubemap conversion, build transient `PassInfo` instances and destroy them after the command buffer finishes.
- A cached `Pipeline` must treat the source `PassInfo` as construction-only state. Runtime command recording should use immutable metadata copied into `Pipeline` at creation time, such as pipeline type and push-constant ranges, instead of reading through the original `PassInfo` reference.
- Vulkan descriptor auto-binding must still run when rebinding resources for the same cached pipeline. Skipping descriptor binds just because the pipeline object is already current can leave stale descriptor sets in place for repeated transient passes.

## Solid-Color Skybox Fallback

When no HDR path is configured, `SkyBox::LoadSolidColor()` builds a 1x1 cubemap. On Vulkan that fill is a transfer clear of all six faces (`vkCmdClearColorImage`), not six `vkCmdCopyBufferToImage` regions. Some ICDs (Mesa Dozen on WSL) report `minImageTransferGranularity = (0,0,0)`, which requires a whole-subresource copy; a per-face 1x1x1 copy then fails `VUID-vkCmdCopyBufferToImage-imageOffset-07738`. A clear is legal on every Vulkan queue, including Android. DX12 has no matching clear without an RTV, so it keeps a packed 6-layer buffer upload. The HDR equirect-to-cubemap path is compute and is unchanged.

## Skybox Runtime Reload

Runtime `skybox.load(...)` exercises this path: `SkyBox::LoadSkyBox()` loads an equirect HDR, dispatches `EquirectangularToCubemap.hlsl` into cubemap mip 0, then dispatches `PrefilterCubemap.hlsl` through another transient compute `PassInfo` to fill roughness-filtered mips for IBL. Startup and runtime reloads should both produce nonzero cubemap memory; a black cubemap after runtime reload points first at descriptor/pipeline binding and transient-pass lifetime.

IBL specular sampling expects those roughness-filtered cubemap mips, with roughness mapped linearly to the mip range (`ComputeIBL_Common()` uses `mip = roughness * (mipCount - 1)`).

A bright HDR sun is a sub-texel, very-high-radiance delta. Naive GGX importance-sampling of it during prefiltering lights up isolated texels on a regular lattice (the sample set is identical per texel, so the sun falls into the same fixed sample slots everywhere), which the floor reflection magnifies into a grid of bright squares. `PrefilterCubemap.hlsl` suppresses this with three load-time measures:

- **`MAX_PREFILTER_RADIANCE`** — clamps per-sample radiance so the delta sun has no high-contrast spike to expose.
- **`SOURCE_MIP_BIAS`** — biases each sample toward a blurrier (pre-averaged) source mip, scaled by roughness, so the integral converges to a smooth blur (low roughness stays sharp). This is the main lever; raise it if squares/blotches return, lower it if rough reflections over-blur.
- **`PrefilterSampleCount`** (in `Skybox.cpp`) — generous counts (64/128/256/512); load-time only.

Per-texel jitter was tried and removed — once the mip bias converges the integral, jitter only trades the grid for swimming grain. The prefilter is a one-time bake at skybox load/reload (`LoadSkyBox` → `PrefilterSkyboxMips`), not a per-frame pass; per-frame IBL is a single `SampleLevel` of the baked mips. If the prefilter failed to compile/run, the mips are black.

## Skinned Motion Vectors

The G-buffer's velocity follows a skinned mesh's bones, not only its node's transform and the camera. Each skinned node's joint tail holds the current pose and then the previous rendered frame's pose (`NodeGpuData.jointCount`, byte 136, tells the shader where the second block starts; the node's data is `sizeof(NodeGpuData) + 2 * jointCount * sizeof(mat4)`). `Scene::UpdateUniformData` rolls `prevJointMatrices` from the last uploaded pose on the node's first upload of a frame (the late script catch-up uploads again without rolling) and keeps a moving node dirty for one more frame, so a pose that stops reads zero motion instead of its last step. `GBufferVS.hlsl` skins `prevPositionCS` with that previous pose; before this TAA smeared animated limbs, whose velocity carried only the camera and node motion (verified 2026-09-29: [Scene.cpp](../../../Phasma/Runtime/Code/Scene/Scene.cpp), [SceneBuffers.cpp](../../../Phasma/Runtime/Code/Scene/SceneBuffers.cpp), [GBufferVS.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/Gbuffer/GBufferVS.hlsl)). Depth, shadow and ray-tracing passes read only the current block at unchanged offsets.

## Motion Blur Sampling

The shared `MotionBlurPS.hlsl` filter converts the existing frame-time-normalized velocity to source-image pixels before choosing its sample count. Samples use symmetric midpoint positions and tent weights. The blur span is capped at the configured sample budget (16 pixels at the default 16 samples, at most 32), keeping adjacent taps no more than one pixel apart. Stretching a fixed number of taps over an unbounded span made thin silhouettes appear as separate translucent copies during fast camera rotation. Longer blur would require a reconstruction filter rather than merely increasing the velocity multiplier.

Color fetches use explicit mip level zero and clamp to half-texel-inset image bounds, so the repeat sampler cannot pull the opposite edge into the blur. Zero strength/blend, a one-sample budget, subpixel motion, and invalid velocity retain the sharp color; filtering preserves its alpha. The effect remains enabled by the normal scene settings, including in the Animator.

Skybox pixels have zero depth and no mesh velocity. `MotionBlurPass` supplies a rotation-only reprojection from the current camera view to its previous view, using the same perspective sky rays as lighting (including its virtual perspective sky for orthographic cameras). The shader uses this for zero-depth pixels instead of skipping them. Camera translation and projection jitter are excluded, so an infinitely distant sky blurs during rotation but remains sharp during translation or stationary TAA jitter. Geometry continues to use the existing velocity buffer.

## Lines And Script Passes

The editor/Animator grid is an analytic world-aligned plane at Y=0 (`GridPass`, `Utilities/GridPS.hlsl`). It alpha-blends into the full-resolution display target after TAA, upsampling and motion blur, with destination alpha preserved. Both the pass-wide and attachment blend switches must be enabled; disabling the former replaces the background with transparent grid pixels and produces a black footprint in the viewport.

Grid spacing follows the projected pixel footprint, cross-fading between world-space decades with persistent major lines. Each line family is antialiased and suppressed before its cells become subpixel; only grazing-angle opacity fades toward the horizon, with no fixed-radius cutoff. Rays start at each pixel's near-plane point and use two finite reverse-Z depths, supporting perspective with an infinite far plane and orthographic cameras. Scene-depth rejection uses the matching jittered depth texel at its own resolution; zero depth is sky. Derivatives are evaluated before divergent discards so object edges cannot corrupt the AA footprint.

- `RenderType::Lines` is reserved for hardware line-strip meshes from `Primitives::CreatePolyline(...)` / Lua `scene.attach_lines(node, {vec3...}, closed)`. These meshes are skipped by the indirect raster buckets, shadow cull/draw, mesh-constants culling path, and ray-tracing BLAS/TLAS triangle path. `LinesPass` draws them directly from the position stream after `LightTransparent` and before TAA, using node uniform data for transforms and material emissive (or base color) for color.
- Lua registers frame-graph callbacks with `render_graph.add_pass{name = ..., order = ..., reads = {...}, writes = {...}, fn = function(cmd) end}` (order in the table since 2026-10-09) and removes them with `render_graph.remove_pass(name)`. `reads` are render targets sampled in the fragment stage (the graph issues their barriers), `writes` the targets the pass renders into; both enter the order checks, and a script pass that declares them may share a column. A scene's `render_pass_orders` key `script:<name>` overrides it; a pass without either runs in its own column after the built-in passes (`kScriptRenderPassUnplacedOrder`). `render_graph.add_fullscreen_pass` adds a native fullscreen shader pass (no Lua per frame). C++ scripts' fullscreen passes keep their `order`; `render_graph.has_pass(name)` also sees C++ scripts' passes (ABI 12), which a Lua reload keeps. Editor and player renderers watch the script-pass registry revision and rebuild the graph before command recording when scripts add/remove passes. The callback receives the frame `CommandBuffer`; `render_graph.get_target(name)` resolves current render targets such as `viewport`, `display`, and `depthStencil` for passes that need to record their own barriers/blits/attachments. Lua `cmd:begin_pass(...)` copies its attachment table into thread-local storage that remains valid until `cmd:end_pass()`, so scripts can safely record manual render passes without owning C++ attachment vectors.

## Ray Tracing Cameras And Geometry

- Full ray tracing must build camera rays differently for perspective and orthographic projections. Perspective rays originate at the camera and use the unprojected per-pixel direction. Orthographic rays originate from the unprojected per-pixel view position and share the engine's positive view-Z forward direction; Hybrid depth clamps are measured from that per-pixel origin. Using perspective-style ray origins for orthographic cameras makes 2D quads/sprites appear as giant screen-filling surfaces in full RT.
- When geometry changes, the RT descriptor set must refresh every resource whose backing object can be recreated: TLAS, scene uniforms, mesh constants, combined geometry buffer, MeshInfo buffer, material table, and image views. Primitive-cache hits share their immutable scene-source metadata but still create an instance mesh index and require a BLAS rebuild, because `m_blasByMesh` is keyed by scene mesh index. Deleted, unreferenced mesh slots and owned material instances are reclaimed; a primitive cache entry promotes another live mesh with the same source before its old slot is recycled. The merged BLAS buffer size must be computed with the same align-before-place math as the build loop so later BLAS ranges stay inside the allocation.

## Global Illumination And Cluster Geometry

PE has engine-native probe GI and resident cluster rendering; these use published algorithms and the existing RHI. Both are opt-in scene settings, saved in `.pescene` and exposed in Scene Settings and Lua. Verified 2026-10-07.

### Dynamic Diffuse GI

[GlobalIlluminationPass](../../../Phasma/Runtime/Code/RenderPasses/GlobalIlluminationPass.cpp) traces an 8×8×8 probe grid with 64 rotating rays per probe, integrates directional irradiance (RGBA32F) and distance moments into bordered octahedral atlases, and keeps separate histories. [ProbeVolume.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/GlobalIllumination/ProbeVolume.hlsl) gathers eight neighbouring probes with trilinear weights, normal bias, distance-based visibility and backface classification. Placement: when the static mesh bounds (enabled, visible mesh nodes; refit on geometry changes, grow-only per scene generation) span at most 7 cells of 4× `gi_probe_spacing` per axis, one volume is fitted to them with per-axis spacing (Sponza about 5×2×3 m) and no edge fade; otherwise the grid follows the camera at `gi_probe_spacing`, fades into environment lighting over its outer cell, and remaps overlapping atlas tiles when the camera crosses a cell (only newly exposed probes start fresh). Pitfall, the bright band: before 2026-10-08 the grid always followed the camera, so with IBL on everything past about 6–8 m fell back to unoccluded sky light. In Sponza's covered aisle the floor jumped from 17 to 63 (the GI-off value) at the box edge, and the edge moved in 2 m steps as the camera flew. With the fitted volume the same aisle stays at 9–18. Pool test `gi-fitted-volume-vulkan`/`-dx12` checks a 40 m covered corridor stays flat (far/near 1.14) and, as a self-check, that a 1 m camera-following box still shows the band (1.53). Scene replacement, spacing or placement changes and a frame without a probe update (GI toggled off, no TLAS) discard history, but lighting still samples the newly updated atlas on that frame. This history is independent of TAA. Verified 2026-10-08.

The pass runs after the G-buffer and before opaque lighting. [LightPass](../../../Phasma/Runtime/Code/RenderPasses/LightPass.cpp) consumes the cache for opaque and transparent lighting; valid probes replace the diffuse environment term while environment specular remains. [RayTrace.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/RayTracing/RayTrace.hlsl) supplies emissive/direct hit radiance, alpha-cut visibility and probe feedback for additional diffuse bounces, and samples the same cache in hybrid/full RT shading. Probe rays ignore alpha-blend/transmission surfaces; shadow rays retain their existing behaviour.

Controls are `global_illumination` (default false), `gi_probe_spacing` (2 world units; camera-following spacing and the fitted-volume limit), `gi_intensity` (1) and `gi_hysteresis` (0.999, the ceiling of the per-probe average).

Pitfall, GI trembling: each probe re-estimates its light every frame from 64 rays whose directions rotate per frame, so a single frame is noisy wherever a few rays catch a small bright surface (sunlit patches, emissives). Any fixed blend lets part of that noise through: at 0.95 history colour bleeding flickered like a candle. Fixed directions removed the flicker (it is the rotation) but never sample the whole sphere; steadying the distance moments changed nothing, steadying irradiance removed it. [ProbeUpdate.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/GlobalIllumination/ProbeUpdate.hlsl) keeps a progressive average instead: each texel weighs the new frame by 1/n, n counting frames since the probe started or the lighting last changed (stored in the distance atlas's z), capped by `gi_hysteresis`, and the active flag shares that blend. [GlobalIlluminationPass::Update](../../../Phasma/Runtime/Code/RenderPasses/GlobalIlluminationPass.cpp) restarts the average (n drops to 49, the old 0.98 rate) when `Scene::GetGiInputVersion` changes (a hash of the packed light data in `UpdateLights`, ray-traced instance moves in `UpdateTLASTransformations`, TLAS rebuilds), when the geometry version changes (geometry, materials, textures, streaming), or when IBL, IBL intensity, shadows or the Disney BRDF setting change; camera movement does not restart it. Irradiance is RGBA32F because a 0.999 history moves texels by less than half precision. Measured: Sponza static camera at 60 FPS, pixels ranging over more than 4/255 across 12 captures 0.3 s apart fell from 12.1% (largest range 38) to 0.08–0.11% (6) in four runs; the emitter scene of `gi-range` in the editor at default settings went from a mean frame-to-frame range of 1.84/255 to 0.34/255 (pixels over 4/255: 15.4% to 0.26%). Response, emissive cube behind the camera: switched off or on, its bounce reaches half in about 1.2 s and is 17–24% short after 4 s. Undetected lighting changes (none known) would take up to about 1000 frames. Restart counts were checked with temporary logging: none idle or while the camera moved; MCP screenshots bump the geometry version. Pool test `gi-flicker-vulkan`/`-dx12` bounds probe irradiance next to a small emitter (1.40 at 0.95, 0.45 with the earlier rise clamp, 0.034 now). Verified 2026-10-08. On screen (2026-10-10, Vulkan, static camera, 30 frames 0.1 s apart grabbed with `PrintWindow` on the editor window, since MCP captures restart the average): at the default 0.999 the pixels swinging more than 4/255 were 0.65% in a Cornell box and 0.10% next to a small emitter, against 0.57% and 0.07% with GI off; at `gi_hysteresis` 0.85, which `gi_range`, `gi_debug` and `gi_scroll` set for fast response, they were 53% and 54% (mean swing 6.3/255 and 11.9/255), visible trembling. In the first 3 s after GI switches on at 0.999 they were 23% and 18% (mostly over 4/255, only 2.4% and 4.5% over 8/255) while the bounce builds up and the average restarts; from 3 s on, the steady values above.

Pitfall, Vulkan sync validation (fixed 2026-10-10): the GI probe pass and the hybrid ray-tracing pass both run `RayTracingPass::ExecutePass`, which refits the TLAS when a ray-traced node moved; the second refit wrote the TLAS while the first pass's trace rays could still read it. `Scene::UpdateTLASTransformations` now refits once per frame (`m_tlasRefitFrame`), and `UpdateVulkanTLAS` issues a barrier just before the in-place build (ray-tracing, compute and fragment acceleration-structure reads to the build); DX12 already had `PrepareBuildBarriers`. Barrier ranges must cover the whole bound buffer: `Buffer` rounds storage sizes up (`AlignStorage`) and descriptors bind the whole buffer, so a barrier sized from a count (shadow-cull indirect buffers at `indirectSize`, the object-ID `ObjectIdNodeVis` at capacity x 24) left the tail unsynchronised between per-cascade dispatches; those barriers now use `Buffer::Size()`, in place, just before each dispatch. The main culling pass still sizes its indirect barriers from `indirectSize` but runs once per frame and is not flagged. Pool tests `gi-flicker`/`gi-fitted-volume`/`gi-scroll`/`cluster-instances`/`cooked-clusters`-vulkan cover them.

Local Vulkan/DX12 checks confirm emissive colour transfer, resizing, toggles and raster/hybrid/full RT operation without GPU validation errors. The algorithm is based on [ray-traced irradiance fields](https://jcgt.org/published/0008/02/01/) and [production DDGI](https://jcgt.org/published/0010/02/01/).

### Resident Cluster Geometry

[ClusterGeometry.cpp](../../../Phasma/Runtime/Code/Scene/ClusterGeometry.cpp) uses meshoptimizer v1.3's maintained [clusterlod.h](https://github.com/zeux/meshoptimizer/blob/v1.3/demo/clusterlod.h), including position/normal/UV/colour attributes, to build clusters of at most 128 triangles and a refinement hierarchy. [ModelAssetCooked.cpp](../../../Phasma/Runtime/Code/Scene/ModelAssetCooked.cpp) writes bounds, simplification errors, refinement links and cluster indices in `.pemesh` v8 only when requested: `PhasmaCook source output --clusters`, `PhasmaCook --batch manifest --clusters`, or the editor's Cook Cluster Geometry checkbox. Default cooking remains v7 without cluster generation. Versions 3–7 build a hierarchy only when the scene enables clusters. Cluster payloads are range checked and reject nonfinite bounds/errors and invalid refinement links. Re-saving a model without `--clusters` (Animator timeline save, rig bake) keeps each hierarchy that still validates against its mesh and drops it when the mesh became skinned, non-opaque or changed vertex count, because the reader rejects the whole file when a skinned mesh carries clusters; the file is v8 only while some mesh keeps a hierarchy. No automated check covers this path (no headless re-save; verified by build and review 2026-10-07).

[Scene](../../../Phasma/Runtime/Code/Scene/Scene.cpp) builds/uploads resident cluster metadata and extra indices only while the scene enables clusters. `Scene::UpdateClusterGeometry` rebuilds the store on every full geometry upload: meshes that share a geometry range (instances) share one uploaded hierarchy, deleted meshes drop out, and generated hierarchies are cached by `{vertexOffset, vertexCount, indexOffset, indexCount}` because the geometry stores are append-only until the scene clears. Before 2026-10-07 every instance appended its own copy and deleted meshes kept theirs while clusters were on; pool test `cluster-instances-vulkan` checks that ten sphere instances and spawn/delete churn keep the one-sphere size (1,984 bytes). With the feature off, the cluster binding has a 64-byte placeholder and indirect capacity follows normal meshes; disabling it releases cluster CPU storage and recreates GPU geometry/indirect buffers without the extra data. Allocator pools can retain freed GPU memory. [CullingCS.hlsl](../../../Phasma/Runtime/RuntimeAssets/Shaders/Compute/CullingCS.hlsl) assigns one workgroup to each instance while cluster rendering is enabled, spreads cluster selection across 64 threads, and selects a consistent hierarchy cut by projected pixel error. Bounds conservatively cover nonuniform scale and shear. Frustum/Hi-Z tests emit ordinary indexed indirect draws, including both depth phases; depth, G-buffer and [object-ID perception](../../../Phasma/Runtime/Code/Render/ScenePerception.cpp) draw limits use expanded indirect capacity. The original geometry remains available for shadows and BLAS.

Controls are `cluster_geometry` (default false) and `cluster_error_pixels` (1 pixel). The path handles static opaque meshes. Skinned, alpha-cut, blended, terrain and voxel geometry retain their existing paths. All hierarchy/index data stays resident; there is no imported-mesh page streaming, visibility-buffer material resolve, software rasterizer or mesh-shader dependency. A GPU memory budget and demand paging are required before treating it as virtualized geometry for assets larger than VRAM. Vulkan still advertises `caps.meshShaders=false`.

Local checks cover hierarchy selection (7,938 to 122 triangles on a curved test mesh), malformed payload rejection, opt-in v8/default v7 cooking, object-ID coverage, off/on/off allocation sizes and Vulkan/DX12 frustum-only and two-phase Hi-Z culling. Small scenes can spend more time on cluster selection and draw setup than they save in rasterization; profile before enabling it.

Sponza Release comparisons on an RTX 4080 SUPER use immediate presentation and ten snapshots one second apart. Fresh feature-off controls against the fixed original LDR baseline changed FPS -0.3% on Vulkan and -0.1% on DX12, GPU time -0.058/-0.039 ms and application VRAM +14/0 MB, within the project thresholds. A separate cluster-only off/on/off run, with no preceding HDR allocations, added 11/13 MB application VRAM and 11.7/14.8 MiB resident buffers. This includes about 5.0 MiB of extra indices, 0.25 MiB of metadata and expanded indirect/storage buffers. First activation on legacy v7 Sponza assets took 313/328 ms from the setting request to visible uploaded metadata, including CPU generation, GPU buffer rebuilding and frame/MCP scheduling. `Scene::UpdateClusterGeometry` has a CPU profiler scope. Disabling restored the initial application VRAM and buffer sizes. Earlier cluster comparisons had included those allocations in the disabled baseline and understated their cost. Verified 2026-10-07.

### HDR Boundary

[SceneRenderTargets.cpp](../../../Phasma/Runtime/Code/Render/SceneRenderTargets.cpp) uses RGBA8 by default. The saved/Lua `hdr` setting defaults to false; hardware-RT GI also activates HDR so indirect radiance is preserved. In HDR, lighting, emissive, TAA history and bloom use RGBA16F. [SceneRenderGraph.cpp](../../../Phasma/Runtime/Code/Render/SceneRenderGraph.cpp) orders TAA or upsampling, bloom, DOF and motion blur before [TonemapPass.cpp](../../../Phasma/Runtime/Code/RenderPasses/TonemapPass.cpp), which converts to RGBA8. RCAS, FXAA, colour grading and overlays run afterwards. The conversion pass also runs with ACES disabled; disabling tone mapping changes the curve, while display conversion remains necessary. TAA history is copied before bloom and tone mapping; RCAS receives tone-mapped values. Live HDR changes resize targets and rebuild format-dependent pipelines and graph order on both hosts. LDR retains its previous pass order and allocation formats.

The [Player](../../../Phasma/Runtime/Code/Render/RuntimeSceneRenderer.cpp) defers LDR bloom and colour grading until after runtime UI, preserving existing HUD bloom. HDR scene bloom runs before tone mapping and UI; only colour grading is deferred. Player checks verify this distinction on Vulkan/DX12. RGBA8 lighting clips radiance above 1.0 before ACES; opt-in HDR range checks distinguish emissive 2 from 4 with TAA/RCAS on and off. The display image is retained across same-size HDR changes, and target creation uses exact names so the LDR `hdrDisplay` lookup fallback cannot substitute an RGBA8 allocation. Pipeline refresh preserves compute descriptors that do not depend on scene colour. A Vulkan saved-Sponza check covers uncached TAA compilation and HDR switches without validation instrumentation. Verified 2026-10-07.

RGBA16F doubles per-pixel storage for converted images; GI has additional caches/history. Against the fixed original LDR Sponza baseline, optional HDR changed FPS -5.2%/-4.4% and application VRAM +96/+128 MB on Vulkan/DX12. GI with clusters and HDR changed FPS -14.3%/-14.0% and VRAM +125/+158 MB; these are total enabled-path costs, not GI alone. Optional paths exceed the default regression budgets. Several DX12 runs, including cold feature-off controls, contained a two-second stall inside `Present`; failed raw captures were retained, and complete ten-snapshot controls were repeated rather than trimming samples. The fresh controls above passed. These numbers are scene/hardware specific; Android HDR/GI and in-game bloom remain unverified. Verified 2026-10-07.

### Linear Colour

Without `linear_color` nothing decodes sRGB colour inputs or encodes the image: albedo is lit as stored bytes, the sky is linear, and the UNORM display target goes to the UNORM swapchain unchanged (survey 2026-10-10). The per-scene `linear_color` setting (default false; saved, Lua, a Pipeline-panel checkbox next to HDR) follows Unreal's model and forces HDR scene colour ([SceneRenderTargets.cpp](../../../Phasma/Runtime/Code/Render/SceneRenderTargets.cpp) `SceneUsesHDR`, `SceneUsesLinearColor`, `SceneColor`). Spec and plan: [design](../../superpowers/specs/2026-10-10-linear-color-design.md), [plan](../../superpowers/plans/2026-10-10-linear-color.md).

- Textures: RGBA8/BGRA8/BC1/2/3/7 UNORM images are created with `mutableFormat` (Vulkan `MUTABLE_FORMAT | EXTENDED_USAGE`, DX12 typeless resource) and `Image::GetSrgbSRV` makes a second, sample-only sRGB view ([Image.cpp](../../../Phasma/Core/Code/API/Image.cpp), [VulkanImageViewImpl.cpp](../../../Phasma/Core/Code/API/Vulkan/VulkanImageViewImpl.cpp), [Dx12ImageImpl.cpp](../../../Phasma/Core/Code/API/DX12/Dx12ImageImpl.cpp)). `Scene::UpdateImageViews` keys the bindless table by view and gives base colour (slot 0) and emissive (slot 4) the sRGB view when the scene is linear ([SceneBuffers.cpp](../../../Phasma/Runtime/Code/Scene/SceneBuffers.cpp) `MaterialSlotView`); raster, ray-traced and GI probe hits share that table. Named textures of custom passes keep the UNORM view. Mips stay averaged in encoded space.
- Authored colours (material factors, vertex colours, light colours in `UpdateLights`, sprite tints, lines, AABBs, selection outline, fallback sky) stay stored as picked (sRGB) and are decoded where they enter the frame; values above 1 keep their brightness (`SrgbToLinearHdr`: the colour over its largest channel is decoded, then scaled back).
- The 8-bit G-buffer albedo is stored sRGB-encoded (`GBufferPS`, terrain, voxel) and decoded by `LightingPS` and `SSRPS`, as Unreal's sRGB GBufferC; emissive goes linear into the RGBA16F target.
- `TonemapPS` ends with the single `LinearToSrgb`; Sharpen, FXAA, colour grading, grid, particles, runtime UI and ImGui stay after it on display values. Terrain layers, skyboxes and the voxel atlas were already linear and are unchanged.
- Toggling rebuilds the table (`m_linearColorViews` in `Scene::Update`), reloads the sky only while the solid fallback shows (`SceneSkyIsFallback`) and repacks lights, which restarts GI averaging. In a linear scene every resident colour texture's sRGB view is also in the table (`Image::CanSampleAsSrgb`), so `TryBindCachedTexture` hits for sprite and material swaps instead of forcing a texture rebuild. Vertex colour and base-colour factor are decoded separately (the sRGB curve does not distribute over a product). Lua `create_image` colour images are mutable too.
- Mutable colour images are typeless resources on DX12: `Dx12BlitImage` and `Dx12ImageImpl::Blit` compare and build pipelines from the typed view format. Open (2026-10-10): `MUTABLE_FORMAT` on every colour texture may disable compression on some drivers (AMD DCC, Mali AFBC) even with the switch off; only an RTX 4080 SUPER was measured, and a `VkImageFormatListCreateInfo` limited to the UNORM/sRGB pair would keep it on but would break WebGPU textures that declare other view formats. WebGPU textures with extra view formats also become typeless on DX12; the WebGPU suites were not run.

Pitfalls: scene render targets have no transfer-source usage, so `capture_image_resource` cannot read `rt:emissive`/`rt:normal`, and `take_scene_screenshot` `target: viewport` returns `rt:viewport`, the scene colour before Tonemap. The pool test reads `rt:display` cropped to the `Viewport` panel from `query_imgui_windows` (window origin = `##MainMenuBar` corner). Normal maps on primitives render black (no tangents) with or without linear colour (2026-10-10).

Verified 2026-10-10 by pool tests `linear-color-vulkan`/`-dx12`: emissive colours, an HDR emissive (G/B 158/80 at factor 1.6, 0.8, 0.4) and an sRGB-128 emissive texture show as authored across on/off toggles; a lit plane matches values derived from off mode within 2/255; a base-colour texture equals the decoded factor while a metallic-roughness texture is not decoded; a (1, 0.5, 0.25) point light decodes to G/R 0.214; GI bounce is brighter once encoded; with the switch off, Sponza and a mixed scene match the pre-change binary byte for byte at the scene-colour target. Cost on an RTX 4080 SUPER, Sponza editor, immediate present, medians of 10 snapshots in both run orders: linear on versus `hdr` on changed the G-buffer pass by 0.000 ms (Vulkan) / -0.002 to -0.009 ms (DX12), the whole GPU frame by +0.000 to +0.003 ms, Tonemap by +0.001 ms; mutable/typeless colour textures with the switch off changed the frame by -0.001 ms (Vulkan) / +0.003 ms (DX12). Editor FPS at these rates varied 546-746 between identical runs, so the first spike-skewed average (-6.3%) was not a regression.

## ImGui Platform Windows

Editor and Animator panels dragged outside the main window become their own OS windows (ImGui multi-viewport) on Vulkan and DX12. [GUIBackend::ConfigureIO](../../../Phasma/Editor/Code/GUI/Backends/GUIBackend.cpp) sets `ImGuiConfigFlags_ViewportsEnable`, but ImGui silently clears the flag each frame unless both the platform and the renderer backend report `...HasViewports`. The vendored `imgui.cpp` is the docking branch (upstream `a4ebe3d5`), while the old `third_party/imgui/imgui_impl_vulkan.cpp` was the master-branch file with no viewport code, so floating panels never left the window on Vulkan. Both renderer backends now live in [Runtime/Code/UI/Backends](../../../Phasma/Runtime/Code/UI/Backends/): `imgui_impl_vulkan` is the docking-branch file from that same upstream commit, and `imgui_impl_dx12` is PE's adapted copy. When updating the vendored ImGui, take both backends from the matching docking commit. [GUIBackend::RenderPlatformWindows](../../../Phasma/Editor/Code/GUI/Backends/GUIBackend.cpp) wraps `UpdatePlatformWindows`/`RenderPlatformWindowsDefault` in the main queue's submit mutex because the upstream backends call `vkQueueSubmit`, `vkQueuePresentKHR` and `vkDeviceWaitIdle` directly while worker threads submit through `pe::Queue`. Pool test `editor-viewports-vulkan` floats the Console via `imgui.ini` and checks for its OS window. Verified 2026-10-05: Vulkan (with validation, zero errors) and DX12 floating windows render, and the platform window survives a module hot reload.
