# Runtime UI

Runtime/game UI is a backend-neutral service in `PhasmaRuntime` with concrete renderer implementations outside PhasmaCore. The runtime-facing API is intentionally small: screens can be shown/hidden and populated with prototype text, number, bool, button, image, and positioned quad widgets. Public runtime and Lua call sites do not include ImGui types.

The first concrete player backend is Dear ImGui. Its implementation lives under `Phasma/Runtime/Code/UI/Backends`, but it is compiled into `PhasmaPlayer` at the host boundary so PhasmaRuntime still exposes only backend-neutral UI APIs and the editor does not link a second ImGui renderer. The player creates that backend, sends SDL events to runtime UI before gameplay input, exposes UI capture state to runtime input bindings, and renders the UI after the render graph has produced the display target but before `BlitToSwapchain`. Bloom and colour grading are deferred out of the graph in the player (`SceneRendererCore::SetPassDeferred`) into a second render graph executed after that UI composite, so HUD and menus get the same look as the scene instead of being pasted on top of a finished frame. Deferred passes keep their graph order and still run through `RenderGraph`, so each one's declared input barriers are issued. The scene-side passes stay in the main graph: FXAA antialiases the viewport target before upsample, and TAA and its RCAS sharpen need motion vectors and projection jitter that runtime UI has not got. The editor defers nothing, so its authoring preview shows runtime UI without bloom or grading. The standalone player and editor-hosted play event pumps reserve Ctrl+T as a RenderDoc capture shortcut before runtime UI capture is applied, so GPU captures remain reachable while a HUD has keyboard focus; in the editor, the shortcut is also active while the editor UI is hidden for clean captures. Android feeds the current system-bar/display-cutout safe area from `PhasmaPlayerActivity` into the runtime UI frame so player HUD windows are inset from status/navigation bars while the scene still renders full-surface; the player resolves SDL drawable-size changes before starting the UI frame so Android rotation cannot pair fresh insets with a stale swapchain extent.

The editor also hosts the same `RuntimeUiSystem` and Lua `runtime_ui.*` surface with the shared Dear ImGui runtime backend. The backend owns a separate ImGui context and renders into the editor display surface before the editor GUI pass submits its draw data, so runtime UI becomes part of the Viewport image rather than an editor overlay. Editor input maps the Viewport image rectangle back into the runtime surface coordinates before reaching runtime UI; when editor chrome is hidden, the mapping falls back to the full window. Leaving editor play mode clears all runtime UI screens after PlayerOnly script destroy hooks run, so script-generated widgets do not survive the restored scene snapshot; authored Runtime UI scene nodes are repopulated by the normal scene sync path on the next frame. **Escape stops editor Play, including paused Play:** `GUI::Update()` handles the non-repeating key press before its hidden-GUI early return and calls the normal `Stop()` path to restore the authoring snapshot and editor chrome. `Stop()` also releases relative mouse capture after script teardown. This shortcut belongs to PhasmaEditor; standalone PhasmaPlayer keeps the game's Escape handling. Two input behaviors are load-bearing here. First, stock `imgui_impl_sdl2` re-injects the raw window-relative mouse position from global mouse state on every NewFrame while no button is held, bypassing the event mapping; the runtime backend queues the surface-mapped position again after `ImGui_ImplSDL2_NewFrame` (`SyncMousePosition`), otherwise hover and clicks land on the wrong widgets whenever the Viewport image is offset or letterboxed. Second, hosts publish UI capture state to `InputState` once per frame by plain assignment after event polling; an OR-latch there sticks after the first captured frame and permanently disables Lua `input.*` polling (dead fly camera). UI capture masks mouse buttons, mouse motion, mouse wheel, touch, and keyboard text; the editor only forwards uncaptured wheel deltas to Lua when the cursor is inside the SceneView image (or the full window while editor chrome is hidden), so viewport zoom/follow controls do not fire while scrolling another widget or editor panel. Lua scripts that need to coexist with other camera scripts can use `input.peek_mouse_delta()` to read the current frame's uncaptured mouse delta without consuming it; `input.get_mouse_delta()` remains the consuming variant for single-owner controls. The editor Viewport can present the copied scene image in a fixed aspect rectangle, such as phone portrait, without resizing the widget or editor layout; the unused panel area is black, the editor camera aspect follows the selected mode while the GUI is visible, and the mode persists in `.pescene` global settings as `scene_view_aspect_mode`. SceneView also overlays a transparent active-camera orientation gizmo inside the rendered image rect (drawn by the shared `GUI/OrientationGizmo.h`, which PhasmaAnimator's viewport uses too): red Right/X, blue Front/Z, and green Up/Y arrows are projected from the active camera orientation, clicking an arrow snaps the camera to that world direction while preserving position, and viewport picking is suppressed while an arrow is hovered or active. The orientation gizmo and the other SceneView gizmos are editor-only `PhasmaEditor` UI state, controlled from the Gizmos menu rather than serialized scene/runtime state. RmlUi is reserved as a future backend that can plug into the same lifecycle/event/render surface without rewriting runtime/game call sites.

`RuntimeUiSystem::Shutdown()` waits for GPU idle before asking the active backend to release renderer resources, because the backend owns per-frame buffers, texture descriptors, font resources, and pipelines that may have been referenced by the last submitted scene command buffer.
