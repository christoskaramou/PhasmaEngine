# Runtime UI Helper Surface

Image-style quads accept `radial_segments` (0 disables it, 1-64 enables discrete pie slices) and `radial_filled` (clamped to the segment count). The shared ImGui backend draws the fill clockwise from twelve o'clock with antialiased edges and small gaps. Empty slices remain transparent; radial fills suppress the image-placeholder accent rectangle. A single segment uses a filled circle. These are geometry fills and do not allocate textures. Normal image quads retain their existing rendering. Text-only labels must use zero fill alpha to avoid requesting a themed paper plate.

Runtime UI is the current 2D-facing helper path. It stays backend-neutral in `PhasmaRuntime`: callers create or update named screens and generic widgets, then the active host backend draws them. The runtime UI layer does not create game-specific overlays, debug panels, or sample content by itself.

The Lua `runtime_ui` table exposes helper operations for visibility, titles, screen overlay/scroll/max-height settings, clearing/removing widgets, text, numbers, booleans, buttons, images, bool reads, button click consumption, positioned quads, frame surface size, and generic widget state reads. Image widgets are generic path-backed runtime UI resources: `runtime_ui.set_image(...)` resolves asset-relative path/resource strings, caches loaded `Image` resources in the runtime UI system, and asks the active backend to draw an engine `Image*` through its own descriptor/texture mapping. Quad widgets additionally memoize that resolution per widget: `set_quad` re-resolves its image only when the widget's path string changes, so per-frame quad updates do not pay the filesystem candidate-probe/canonicalization cost on every call. `runtime_ui.set_quad(...)` draws a positioned generic quad with optional text/image styling and can mark it draggable; an optional `style` field selects the quad's visual style (`text`, `panel`, `card`, `button`, `image`), defaulting to the `card` look (an accent "art" header above small label text), while `text` is the plain filled-rect-with-aligned-body style used for clean tooltips/labels; an optional `fit`/`auto_size` boolean makes a `text` quad ignore its width/height and snap tightly around the measured text (max line width and line count plus padding), so cursor tooltips size themselves to their content; `runtime_ui.get_surface_size(...)` reports the render-surface coordinate space used by quad positions and widget mouse state; `runtime_ui.get_state(...)` returns hover, click (left `clicked` plus `right_clicked`), drag, release, mouse, and drag-delta state for gameplay scripts to interpret. Positioned quads sort by `z` before rendering and picking, with higher `z` drawn on top unless `bring_to_front` is set. Editor hosts pass the scene-view image rect in window-client coordinates into the runtime UI input mapper so overlay hit tests line up with the image copied into the viewport. Runtime UI quads can also be backed by scene nodes tagged with the generic Runtime UI component; the editor can select those nodes by clicking the rendered quad and manipulate their screen-space rect with the transform gizmo. Runtime UI nodes may be hierarchy groups too: selecting a group uses the bounds of descendant runtime UI quads, so moving a parent group moves all child UI widgets through normal scene transforms. This is intentionally functional UI plumbing, not project/game logic. Dear ImGui is the active backend for now, and future UI renderers can attach behind the same lifecycle, input, and render hooks.

Projects may opt into style-specific runtime UI materials with `runtime_ui.set_style_background(style, path)`, where `style` is `card`, `panel`, `text`, `button`, or `image`; the engine owns no project texture paths. `RuntimeUiSystem` caches each registered image and applies it to authored and script-created quads of that style. Because those materials are global per style, a single button that must differ from its theme (a destructive action, a variant plate) sets its own `image`: the Button branch draws a plate plus caption and never draws a foreground image, so for that style `image` replaces the registered style material instead of layering over it. Texture-backed widgets suppress authored color borders, while selected and hovered states use restrained material tinting instead of replacement frames. Runtime UI has independent RGB multipliers for foreground elements and page backgrounds: `runtime_ui.set_element_tint({r, g, b})` affects normal widgets, while `runtime_ui.set_background_tint({r, g, b})` affects only quads authored with `use_background_tint = true`; `runtime_ui.set_global_tint(...)` remains the shorthand for setting both. Projects that need a lighter foreground material use `runtime_ui.set_element_whiten(amount)`: the clamped 0-1 amount creates a cached load-time variant that lifts light pixels toward white in proportion to luminance, leaving dark line art and source alpha intact. It applies to normal images and registered style plates, never to background-channel quads or the world renderer. A quad or authored Runtime UI node may set `image_whiten` to an explicit 0-1 value to use its own cached variant instead of inheriting that global element lift. Tint and whitening preserve text and authored state colors; neutral white resets RGB tint and zero resets whitening. Single-line controls center their content horizontally and vertically by default; multiline content defaults to top-left flow, and explicit alignment values always take precedence. `runtime_ui.set_text_scale(scale)` applies one clamped 0.5-3.0 multiplier to every authored and script-created Runtime UI quad while retaining each widget's authored relative font size. Accessibility scaling affects glyphs rather than authored padding or image layout, and the backend does not shrink requested text back down to fit a fixed texture. Quad draw lists use the full display clip while text is emitted, so enlarged glyphs remain visible beyond a small authored plate instead of being cut off; projects remain responsible for choosing layouts that avoid unwanted overlap at their supported scale range. Script-created quads can reserve a right-side child-image region with `text_inset_right`; the remaining text region is aligned normally. When `PE_PROJECT_VARIANT=<name>` is set, the backend first tries `Fonts/RuntimeUi.<name>.ttf`; variant names accept only letters, digits, underscores, and hyphens. It then falls back to the generic project override `Fonts/RuntimeUi.ttf`, DejaVu Sans, and Inter. Each loaded face uses the existing Greek glyph range and a 4x rasterization density so large authored HUD text does not enlarge a low-resolution glyph atlas.

The editor authoring path creates those Runtime UI quads as normal scene nodes. The `UI Editor` widget and the Hierarchy `Add > UI` submenu create authored `Component_RuntimeUi` nodes for panel, text, button, and image widgets; dragging an element from the widget into the Viewport places it in runtime UI surface coordinates, and dragging it into the Hierarchy creates it at the root or under the target node. Selected UI nodes use the standard hierarchy, transform, undo, selection, and Properties workflows: local/world X/Y define the screen rect origin, scale defines width/height, and Z defines draw/pick order. Authored Runtime UI components serialize a `runtime_ui` payload in `.pescene` / `.peprefab` files, including optional action metadata. Properties exposes the action trigger as a fixed dropdown (`click`, `hover_enter`, `press`, `release`, `drag_start`, `dragging`, `drag_release`) plus an `action_function` script callback name; drag actions require the component's Draggable toggle. When the selected action fires, `RuntimeUiSystem` asks the node's script instance to call that function with an event table containing the action name, widget id, screen id, node handle, mouse position, and drag/click state. Script-owned Runtime UI tags remain transient unless explicitly converted in Properties. Each editor/player frame, `RuntimeUiSystem::SyncSceneWidgets` converts visible authored Runtime UI nodes into backend-neutral quad widgets so the active backend renders them without coupling scene serialization to Dear ImGui.

Sprites are an editor-authored scene component over the normal mesh/material renderer, not a dedicated sprite render pass. `Component_Sprite` stores image path, `.sprite.json` metadata path, current frame/UV/tint/size, cached frame/clip metadata, playback settings, and an opt-in interpolation flag. Sprite clips advance by changing the quad mesh UVs during `Scene::Update()`; transient changes are deduplicated and packed into one shared staging allocation at the front of the normal editor/player frame command before rendering, with no separate GPU submission or wait, while explicit frame edits still mark geometry/document state normally. When `.sprite.json` sets `"interpolate": true`, the quad carries the current and next atlas UV rectangles plus the fractional clip time through its existing vertex payload, and the depth, GBuffer, and object-ID pixel shaders alpha-crossfade both samples just as particle animation interpolates adjacent atlas frames. Sprite metadata can optionally name an authored silhouette sidecar whose frames contain a fixed number of paired inner/outer vertices. Setup loads that geometry once and adds one actor-owned alpha-blend strip while leaving the main sprite quad alpha-cut and depth-writing; frame changes reuse the strip and join the same batched vertex upload, and `sprite.set_outline_color` recolors only the strip for hover or selection. Procedural primitive instances normally share immutable cached geometry, but sprite setup gives each animated quad its own four-vertex UV ranges so advancing one actor cannot change another actor's frame. Rebinding a texture that is already resident patches only the affected mesh constants in that same frame command instead of rebuilding the scene texture table and synchronously draining the graphics queue. Lua `material.preload_textures(paths)` batches missing material-image uploads so projects can make first-use assets resident outside gameplay; `runtime_ui.preload_images(paths, colorize)` provides the equivalent batch path for normal or colorized UI images and retains each caller path as a direct cache alias so a later first-created quad does not repeat path probing/normalization. `runtime_ui.remove_many(screen, ids)` erases transient widget sets in one pass instead of rescanning the screen vector for every id, while `runtime_ui.set_many_visible(screen, ids, visible)` hides and restores retained widget sets without destroying cached image state. `sprite.setup` accepts only a live four-vertex quad and validates that contract before creating a component, loading an atlas, or changing material state. Its options table may set `whiten` to a clamped 0-1 load-time white lift; the resulting atlas variant shares the image cache with Runtime UI, preserves dark line art and alpha, and adds no per-frame shader work. Sprite-authored materials use base texture alpha plus emissive texture color for unlit rendering through the existing transparent GBuffer/lighting path, and Hybrid mode skips sprite component quads in the ray-tracing TLAS so the raster transparent path owns them once. Sprite quads preserve paired triangle windings for front-cull raster, while script-authored flat cards or slabs can use `material.set_double_sided` so alpha-cut meshes enter the no-cull depth and GBuffer double-sided lists. Sprites inherit normal transform, hierarchy, scene save, prefab, and snapshot behavior. Lua exposes `sprite.create` / `sprite.setup` (Runtime player path: create a textured quad + `Component_Sprite` from `.sprite.json`, or bind metadata onto an existing quad), plus `sprite.reload`, `sprite.play`, `sprite.pause`, `sprite.stop`, frame selection, speed/loop/interpolation controls, and frame/clip queries for gameplay scripts. Regular material helpers such as `material.set_texture(node, path)` remain available for non-sprite meshes.

The direct sprite-outline pipeline explicitly enables attachment blending and applies a minimal reverse-depth-aware bias so the transparent exterior fringe passes the scene depth test without writing depth.
