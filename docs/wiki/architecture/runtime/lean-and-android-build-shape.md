# Lean And Android Build Shape

The top-level build exposes host and dependency switches so mobile/packaged runtime builds can avoid desktop-only surfaces: `PE_BUILD_EDITOR`, `PE_BUILD_LAUNCHER`, `PE_BUILD_MCP`, `PE_BUILD_PLAYER`, `PE_BUILD_PROFILER`, `PE_WEBGPU`, `PE_ENABLE_ASSIMP`, `PE_ENABLE_RUNTIME_SHADER_COMPILER`, and `PE_ENABLE_RENDERDOC_CAPTURE`. Android defaults the desktop hosts, WebGPU, Assimp, and runtime source-shader compiler off while keeping `PhasmaPlayer` available as the runtime host entrypoint. Desktop defaults keep the previous editor/player-oriented shape, with RenderDoc capture API loading opt-in so regular builds do not probe RenderDoc libraries.

The Android player scaffold lives under `Phasma/Player/android`. Gradle drives the root CMake project through Android Gradle Plugin, builds `PhasmaPlayer` as `libmain.so`, subclasses SDLActivity, and extracts packaged `Assets/` into app-private storage before native startup. The scaffold targets Gradle 8.9+, Android Gradle Plugin 8.7.3, NDK 28.2.13676358, and SDK CMake 3.22.1. Android CMake requires source roots for full SDL2 and SPIRV-Cross through `PE_ANDROID_SDL2_ROOT` and `PE_ANDROID_SPIRV_CROSS_ROOT`; the in-repo SDL2 and SPIRV-Cross folders are headers-only for this purpose. Android also builds VMA with dynamic Vulkan function loading and uses the existing Vulkan-Hpp dispatcher for Vulkan 1.1+ entrypoints so it does not link directly against symbols that Android's NDK `libvulkan.so` does not export. The Android player allows portrait and landscape user orientations before SDL window creation, and the Vulkan swapchain prefers `IDENTITY` `preTransform` because the renderer currently draws unrotated frames rather than app-side pre-rotating for Android `currentTransform`.

The Android Gradle build defaults to `arm64-v8a` for physical-phone APKs, but the ABI filter is configurable with `-PandroidAbiFilters=x86_64` for emulator diagnostics. Android x86/x86_64 builds do not force GLM's SIMD intrinsic path because the NDK/GLM combination can otherwise select SSE/AVX code that fails before the player target reaches link. GPU-facing C++ structs cannot rely on GLM's implicit `vec4` alignment on that scalar x86 path: push constants that carry `float4`/`vec4` data must force std430-compatible 16-byte alignment and assert fixed offsets. The culling pass does this for its frustum-plane array so the emulator, physical Android, and editor all write the same layout the SPIR-V shader reads.

The Android manifest gives both the application and launchable SDL activity an explicit `PhasmaPlayer` label plus adaptive launcher icon resources. Some launchers hide or de-emphasize debug APKs whose badging reports an empty launchable icon, even though `cmd package resolve-activity` can still start the package.

The sole exported Android component is the `MAIN`/`LAUNCHER` activity: [Android requires launcher activities to be exported](https://developer.android.com/about/versions/12/behavior-changes-12#exported). Its [manifest](../../../../Phasma/Player/android/app/src/main/AndroidManifest.xml) has a local `nosemgrep` comment for that expected scanner finding. [PhasmaPlayerActivity.getDebugLaunchExtras](../../../../Phasma/Player/android/app/src/main/java/dev/phasma/player/PhasmaPlayerActivity.java) gates all profiler arguments and `PE_*` environment extras on `ApplicationInfo.FLAG_DEBUGGABLE`, and rejects redelivered Recents intents. Release APKs ignore these externally supplied diagnostic options; adb harness launches that need them must use a debuggable APK. Verified 2026-10-05.

When Assimp is disabled, `PhasmaRuntime` excludes `ModelAssetAssimp` sources and runtime model-file loading reports that it is unavailable; primitive/model helpers that do not need Assimp still remain compiled. The runtime primitive factory supports `cube`, `sphere`/`uv_sphere`, `ico_sphere`, `plane`, `grid`, `cylinder`, `cone`, `pyramid`, `quad`, `circle`, and `torus`, and serializes primitive metadata so these generated meshes round-trip through `.pescene` without Assimp. Generated spherical primitives mirror longitude U relative to geometric theta so equirectangular planet maps render in their expected east/west orientation. When the runtime shader compiler is disabled, the Vulkan source-shader compiler path does not include shaderc or DXC and source shader compile entrypoints fail explicitly instead of pulling those dependencies into the mobile runtime. Android also avoids desktop prebuilt library directories and initializes `Path::Root`, `Path::Executable`, and `Path::Assets` from SDL's app-private storage path.

Cooked `.pemesh` files are the runtime model contract. Format v4 stores the GPU-ready geometry streams, a material table (PBR scalar state, texture masks, and five relative texture slots), and a skeleton + animation-clip table for skinned meshes; each TRS key also stores its outgoing interpolation mode. The loader remains backward-compatible with v3 and assigns Linear interpolation to its legacy keys; v5 appends each clip's optional extracted root-motion track, v6 its ruler markers, and v7 the skeleton's planar-2D flag plus each bone's bind length and spline flag. For a planar skeleton, pose evaluation rebuilds every spline chain's final skinning frames from neighboring XY stations, so Catmull-Rom-weighted flat meshes follow a smooth tangent frame instead of thinning at authored FK joints; non-planar and older assets keep the previous evaluation path. `ModelAssetCooked::ReadAnimations` reads only the skeleton and clips of a file without touching the GPU: PhasmaEditor polls the write time of every cooked model in the scene every two seconds and, when the Animator re-saves one, swaps its clips into the live model in place as long as the skeleton on disk still matches by bone names and parents (a changed skeleton or geometry still needs a scene reload; a playing state whose clip index no longer exists simply stops). `ModelAssetCooked::WriteToFile` copies referenced texture files beside the cooked output at those serialized paths so editor import, the desktop cook host, and Android prebake staging share one self-contained asset path. Vertex joint/weight skinning data already rides in the cooked PBR vertex stream, so the skeleton table only adds bone bind/offset matrices and per-bone TRS keyframe channels; `ModelAssetCooked::Load` rebuilds the skeleton/clips on the CPU and uploads material textures through a single command buffer. Embedded `.glb` textures are extracted during cook: `ModelAssetAssimp` exposes the retained `aiScene` image bytes via `GetEmbeddedTextureBytes`, and `ModelAssetCooked::WriteToFile` writes the original encoded PNG/JPG verbatim beside the cooked output as `<stem>_embedded<N>.<ext>`, then references it like any external slot (raw uncompressed embedded textures, which glTF rarely uses, still fall back to the default). In the editor every scene-load affordance (browser double-click, hierarchy/viewport drag-drop, the File > Load Cooked Mesh picker, and the Models palette) operates on `.pemesh`; source models (glTF/FBX/OBJ/...) are import-only through File > Import, which cooks them.

Meshes without bones cook with zero skinning weights in both the PBR and depth/shadow vertex streams. This keeps static props outside the skinning path when the scene also contains animated meshes. Static assets cooked with the old unit-weight default must be recooked and the scene reloaded.

Android does not use the desktop CMake runtime-asset copy target; Gradle stages the APK assets instead, excluding the large glTF sample model and Sponza model folders — and all of `Scenes/**` — so startup is not coupled to local editor scene files. The startup scene and `editor_config.json` are shipped as tracked Android-local assets under `app/src/main/assets/Assets/` (`Scenes/android_physics_balls.pescene` plus an `editor_config.json` that restores it), rather than from local source-tree scene files which `.gitignore` treats as user scenes; this keeps a clean-checkout APK deterministic instead of bundling whatever local scene files happen to exist. The default Android scene is a primitive-only physics loop: it builds a static box container, spawns 10 colorful dynamic spheres above it, deletes the batch after five seconds, and repeats.

`PlayerHostDesc::fileWatchersEnabled` defaults to false. The player host temporarily applies that setting through `FileWatcher::SetEnabled`, so packaged/runtime hosts can start without shader/script file-watch threads while editor-style hot reload remains opt-in for hosts that request it. The desktop `PhasmaPlayer` entrypoint opts back into watchers for development parity; the Android `SDL_main` entrypoint keeps the packaged default.

The desktop player logs which clean exit path stopped its frame pump: SDL window close, Lua `engine.quit()`, or script play-mode shutdown. A matching `Player frame pump stopped cleanly` line confirms normal teardown; its absence distinguishes a hard crash or external process termination from those handled exits.

For an unexplained Windows exit, launch through `pwsh tools/run_player_monitored.ps1`. It appends the PID, duration, and native exit code to `PhasmaPlayer.exit.jsonl` beside the selected executable and configures full user-mode dumps under `%LOCALAPPDATA%\CrashDumps`.

With `PE_ENABLE_RUNTIME_SHADER_COMPILER` off, the device has no shader compiler and can only `ReadSpvFile` from a populated cache, so the APK ships a **pre-baked SPIR-V cache**. Two engine properties make a desktop-baked cache resolve on-device. First, the `ShaderCache` key hashes the shader source/entry/defines with a deterministic FNV-1a (`Hash::CombineString`, `Fnv1a64` in `Base/Hash.h`) rather than `std::hash`, whose result diverges between the desktop MSVC STL and the NDK libc++ — so the same inputs produce the same on-disk filename on both. Second, the key (and the emitted bytecode) fold in the SPIR-V target version, which Android hard-forces to Vulkan 1.2; a desktop bake host pins the same target through the `PHASMA_SPIRV_TARGET` env override on the non-Android path. `tools/bake_android_shaders.ps1` drives a desktop Vulkan `PhasmaPlayer` at that target, creates temporary Android-runtime scene variants that enable the HUD pass toggles, also bakes a TAA-off variant for the Upsample path, harvests `ShaderCache/_spv/` into `Phasma/Player/android/prebaked/`, and scans every baked blob's `OpCapability` set. Gradle stages that tree as a top-level APK `ShaderCache/` (sibling of `Assets/`) and `PhasmaPlayerActivity` extracts it to `<internalStorage>/ShaderCache/`, the `Path::Root` location `ShaderCache::Init` reads; when the installed APK changes, the Activity replaces the extracted shader cache so same-version debug reinstalls cannot keep stale target-keyed blobs. The Vulkan device-feature gate (`RHI.cpp`) is split for cross-device Android portability rather than tuned to one GPU. Features the engine consumes unconditionally with no fallback are hard-required on every platform (`RequireVulkanFeature`) so a missing one is a clear startup abort, not a crash deeper in: the bindless descriptor set (`descriptorBindingPartiallyBound`, `runtimeDescriptorArray`, `shaderSampledImageArrayNonUniformIndexing`, `descriptorBindingVariableDescriptorCount`), `separateDepthStencilLayouts` (depth/stencil-only image layouts), and the GPU-culling indirect-draw features (`multiDrawIndirect`, `drawIndirectFirstInstance`). `bufferDeviceAddress` is capability-gated: VMA enables device addresses only when supported, and ray tracing plus descriptor-buffer paths remain disabled otherwise. Features the shipped shaders never declare a SPIR-V capability for are softened to warn-on-Android (`shaderInt64`, `shaderInt16`, `shaderStorageBufferArrayNonUniformIndexing`); `shaderFloat16` is warn-only on every platform because the shipped shaders do not use it and Polaris-class desktop GPUs lack it. The bake script enforces that split — if any baked blob declares a softened feature's capability, the bake fails and that feature must be promoted back to required.

Desktop DX12 device creation requests feature level 12_0. The renderer still requires Shader Model 6.6, resource-binding tier 3, and resource-heap tier 2 for its bindless layout. Built-in raster shaders always read the draw ID from the scene's indirect-command template as per-instance vertex data and flip clip-space Y in the vertex shader; DX12 uses positive-height viewports, and scaled blits use the matching UV transform. Keeping one Shader Model 6.6-compatible path makes the compatibility behavior continuously exercised on every DX12 device.

Some Android Emulator images can advertise a Vulkan loader while exposing no usable Vulkan device. The Pixel 9 Pro API 37 x86_64 16 KB Play Store image on this host reported loader 1.4 and `ro.cpuvulkan.version=4202496` (Vulkan 1.2), but `cmd gpu vkjson` returned `{}` and `vkCreateInstance` failed even after the player retried at Vulkan 1.2 with native `lib/x86_64`. In that state the failure is emulator GPU backend/configuration, not Android shader cache, ABI translation, scene aspect settings, or phone APK packaging. The working emulator path was an API 35 Google APIs x86_64 image where `cmd gpu vkjson` returned real device JSON; Phasma then selected the host NVIDIA GPU through `ranchu`, loaded Android Sponza, and ran at the emulator's 60 Hz limit. Android debug object naming is disabled because `vkSetDebugUtilsObjectNameEXT` crashed inside `vulkan.ranchu.so` on the working emulator during swapchain image naming; object names are optional debug metadata and not part of render correctness.


A game's own scenes bake too: `tools/bake_android_shaders.ps1 -ProjectPath <game> -ProjectScene <scenes> -ProjectWaitSeconds <s> -ProjectEnv NAME=value` runs them after the engine scenes in a temporary copy of the project laid out the way the APK stages it (the engine's RuntimeAssets `Shaders/` and `PassInfo/` win, the game's own files fill the gaps; everything else is junctioned to the game), so every cache key is the one the device computes even where the game's desktop copy of an engine shader differs. A project run counts only when its host is still running at the end of its time, logs `Scene loaded from:` for the scene and `[CppScript] module loaded`, and logs no `[ERROR] [CppScript]` line; before the runs the build's `NativeScripts.json` must show the host's C++ scripts come from that project. Any of these failing stops the bake before it writes a manifest. It backs up and restores the build folder's `phasma_settings.json` and runs its hosts with `audio_muted`. ATH bakes intro_ink_cpp, a hands-off spud_fields_3d_v1_cpp match that reaches the King (330 s) and hero_select_ink_cpp, with `PE_SCRIPT_ATH_MOBILE=1` so the phone preset's shader variants exist. The game's `Assets/Shaders/` and `Assets/PassInfo/` are bake inputs in both the manifest and Gradle's check (`androidShaderBakeInputs`), so editing a game shader makes the APK build ask for a new bake (verified 2026-09-29).

The APK stages the game's `Assets/` without `Save/` (extraction copies over the device's own saves) or the editor's `editor_config.json`, `editor_windows.json` and `imgui.ini` (the first clashed with the Android-local boot config). On Android the game's C++ scripts build as an object library whose objects archive into `PhasmaRuntime`, which the player links whole: the NDK's CMake 3.22 hand-written `--whole-archive` pair lost its closing flag once CMake merged link items and duplicated the unwinder (`Phasma/ProjectNative/ProjectNative.cmake`). The device picks its boot scene from `files/phasma_settings.json` `startup_scene` like a desktop player (written with `adb shell run-as` on a debuggable build; it survives reinstalls).

## Physical-device profiling caveats

Android remains a multi-device target. Treat the devices below as reproducers, not a compatibility definition: query each physical device's Vulkan features and per-format usage support before selecting an optional path, and provide a portable fallback when that path is needed by the renderer. The Mali-G610 reproducer advertises storage-image read/write without format and extended formats, but lacks `vertexPipelineStoresAndAtomics`; those capabilities must not be inferred for other Android GPUs. In particular, its formatless-write support does not justify an unconditional formatless TAA shader. The typed [downsampler contract](../rendering.md#downsampler-storage-formats) remains independent of formatless storage-image support (capabilities verified with `adb shell cmd gpu vkjson`, 2026-09-30).

Verify the native configuration from profiler snapshot `context.build_configuration`, not the APK's release label. The installed 0.20 APK on a Redmi Note 13 Pro+ 5G (Mali-G610 MC4) reported `RelWithDebInfo`; the local Android CMake cache used `-O2 -g -DNDEBUG`. This is suitable for investigating that installed build, but is not the project's native Release comparison gate. [Profiler capture](../../../../tools/profiler_capture.py) records the configuration and effective scene settings (verified 2026-09-29).

TAA's cost includes its G-buffer dependency: [SceneNeedsVelocityRT](../../../../Phasma/Runtime/Code/Render/SceneRenderTargets.cpp) retains velocity for TAA or motion blur, and [ApplyGBufferSurface](../../../../Phasma/Runtime/Code/RenderPasses/GbufferPass.cpp) selects `GBUFFER_NO_VELOCITY` when that attachment is absent. Exploratory 25-second ATH native first-wave captures on this phone, at 2712x1220 display / 1356x610 render resolution, measured G-buffer medians of 24.3 ms with TAA and 7.8 ms without it; depth and lighting were similar. Investigate the velocity-writing path before attributing the difference solely to the approximately 1.4 ms TAA resolve. This is a diagnostic lead, not proof of the hardware cause or a validated visual-quality tradeoff. A Forward+ off run and a baseline repeat both hit Mali `cpu queue set unrecoverable error` followed by `device lost`; exclude their truncated captures from comparisons. A later validation-enabled run reproduced the same GPU loss with the profiler disabled, so timestamp queries are not required to trigger it. Core and synchronization validation reported no preceding error after the composite-alpha fix below; this does not rule out shader memory errors or host/GPU data races. A subsequent 120-second observation with validation and profiling both disabled completed without loss; one passing run is not a stability guarantee (verified 2026-09-29).

The Vulkan swapchain must select `compositeAlpha` from `supportedCompositeAlpha`. This phone advertises only `INHERIT`; the old hardcoded `OPAQUE` raised `VUID-VkSwapchainCreateInfoKHR-compositeAlpha-01280`. [VulkanSwapchainImpl](../../../../Phasma/Core/Code/API/Vulkan/VulkanSwapchainImpl.cpp) now prefers opaque when supported and otherwise selects a supported alternative. A rebuilt Android core eliminated that validation error, but the intermittent device loss still reproduced. Do not treat this WSI correction as a GPU-loss fix (verified 2026-09-29).

For non-debuggable Android APKs, the [Khronos validation layer can be bundled in the APK](https://developer.android.com/ndk/guides/graphics/validation-layer). Keep diagnostic repackaging outside the repository, preserve the original APK/signature and app data, and restore the original after testing. Explicitly enable synchronization validation via `debug.vulkan.khronos_validation.validate_sync=true` when testing: [RHI::IsInstanceExtensionValid](../../../../Phasma/Core/Code/API/RHI.cpp) checks global extensions, so its `VK_EXT_layer_settings` gate alone does not demonstrate that synchronization validation was enabled. Save and restore any Android validation properties changed for a test. GPU-assisted shader instrumentation with VVL 1.4.363.0 disabled itself on this Mali device because `vertexPipelineStoresAndAtomics` was unavailable; ordinary validation therefore did not check shader memory accesses (verified 2026-09-29).

Desktop GPU-assisted validation exposed an independent mip-generation correctness issue: the embedded [downsampler](../../../../Phasma/Core/Code/API/Downsampler/Downsampler.cpp) declared `Rgba32f` for RGBA8 storage views. It now selects typed RGBA8, RG16F, RGBA16F and HDR RGBA32F modules, with distinct bytecode pipeline-cache identities; no formatless storage-image features are required. All four variants passed a desktop core-validation/GPU-AV format check, and the Android RelWithDebInfo core compiled. See [rendering notes](../rendering.md#downsampler-storage-formats) for the format and pipeline contracts (verified 2026-09-30).

With the composite-alpha and typed-downsampler fixes present, unattended Android RelWithDebInfo ATH native Map 1 runs still reproduced Mali `cpu queue set unrecoverable error` followed by `device lost`: after 173.9 seconds without validation and after 80.1 seconds with core/synchronization validation. Profiling was disabled in both, and neither had a preceding app-backgrounding event. Validation reported only shader-cache-file information and swapchain pre-transform performance warnings, with no core or synchronization error before loss. Thus neither validation nor profiling is required to trigger the failure; the corrections do not resolve it. These reproducer results do not qualify other Android devices (verified 2026-09-30). With the TAA-off Android preset installed (APK hash checked), unattended runs lost the device again at 73.8 s and 118.2 s of match with no preceding lifecycle, screen or kill event, so TAA and its storage-format mismatch are not the cause (verified 2026-09-30).

The remaining [SPD race reports](../rendering.md#downsampler-storage-formats) require investigation. The TAA, RCAS and SSAO storage-format mismatches (`Rgba32f`/`R32f` declared against BGRA8, R16F and R8 views) are fixed on desktop: scene colour targets are RGBA8 and the shaders declare their formats ([storage image formats](../rendering.md#storage-image-formats)); the changed shaders need a new Android bake. GPU-AV message counts are capped by the layer and instrumented timings are not performance evidence. Passing desktop validation of a correction does not establish Android stability or identify the Mali device-loss cause (verified 2026-09-30).
